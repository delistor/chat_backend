0全局地图

先记住这一句

Web 开发里几乎所有的复杂度，都源自同一个事实：HTTP 是无状态的、一问一答的、纯文本的。 服务器在两次请求之间不认识你，浏览器只能听服务器的话，而两者之间只靠一段可读的字符串沟通。 这门课九讲的全部内容——模板、会话、ORM、React、缓存、CSRF——本质上都是在给这个过于贫瘠的模型 补上它天生缺的东西。当你能看出某个框架特性"在补哪一块"，你就不再需要背它了。

0.1 这门课到底在教什么

很多人对 CS50W 的第一印象是"教你用 Django 写网站"。这个印象不能说错，但会让你用错力气。 课程真正想让你建立的是一张自上而下贯通的心智地图：从浏览器地址栏敲下回车的那一瞬间开始， 到屏幕上出现内容为止，中间经过了哪些层，每一层各自在做哪一类决定，以及——这一层为什么必须长成这样。

九讲的顺序不是随意的堆叠，而是沿着一条真实的请求链路，从最外层逐步往内走，再从内往外回到用户面前：

0 HTML/CSS→ 1 Git→ 2 Python→ 3 Django→ 4 SQL / 模型→ 5 JavaScript→ 6 用户界面→ 7 测试 / CI→ 8 扩展性与安全

这条链路上，前三讲是工具与语言（浏览器端的描述语言、版本控制、服务端语言）， 中间三讲是应用的主体（服务端框架、数据层、客户端脚本）， 后三讲是让它成为一个真东西（交互体验、可验证性、能扛住流量且不被攻破）。

一个关键判断

CS50W 不是一门 API 记忆课。Django 的某个函数叫什么名字，你可以随时查文档； 但"为什么这个请求必须带 CSRF token"、"为什么这个查询慢了一千倍"、"为什么这段代码在本地好好的，一上线就出错"—— 这类问题的答案不在文档里，而在这张心智地图里。课程的所有讲义都在往这张地图上贴东西， 而本文会在每一讲补上"课上没时间展开、但不懂就只能照抄"的那部分原理。

0.2 一条请求的完整旅程

下面这个演示把"在地址栏输入 https://example.com/hello?name=cs50 并回车"到"页面可以交互" 的全过程拆成了二十来步。请务必完整走一遍——后面九章讲的每一个主题，都能在这条链路上找到自己对应的那一格。

几个反直觉的点

1"打开一个网页"从来不是一次请求。 服务器发回来的那份 HTML 只是骨架；浏览器读完它会立刻发现里面引用了 CSS、JS、字体、图片， 然后并发发出几十上百个请求。这就是为什么"减少 HTTP 请求数"曾经是前端性能优化的头号话题， 也是为什么 HTTP/2 要引入多路复用——把"并发请求"从"开很多条 TCP 连接"变成"一条连接上跑很多个流"。

2服务器在两次请求之间根本不认识你。 HTTP 协议本身没有任何字段能表达"我是刚才那个人"。这不是设计失误，而是刻意的： 正因为无状态，服务器才能水平扩展——把你的请求发给哪台机器处理都一样。 而"记住你"这件事只能由应用层自己补：这就是 cookie 与 session 存在的全部理由（第 4 章）。

3你所谓的"服务器"，其实是一串软件叠起来的。 从外到内至少有三层：反向代理（Nginx，负责 TLS 终止、静态文件、限流）、 应用服务器（Gunicorn/uWSGI，负责把 HTTP 翻译成 Python 能懂的函数调用）、 以及 Django 应用本身。这个分层不是官僚主义，而是为了让每一层可以用最适合的语言和策略做自己那件事（第 9 章）。

4渲染是"先画再改"的，JS 随时能把已经画好的东西推翻。 HTML 解析、CSS 计算、布局、绘制、合成，这五步中每一步都可能被后来的 JS 打断并重来。 这就是为什么一个会阻塞主线程 3 秒的 for 循环会让页面看起来"死了"——它不是在等网络， 它是在等你的循环跑完，而这期间浏览器连一次重绘的机会都没有（第 6 章）。

1HTML 与 CSS：页面是怎么被"描述"出来的

先记住这一句

HTML 声明结构，CSS 声明匹配规则。 你写的 HTML 是一棵树，你写的 CSS 不是"给某个元素设置样式"，而是"声明一条规则：凡是满足这个条件的元素，都长这样"。 浏览器负责把这两者对上号。理解了这个"声明—匹配"模型，CSS 里所有让你困惑的东西（层叠、特异度、继承、为什么改不动） 都会立刻变得可预测。

1.1 服务器发回来的其实是一段文本

Web 的第一性事实：HTTP 响应体就是一段字节流，浏览器要靠响应头里的 Content-Type 才知道该怎么解读它。这个头没写对，页面就会以你意想不到的方式坏掉。

HTTP 响应原文
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8      ← 这两行决定了下面那段字节的命运
Content-Length: 137
Set-Cookie: sessionid=abc123; HttpOnly

<!DOCTYPE html>
<html lang="zh-CN">
  <head><meta charset="utf-8"><title>你好</title></head>
  <body><h1>你好，世界</h1></body>
</html>
Content-Type: text/html

浏览器按 HTML 规则解析，渲染出一个标题。

Content-Type: text/plain

浏览器把整份源码原样显示成文本——你会在页面上看到 <h1> 这五个字符。

最常见的翻车现场

Content-Type 还管着字符编码。如果你忘了写 charset=utf-8，也没有 HTML 里的 <meta charset="utf-8">，浏览器就会去猜（而且经常猜成 windows-1252）， 中文就会变成一串 ä½ å¥½。这是"乱码"的唯一成因，没有第二种。

顺带说一句：<!DOCTYPE html> 这一行不是给浏览器看的"版本号"， 而是一个开关——写上它，浏览器进入标准模式（standards mode）； 不写，浏览器会退回二十多年前的怪异模式（quirks mode），盒模型的计算规则都会不一样。 所以永远写上它。

1.2 HTML 是一棵树

浏览器解析 HTML 的过程，就是把这堆嵌套的标签折叠成一棵树。这棵树叫 DOM （Document Object Model，文档对象模型）。它不是"HTML 的另一种表示"，而是一个独立的东西： HTML 是文本，DOM 是内存里的对象树，JS 操作的是后者。

<!DOCTYPE html> <html> lang="zh-CN" ├── <head> │ ├── <meta> charset="utf-8" │ └── <title> CS50W 全解 └── <body> ├── <h1> 你好，世界 └── <ul> class="nav" ├── <li> 首页 └── <li> 关于

这棵树有几个必须记牢的性质：

  • 每个标签是一个节点，每个节点有父、有子。这就是为什么叫它"树"而不是"列表"。
  • 标签之间的空白文字也是节点。（叫 text node）——这是很多"为什么我的间距对不上"的根源。
  • 属性是节点的属性，不是子节点。所以 <a href="x"> 里的 href 要用 element.getAttribute('href') 读，而不是去找一个叫 href 的子节点。
  • 解析是容错的。你漏掉 </li>、把 <p> 嵌套错， 浏览器不会报错，而是按一套固定的补全规则猜你的意思。所以"本地看着没错"不等于"结构是对的"—— 错误的结构会让后面的 CSS 和 JS 一起出问题。
View Source 与 Inspect Element 看到的不是同一个东西

"查看源代码"显示的是服务器发来的原始文本；"检查元素"显示的是浏览器当前内存里的 DOM。 如果 JS 往页面里插入了内容，只有后者能看到。这个区别在调试时极其重要—— 当你怀疑"我的 JS 到底有没有生效"时，去 Elements 面板看 DOM，而不是去看源码。

1.3 语义化：为什么 <div> 泛滥是一种病

初学者很容易写出一份"能跑但全是 div"的 HTML：

能被解析，但什么都没说bad
<div class="header">
  <div class="title">我的博客</div>
  <div class="menu">
    <div class="item"><a href="/">首页</a></div>
  </div>
</div>
<div class="content">
  <div class="post">...</div>
</div>
结构本身携带信息good
<header>
  <h1>我的博客</h1>
  <nav><ul><li><a href="/">首页</a></li></ul></nav>
</header>
<main>
  <article>
    <h2>文章标题</h2>
    <time datetime="2026-03-01">2026 年 3 月 1 日</time>
  </article>
</main>

右边这份不只是"更好看"。它带来了三件左边永远做不到的事：

可访问性

屏幕阅读器靠语义标签来判断"这一段是导航，我用快捷键跳过"、"这是一级标题，我用标题跳转"。全是 div 的页面， 对盲人用户就是一片没有形状的噪音。

搜索引擎

Google 靠 <article>、<h1>、<time> 判断哪部分是正文、什么时候发布的。没有这些，你的内容在搜索结果里就是"一大堆文字"。

可读性与复用

半年后回来看，<nav> 比 <div class="menu"> 省一次脑内翻译。 而且浏览器的默认样式（比如 <h1> 会自动变大加粗）本来就是在帮你。

一个极易被忽略的细节

<a> 用来"跳到另一个地址"，<button> 用来"在当前页面做一件事"。 很多教程教你用 <a href="#" onclick="..."> 做按钮——这是错的： 它不能被键盘 Tab 聚焦后按 Enter 触发，屏幕阅读器会念成"链接"， 而且 href="#" 会把页面滚回顶部。用 <button>，它能白送你所有正确的默认行为。

1.4 表单：GET 与 POST 的分水岭

表单是 HTML 里唯一一个"会主动和服务器说话"的元素，也是 P0 项目的全部内容。 它的核心机制简单到只有两句话：每个有 name 属性的控件都会贡献一对"名字=值"， 这些对子被编码后发送到 action 指明的地址。而 method 决定了这些对子被放在哪里。

URL 查询串的规则

左边那一次提交，浏览器实际发出的请求是：

GET 请求原文
GET /search?q=cs50%26web&lang=zh&safe=on HTTP/1.1
Host: example.com

三个细节值得停下来看：

  • ? 之后是查询串，名字=值 用 & 连接，# 之后是片段（片段不会发给服务器）。
  • 值里的 & 必须被编码成 %26，空格变成 %20 或 +。 这套规则叫 URL 编码（percent-encoding）。如果不编码，你在搜索框里输入 a&b=c，服务器就会以为你提交了三个参数而不是一个。 这就是"注入"类漏洞的共同原型：把数据放进了本该放代码的位置。
  • 未勾选的复选框根本不会被发送（注意 safe=on 只在勾选时出现）。 这是新手最常踩的坑：后端要判断"没收到"而不是"收到了 false"。

1.5 CSS 怎么找上元素：选择器与特异度

CSS 不是"给元素设样式"，而是声明一批规则，每条规则有一个条件（选择器）和一组声明（属性:值）。 浏览器把页面上所有元素和所有规则做一次匹配，然后对每个元素决定"哪条规则赢"。决定胜负的规则只有四条， 按顺序比较：

① 来源与重要性→ ② 特异度→ ③ 出现顺序→ ④ 继承来的值（最弱）

第 ② 步"特异度"是绝大多数冲突的裁决者。它的算法是把选择器拆成三档计数，然后按字典序比较：

\[ \text{特异度} = (a,\; b,\; c) \qquad \begin{cases} a = \#\text{ID 选择器的个数} \\ b = \text{类 / 属性 / 伪类的个数} \\ c = \text{元素 / 伪元素的个数} \end{cases} \]

比较时不看总和，从 a 开始逐位比大小。所以 (0,1,0) 永远打赢 (0,0,99)——一个类选择器胜过九十九个元素选择器。这一点非常反直觉，动手试一下：

1.6 盒模型：宽度的谎言

页面上每一个元素，无论看起来是什么样，在浏览器眼里都是一个矩形盒子，由内到外四层组成： 内容（content）、内边距（padding）、边框（border）、外边距（margin）。 把 width: 300px 写在一个元素上时，这 300px 量的是哪一层？答案取决于 box-sizing—— 而这正是初学者写出"加起来超出一屏导致横向滚动条"的根本原因。

外边距折叠：一个反直觉但必须知道的规则

相邻的垂直外边距不会相加，只有大的那个生效。两个各带 margin-bottom: 20px 和 margin-top: 30px 的块级元素上下相接， 它们之间的间隙是 30px 而不是 50px。更极端的是父子的上外边距也会折叠—— 这解释了"我给子元素加了 margin-top，结果整个父元素带着它一起往下移"这个经典困惑。 折叠只发生在普通流的垂直方向；Flex 和 Grid 布局里不会折叠，加了 overflow: hidden 或 display: flow-root 建立 BFC 后也不会。

1.7 布局：从 float 到 Flexbox

CSS 布局的演化史，就是一部"用越来越贴切的原语描述二维排布"的历史。 理解这段历史能帮你读懂大量老代码，也能理解为什么 Flexbox 的每一个属性都长成那样。

正常流 1996

块级元素从上往下堆，行内元素从左往右排。这是默认行为，也是所有布局的起点。 想"并排"就要打破它——这就是后面所有麻烦的来源。

float 1998

本意是"让文字环绕图片"（像报纸排版），却被拿来当多列布局用。 需要 clear 清除浮动、父元素高度塌陷——全是副作用。 今天的用途只剩一个：真的要做文字环绕。

Flexbox 2012+

为一维排布而生：一行或一列。分配剩余空间、对齐、换行、顺序调整，全部有专门的属性。 它是"组件内部布局"的正确答案。

Grid 2017+

为二维排布而生：同时定义行和列。它是"页面整体骨架"的正确答案。 Flexbox 和 Grid 不是竞争关系，而是"一维"和"二维"两种工具。

Flexbox 的四个概念

Flexbox 的全部行为都可以用四个概念推导出来：容器与项目、主轴与交叉轴、主轴尺寸分配、对齐。 关键在于——方向是可以旋转的：把 flex-direction 设成 column， 主轴就从水平变成垂直，于是 justify-content 也跟着从"水平对齐"变成"垂直对齐"。 无数人在这上面栽跟头，就是因为把"justify = 水平"背成了口诀。

1.8 Grid 与响应式

Grid 把容器切成一个二维的格子矩阵，然后你可以指定项目"占第几行到第几列"。 它最实用的一个用法是自动响应式网格——只用一行 CSS 就能实现 "窗口宽就多排几列，窗口窄就少排几列"，完全不需要媒体查询：

一行搞定的响应式网格CSS
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(220px, 1fr));
  gap: 12px;
}

这一行读作："尽可能多地放列（auto-fit），每列最少 220px，剩下的空间平均分（1fr）。" 浏览器在布局时会自己算出当前宽度下能放几列。本文里所有的卡片网格（包括上面那几张）用的就是这一行。

响应式：三个必须先搞清楚的概念

  • <meta name="viewport"> 是前提。 手机浏览器默认会假装自己有 980px 宽，然后整体缩小显示（这样老网站不会碎）。 加上 <meta name="viewport" content="width=device-width, initial-scale=1"> 才是告诉它"请按真实宽度渲染"。P0 的移动端检查如果没通过，九成是漏了这一行。
  • 媒体查询判断的是视口，不是设备。 @media (max-width: 600px) 的含义是"浏览器窗口不超过 600px 时"， 所以它同样作用于把桌面窗口拖窄的用户，以及分屏显示的平板。
  • 移动优先意味着 min-width。 @media (min-width: 800px) 表示"宽于 800px 时追加样式"， 窄屏是默认状态。反之 max-width 是桌面优先，需要写一堆"覆盖回去"的规则。 两者的差别不只是写法，而是你默认服务的对象是谁。
写响应式时最有用的三个单位

rem（相对根元素字号）、%（相对父元素）、vw/vh（相对视口）。 再配合 clamp(最小值, 理想值, 最大值)，就能写出"字号随窗口平滑变化但有上下限"的效果， 比写一堆媒体查询断点更好维护：
font-size: clamp(1.6rem, 4vw, 2.6rem);

2Git：快照、分支与协作

先记住这一句

Git 不是"记录文件改动的列表"，而是一个由快照组成的图。 每个提交是一份完整目录树的快照，外加若干指向父提交的指针。分支不是文件夹、不是副本， 只是一个写着某个提交哈希的文件。想通了这一点，分支、合并、变基、 冲突这四件事会同时变得不言自明。

2.1 Git 存的是快照，不是差异

几乎所有人第一次接触版本控制时，脑子里装的都是"改动列表"模型：每次提交记录"这次改了哪几行"。 早期的工具（SVN、CVS）确实是这么存的。Git 不是。

在 Git 里，每一次提交都记录了当时整个项目的完整状态——不是"相对上一次改了什么"， 而是"此刻所有文件长什么样"。它通过几种对象来实现这件事：

commit # 一次提交 ├── tree # 项目根目录的快照 │ ├── blob # index.html 的内容 │ ├── blob # styles.css 的内容 │ └── tree # 子目录的快照（递归） │ └── blob ├── parent # 指向父提交（合并时有两个） └── author / message / timestamp

关键点在于：blob 是按内容寻址的。一个 blob 的编号由它的内容算出来。 所以两个内容完全相同的文件在仓库里只存一份；而"这次没改过的文件"在新快照里只是复用同一个 blob 引用， 并不产生新数据。这就是"每次都存全量快照"却不会让仓库爆炸的原因——不是它额外做了空间优化， 而是内容寻址让"复用"成了自然结果。

为什么这个区别很重要

"差异列表"模型里，"回到某个历史版本"需要把从头到尾的所有差异依次重放一遍； "快照"模型里，那个历史版本本身就完整存在于仓库中。这就是 git checkout 能在几十毫秒内切换到一年前的分支的原因——它只是把工作区文件换成另一份已经存在的快照。 也是为什么 Git 可以离线做几乎所有事。

2.2 三个区域与四种状态

Git 的日常操作之所以让人迷惑，是因为大部分命令的名字和它实际做的事并不是一一对应的。 真正需要建立的模型是"三个区域"：文件在你的工作区（working directory）、 在暂存区（staging area，也叫 index）、还是已经进了仓库（repository，即某次提交里）。

状态含义怎么进入怎么离开
untracked新文件，Git 完全不管它新建文件git add
modified已跟踪的文件被改了，改动还没进暂存区编辑文件git add（或 git restore 丢弃）
staged改动已经在暂存区，下次 commit 会包含它git addgit commit
committed已经进入某个提交，工作区和仓库一致git commit编辑文件
为什么"暂存区"这个设计一开始让人觉得多此一举

因为最直观的做法是"把当前所有改动一次性提交"。但暂存区的存在让你能把一堆混杂的改动 切成几个逻辑清晰的提交：修了一个 bug、顺手改了个错别字、又重构了一个函数—— 这三件事应该出现在三个提交里。git add -p 甚至可以让你逐块选择要暂存的改动。 这不是官僚流程，而是让 git log 在半年后仍然能被读懂的前提。

2.3 分支只是一个指针

课程讲义里有一个很重要的演示：创建一个新分支后，去 .git/refs/heads/ 目录里看一眼。 你会发现所谓"分支"就是一个文本文件，里面只有一行——一个提交哈希。

$ git checkout -b feature Switched to a new branch 'feature' $ cat .git/refs/heads/feature a3f9c1e8b7d6402f5a9e1c3b8d7f0a2e4c6b8d10 ↑ 一个分支的全部内容就是这一行

由此可以立刻推出几件事：

  • 创建分支是瞬时的，不需要复制任何文件。所以 Git 鼓励你"随便开分支"， 而这在 SVN 时代（分支 = 复制整个目录）是不可想象的。
  • HEAD 是"你在哪"，它是一个指向分支的指针。 git checkout feature 做的事就是"把 HEAD 指向 feature，然后把工作区文件换成 feature 指向的那个快照"。
  • 分支之间没有层级、没有父子。"主分支"只是一个大家都遵守的约定， Git 本身完全不知道 main 有什么特殊地位。
  • 提交会移动你当前所在的那个分支指针。这就是为什么切分支之前要先提交或暂存—— 否则你的改动会跟着你跑到另一个分支上去。

2.4 merge 与 rebase：两条历史怎么合流

当两条分支各自向前走了，你有两种方式把它们合起来。它们的最终文件内容可以完全一样， 但历史的形状不同——而历史形状是有后果的。

git merge feature
A───B───C───M ← main \ / D───E ← feature M 是一个真实的提交， 有两个父提交 B 和 E。 历史如实记录了"这两条线 曾经并行存在过"。
git rebase main（在 feature 上执行）
A───B───C───D'───E' ← main / feature D 和 E 被"重放"到 C 之上， 变成了全新的提交 D' 和 E' （哈希不同，因为父提交变了）。 历史变成一条直线。
rebase 唯一必须记住的规则

不要对已经推送到共享分支的提交做 rebase。因为 rebase 是"重写历史"—— 它丢弃原来的提交、创造新的提交。如果别人已经基于那些旧提交做了工作，你们的历史就会分叉成两套， 然后所有人都会被卷进一场痛苦的修复。 本地没推送过的提交随便 rebase；推送过的，用 merge。

"快进"（fast-forward）到底是什么

如果 main 在分叉之后没有新的提交，那么合并时根本不需要创建合并提交—— Git 只需要把 main 这个指针直接"挪"到 feature 的位置就行了。这叫 fast-forward。 它是 merge 的一个特例，也是最容易让人困惑的地方："我明明 merge 了，为什么 git log 里 看不到合并提交？" 因为确实没有。想让每次合并都留下记录，可以用 git merge --no-ff 强制产生合并提交。

2.5 冲突与撤销速查

冲突不是"Git 出错了"，而是Git 拒绝替你做一个它没有资格做的决定： 同一个文件的同一段内容，两条分支改成了不同的样子，哪个对？Git 不知道，只有你知道。 于是它把两种版本都留在文件里，让你选：

冲突现场文件里长这样
<<<<<<< HEAD
<h1>欢迎来到我的博客</h1>
=======
<h1>我的博客</h1>
>>>>>>> feature

<<<<<<< HEAD 到 ======= 之间是你当前分支的版本， ======= 到 >>>>>>> feature 之间是要合并进来的那条分支的版本。 你要做的是：把整个标记块替换成你想要的那段内容，然后 git add 这个文件， 再 git commit 完成合并。

三个最容易犯的错
  • 只删掉标记而没删掉不要的那一半内容。编辑器里那些 "Accept Current / Accept Incoming" 按钮是帮你做这件事的，但点完一定要自己看一眼结果。
  • 忘了 git add。解决完冲突后必须 git add， Git 才知道"这个文件我处理完了"。
  • 把 <<<<<<< 提交上去了。这条七字符的线一旦进了仓库， 它就会成为所有人的困惑来源。提交前 git diff --check 能自动查出来。

撤销操作速查（这张表能救命）

我想…命令它到底改了什么

撤销最近一次提交，改动退回工作区git reset HEAD~1指针回退，暂存区也清空
彻底丢弃最近一次提交及其改动git reset --hard HEAD~1指针、暂存区、工作区全部回退。危险
撤销一次已经推送的提交git revert <hash>创建一个新提交来抵消旧提交的改动，历史没有被改写
本地太乱了，完全对齐远程git reset --hard origin/main丢弃本地一切，变成远程的样子。危险
reset 与 revert 的判断标准只有一条

这个提交推送给别人了吗？没有 → 用 reset（干净、历史好看）。 推送了 → 用 revert（不改写历史，别人不会崩）。 这也是团队协作里会反复用到的判断：凡是"已经共享的东西"，就不能悄悄改掉。

3.4 函数是一等公民

"一等公民"的意思很朴素：函数和整数、字符串一样，是一个可以被传来传去的值。 这一条特性直接支撑起了后面所有的内容——Django 的路由表就是"URL 到函数"的映射， JS 的回调就是"把函数当参数传"，装饰器就是"吃一个函数、吐一个函数"。

把函数当值用Python
# 函数可以被赋给变量
square = lambda x: x * x

# 可以被当成参数传给别的函数（课程里用它来排序）
people.sort(key=lambda person: person["name"])

# 也可以在函数里定义函数，并把它返回出去
def make_multiplier(n):
    def multiply(x):
        return x * n
    return multiply

double = make_multiplier(2)
print(double(10))     # 20

最后那个例子是闭包：multiply 记住了它被创建时外部的 n， 即使 make_multiplier 已经返回了。闭包不是炫技，它是后面"装饰器"和 "中间件"能写出来的原因。

装饰器：不改函数本体，给它加行为

Django 里的 @login_required、@require_POST，都是装饰器。 课程讲义里给了一个最朴素的实现，看懂它就等于看懂了所有装饰器：

装饰器的本质：一个吃函数、吐函数的函数Python
def announce(f):
    def wrapper():
        print("About to run the function...")
        f()                       # 原函数在这里被调用
        print("Done with the function.")
    return wrapper                # 返回的是一个新函数

@announce                         # 等价于 hello = announce(hello)
def hello():
    print("Hello, world!")

hello()
# About to run the function...
# Hello, world!
# Done with the function.
看懂 @ 这一行的唯一诀窍

@announce 写在 def hello 上面，等价于在定义完之后立刻执行 hello = announce(hello)。也就是说：装饰器把 hello 这个名字 从原来的函数身上撕下来，贴到了 wrapper 上。 之后你每次调用 hello()，实际调用的都是 wrapper()， 而 wrapper 内部再调用原来那个函数。

这个"撕下来重新贴"的动作，就是为什么 Django 的 @login_required 能生效： 它把视图函数替换成了一个"先检查登录状态、再调用原视图"的新函数。 它没有修改你的视图，只是把名字接了过去。

课程里的 Point 例子Python
class Point:
    def __init__(self, x, y):
        self.x = x          # self 就是"这个对象本身"
        self.y = y

    def __str__(self):
        return f"Point({self.x}, {self.y})"

    def distance(self, other):
        return ((self.x - other.x) ** 2 + (self.y - other.y) ** 2) ** 0.5

p = Point(2, 8)
print(p)                    # Point(2, 8)  ← 调用了 __str__

三个必须记住的点：

  • self 不是关键字，只是约定俗成的第一个参数名。它代表"调用这个方法的那一个对象"。 p.distance(q) 实际执行的是 Point.distance(p, q)。
  • __init__ 不是构造函数，它是"对象创建之后被调用的初始化方法"。 真正创建对象的是 __new__——但你这辈子大概率不需要碰它。
  • 以双下划线包起来的方法是"魔术方法"，它们把对象接入 Python 的语法。 __str__ 让 print 能用，__len__ 让 len() 能用， __eq__ 让 == 能用。Django 的模型里你会看到 __str__ 反复出现—— 它决定了这个对象在 Admin 后台里显示成什么样子。

yield 让函数变成生成器：调用它不会执行函数体，而是返回一个"可以一次次要值的对象"。 每次向它要值时，函数从上次 yield 的地方继续跑。迭代、惰性求值、无限序列—— 全都建立在这个机制上。Django 的 QuerySet 就是惰性的：你写 Person.objects.filter(...) 时它不会碰数据库，直到你真正开始遍历它。

3.7 会让你半夜调 bug 的六个坑

坑 1 · 可变默认参数

见 3.2 节。默认值只求值一次，所有调用共用。

坑 2 · 闭包里的循环变量（晚绑定）

下面这段代码会打印四次 3，不是 0 1 2 3：

为什么全是 3Python
funcs = []
for i in range(4):
    funcs.append(lambda: i)

print([f() for f in funcs])   # [3, 3, 3, 3]

因为闭包捕获的是名字 i 本身，不是它当时的值。等这些 lambda 被调用时， 循环早就结束了，i 停在了 3。修法是给 lambda 加一个默认参数 lambda i=i: i——利用"默认值在定义时就求值"这个特性把当时的值钉住。 这和第 1 章讲的同一件事：什么时候求值，比写的是什么更重要。

坑 3 · 循环里修改正在遍历的列表

for x in lst: lst.remove(x) 会跳过元素——因为删除让后面的元素往前挪了， 而迭代器还在按老位置往下走。正确做法是遍历副本 for x in lst[:]， 或者用列表推导式造一个新列表。

坑 4 · 浮点数不精确

0.1 + 0.2 == 0.3 是 False。这不是 Python 的 bug， 是二进制浮点数的固有性质（就像十进制写不出 1/3）。判等要写 abs(a - b) < 1e-9；涉及金额则应该用整数（以分为单位）或 Decimal。

坑 5 · 整数除法与负数取整

7 / 2 得到 3.5（真除法），7 // 2 得到 3（向下取整）。 但"向下"是指数轴上的向下：-7 // 2 是 -4 而不是 -3。 分页计算里如果用错，就会出现"负数页码"这类离奇 bug。

坑 6 · 字符串编码

open("f.txt") 用的是操作系统默认编码——Linux 上通常是 UTF-8，Windows 上可能是 GBK。 所以同一份代码在两个人机器上跑出不同结果。永远显式写 open("f.txt", encoding="utf-8")。 Django 项目里凡是自己读写文件的地方，这条都适用。

4Django：请求的一生

先记住这一句

Django 是一个把"HTTP 请求"翻译成"Python 函数调用"的机器。 整台机器只有三个部件：一张路由表（URL → 函数）、一堆视图函数 （吃一个 request，吐一个 response）、以及一个模板引擎（把数据塞进 HTML 里）。 其余的一切——表单、会话、Admin、中间件——都是挂在这三个部件上的附件。

4.1 MTV：Django 的世界观

你可能听过 Django 用的是 "MTV" 模式，而别人说的是 "MVC"。这两个说法描述的是同一件事， 只是切分的位置不同：

经典 MVCDjango 里的对应物它负责什么不该负责什么
Model（模型）Model — models.py数据的结构、约束、关系不知道 HTML，不知道 HTTP
View（视图）Template — templates/把数据渲染成 HTML不查数据库，不做业务判断
Controller（控制器）View — views.py接收请求、调用模型、选模板不写 SQL，不拼 HTML 字符串

最容易搞混的是那个名字：Django 的 "View" 其实是别的框架里的 "Controller"， 而 Django 的 "Template" 才是别的框架里的 "View"。名字不重要，重要的是那条边界： 视图负责决定"发生什么"，模板负责决定"长什么样"。当你发现自己在视图里拼接 HTML 字符串， 或者在模板里写复杂的数据查询时，你就越过了这条线。

一个项目 = 多个应用

Django 用 startproject 建"项目"，用 startapp 建"应用"。 项目管配置（settings.py、根路由），应用管功能（一个可复用的模块）。 新建的应用必须写进 INSTALLED_APPS，否则 Django 完全看不见它——这是新手最常忘的一步。

URLconf 是唯一的人口

除了静态文件，任何请求都必须先经过 urls.py。 它先匹配项目级的 urlpatterns，遇到 include() 就剥掉前缀、转交给应用的 urls.py 继续匹配。这条链路决定了"哪个 URL 归谁管"。

视图的契约极其简单

输入是一个 HttpRequest 对象，输出必须是一个 HttpResponse 对象。 render()、redirect()、JsonResponse() 都只是"帮你造一个 HttpResponse"的快捷方式。理解这一点，"视图里能写什么"就没有疑问了。

4.2 URLconf 是怎么工作的

路由匹配是 Django 里最值得亲手玩一遍的东西，因为它的行为非常"字面"： 从上到下，逐条尝试，第一个匹配上的赢。没有优先级、没有智能推断。 下面这个演示允许你改路由表、改 URL，并逐条看到"为什么这条匹配了、那条没匹配"。

转换器速查

写法匹配什么正则等价于典型用途
<int:id>一个或多个数字（不含负号）[0-9]+主键、页码
<str:name>除 / 外的任意非空字符串[^/]+标题、用户名
<slug:s>字母、数字、连字符、下划线[-a-zA-Z0-9_]+URL 友好的标题
<uuid:u>标准 UUID[0-9a-f]{8}-…不可猜测的公开 ID
<path:p>包含 / 的任意非空字符串.+文件路径
为什么应该给 URL 起名字

path("wiki/<str:title>", views.entry, name="entry") 里的 name="entry" 不是为了好看。有了它，模板里就能写 {% url 'entry' title %}， 视图里就能写 reverse("entry", args=[title])， 而它们生成的 URL 会跟着路由表自动更新。 如果你到处硬编码 "/wiki/" + title，那么哪天你把 URL 从 /wiki/ 改成 /entry/，就要在几十个地方手动改一遍——并且一定会漏掉一处。

视图函数拿到的是一个 HttpRequest 对象。它上面挂着你需要的一切：

from django.shortcuts import render, redirect, get_object_or_404

def entry(request, title):
    content = util.get_entry(title)          # 取数据
    if content is None:
        return render(request, "encyclopedia/notfound.html", {
            "title": title
        })
    return render(request, "encyclopedia/entry.html", {
        "title": title,
        "content": markdown2.markdown(content),   # 转成 HTML
    })

注意 render 的三个参数：请求对象、模板路径、上下文（一个字典）。 模板里 {{ title }} 取的就是这个字典里的 title 键。 这个"字典 → 模板变量"的映射是 Django 模板系统的全部机制。

模板语言的三组语法

语法含义例子
{{ … }}把值打印出来（默认会 HTML 转义）{{ entry.title }}
{% … %}控制结构：判断、循环、继承、引入{% for e in entries %} … {% endfor %}
{{ x|filter }}过滤器：对值做一次加工{{ content|safe }}、{{ items|length }}
P1 Wiki 里最多人卡住的地方：|safe

Django 默认会把所有 {{ }} 里的内容做 HTML 转义—— 把 < 变成 &lt;。这是防止 XSS 攻击的核心防线， 是 Django 在保护你（第 9 章会详细讲）。

但 Wiki 项目要求你把 Markdown 渲染成 HTML 再显示。这时你希望浏览器把它当 HTML 解析， 而不是把标签当文字显示出来。于是你需要 |safe 告诉 Django"这段内容我担保它是安全的， 别转义"：

不加 safe结果
{{ content }}
页面上看到：
<h1>Python</h1>   ← 标签被当成了文字
加 safe结果
{{ content|safe }}
页面上看到：
Python          ← 变成了真正的一级标题

但请想清楚你在做什么：|safe 是在说"这段内容可以执行"。 如果这个内容来自用户输入而你没有先清洗它，你就亲手打开了一个 XSS 漏洞。 Wiki 项目里因为内容是学生自己写的、且由 markdown2 生成，风险可接受； 但换成评论区、用户昵称这类地方，就必须用别的办法。 第 9 章的 XSS 演示会让你亲眼看到这个区别。

模板继承：不要复制粘贴导航栏

每个页面都有一样的导航栏和页脚，把它们抄 N 遍是最糟的做法。 Django 的 {% extends %} 让"布局"和"内容"分开：

templates/encyclopedia/layout.html骨架
<body>
  <nav><a href="{% url 'index' %}">首页</a></nav>

  <div class="main">
    {% block body %}
    {% endblock %}
  </div>
</body>
templates/encyclopedia/entry.html子模板
{% extends "encyclopedia/layout.html" %}

{% block body %}
  <h1>{{ title }}</h1>
  {{ content|safe }}
{% endblock %}

{% extends %} 必须是子模板的第一条语句。它的含义是"先渲染父模板， 遇到 {% block %} 就把子模板对应的块塞进去"。 这让"改一次导航栏，全站生效"成为可能，也是所有现代前端框架"组件化"思想的雏形。

forms.Form 帮你做三件事：渲染（{{ form }} 直接把字段变成 HTML 控件）、 验证（类型、必填、长度都在 is_valid() 里一次做完）、 回填（验证失败时用户填过的内容不会丢）。这三件事手写都极其枯燥且容易出错。

补充 ModelForm：更省事的一层

官方讲义里只讲了 forms.Form。但 Django 还有一个 forms.ModelForm， 它能直接从模型生成表单——字段名、类型、甚至数据库层面的约束都自动带上：

从模型直接生成表单forms.py
class ListingForm(forms.ModelForm):
    class Meta:
        model = Listing
        fields = ["title", "description", "starting_bid", "image_url", "category"]

# 视图里：
form = ListingForm(request.POST)
if form.is_valid():
    listing = form.save(commit=False)   # 先别存
    listing.owner = request.user        # 补上表单里没有的信息
    listing.save()                      # 现在存

commit=False 是 P2 Commerce 里非常常用的一招： 表单里不该出现"卖家是谁"这个字段（那不能让用户填），但数据库要求它非空。 于是先拿一个未保存的对象，手工补上 owner，再保存。 你的项目里凡是"创建时自动归属给当前用户"的东西，都是这个套路。

CSRF token：那个神秘的 {% csrf_token %}

每个 POST 表单里都必须写 {% csrf_token %}，否则 Django 会直接返回 403。 它不是形式主义：

没有它会发生什么

假设你已经登录了 bank.com，浏览器里存着你的会话 cookie。 现在你点开了 evil.com，那个页面上藏着一个自动提交的表单：

<!-- evil.com 上的隐藏表单 --> <form action="https://bank.com/transfer" method="post"> <input type="hidden" name="to" value="攻击者"> <input type="hidden" name="amount" value="10000"> </form> <script>document.forms[0].submit()</script>

浏览器会自动带上 bank.com 的 cookie（cookie 是按域名发的，不看是谁打开的页面）， 于是这笔转账在银行看来完全合法——因为请求确实来自你的浏览器、带着你的凭证。 这叫跨站请求伪造（CSRF）。

{% csrf_token %} 会往表单里塞一个只有你的服务器知道如何生成的随机值。 evil.com 上的页面无法读到你的银行页面里的这个值（同源策略拦着）， 所以它伪造的请求里没有 token，服务器一眼就能看穿。 第 9 章会看到这个攻击的完整演示。

4.5 会话与认证

HTTP 是无状态的（第 0 章）。"记住用户登录过"这件事必须由应用层自己补。 Django 的做法是会话（session）：把一个随机 ID 放进 cookie， 真正的数据存在服务器端。

① 浏览器
Cookie 里只有一行：
sessionid=a3f9c1e8…

它看不懂这串字符的含义。它只是一个"会员卡号"，每次请求原样带上。
② 服务器
django_session 表里查这个 ID：
{'user_id': 7, 'cart': [3,9]}

真正的数据在这里。用户改了不 cookie，因为内容是服务器说了算的。
③ 退出登录
服务器删掉这一行。

即使攻击者偷到了那串 ID，它也已经失效了。这就是服务端会话相对"把数据全塞进 cookie"的优势。
会话的基本用法views.py
def add(request):
    if "tasks" not in request.session:      # 第一次访问，先初始化
        request.session["tasks"] = []
    request.session["tasks"].append(new_task)  # 直接当字典用
    return redirect("tasks:index")
一个必须知道的性能细节

会话数据默认存在数据库里。也就是说，每次请求都要多查一次数据库来取会话。 在高流量站点上这是一笔不小的开销——第 9 章讲扩展性时，"把会话搬到 Redis"是标准动作之一， 原因就在这里。

认证：authenticate / login / logout

手写的登录视图views.py
from django.contrib.auth import authenticate, login, logout
from django.http import HttpResponseRedirect
from django.urls import reverse

def login_view(request):
    if request.method == "POST":
        username = request.POST["username"]
        password = request.POST["password"]
        user = authenticate(request, username=username, password=password)
        if user is not None:
            login(request, user)          # 把 user 写进 session
            return HttpResponseRedirect(reverse("index"))
        else:
            return render(request, "users/login.html",
                          {"message": "Invalid credentials."})
    return render(request, "users/login.html")

def logout_view(request):
    logout(request)                       # 清掉 session
    return HttpResponseRedirect(reverse("index"))

authenticate() 做的事是：拿到用户名，查出对应的用户，把用户输入的密码用同样的算法哈希一遍， 和数据库里存的哈希值比对。它从不"解密"密码——因为数据库里根本没有密码的明文（第 9 章）。

补充 保护视图的三种方式
  • @login_required 装饰器 —— 未登录时自动跳转到登录页。P2 Commerce 的提示里点名了这个装饰器。
  • request.user.is_authenticated —— 在模板或视图里手动判断，用于"登录了才显示某个按钮"这种场景。
  • 在查询里加上所有权条件 —— 这是最重要的一条，也是最容易漏的一条： Listing.objects.get(id=id, owner=request.user)。 仅仅在页面上隐藏按钮是不够的，任何人手打 URL 都能绕过界面。

5SQL、模型与迁移：数据放在哪里

先记住这一句

关系数据库解决的是一个很朴素的问题：把数据拆成互不重复的几张小表，用"编号"互相引用。 SQL 是你向它提问的语言，ORM 是"把 Python 写成 SQL"的翻译层，迁移是"把模型改动写成 ALTER TABLE"的版本控制系统。 这一讲的每一个主题都在回答同一个问题：数据以什么形状存在，以及你为这个形状付出了什么代价。

5.1 关系模型解决了什么

假设你要存航班信息。最直觉的做法是一张大表，每行一个航班，把航空公司的名字、城市都写进去：

航班出发城市到达城市时长
AA101New YorkLondon415
AA102LondonNew York435
AA103New YorkShanghai810

这张表有两个致命问题：

  • 重复。"New York" 出现了两次。将来要把城市名改成 "NYC"，你得改好几行—— 漏掉一行，数据就自相矛盾了。
  • 没地方放别的信息。每个城市有国家、时区、机场代码，放哪儿？放在航班表里会跟着重复， 而且一个城市没有航班时就无处可放。

关系模型的答案是拆表 + 引用：城市单独一张 airports 表， 给它一个编号；航班表里只存编号。

airports

现在"New York"在所有航班里出现多少次，实际都只存了一份。 flights.origin 里的数字 1 是一个外键（foreign key）， 它指向 airports.id。

拆表的代价：查询变复杂了

代价是显而易见的：你现在无法从一张表里读出"从纽约出发的航班有哪些"—— 你得先把 airports 里 id=1 找出来，再去 flights 里找 origin=1 的行。 这个"跨表把数据拼回去"的动作就叫 JOIN， 它是关系数据库里最重要的一个操作，也是这一讲的核心。

5.2 SQL 的执行顺序（不是书写顺序）

下面这个实验台里有一个真的会执行 SQL 的迷你引擎，内置三张表。 它最大的价值不是"能查到结果"，而是右侧那个执行计划： 它会显示每一步之后还剩多少行，让你看到 SQL 的执行顺序和你写下来的顺序完全不一样。

三条最容易记错的规则
  • AND 的优先级高于 OR。A OR B AND C 会被理解成 A OR (B AND C)。 不确定就加括号，永远不要赌自己的记忆。
  • NULL 不等于任何值，连它自己也不等。WHERE x = NULL 永远不成立，必须写 WHERE x IS NULL。这是 SQL 里最反直觉、最容易造成静默错误的一条。
  • COUNT(*) 数行数，COUNT(col) 只数该列非 NULL 的行数。 在有空值的列上，这两个结果会不一样。

5.3 JOIN 到底在做什么

JOIN 不是什么神秘操作，它就是一个双重循环：

JOIN 的本质（伪代码）概念模型
结果 = []
for 左表的每一行 L:
    for 右表的每一行 R:
        if L.外键 == R.主键:        # 这就是 ON 条件
            结果.append(L 和 R 拼在一起)

# 所以 JOIN 的结果列数 = 左表列数 + 右表列数
# 在没建索引的情况下，比较次数 = 左表行数 × 右表行数

最后那两行注释解释了很多事：为什么 JOIN 之后列名会重复（两张表都有 id， 所以必须写 flights.id 才不会歧义），以及 为什么大表 JOIN 会慢（十万行 JOIN 十万行 = 一百亿次比较，除非有索引把内层循环变成 O(log n)）。

JOIN 类型行为什么时候用
INNER JOIN只保留两边都匹配上的行默认。想同时看到"航班"和"它的出发城市"
LEFT JOIN保留左表全部行；右表没匹配上的填 NULL"列出所有机场，以及它们各自的出发航班数（没有就是 0）"
RIGHT JOIN镜像的 LEFT JOIN很少用，交换表的顺序写 LEFT JOIN 通常更清楚
FULL OUTER JOIN两边都保留找"互不匹配的记录"
LEFT JOIN 是"找孤儿数据"的标准手法

想知道"哪些机场从来没被当作出发地"？用 LEFT JOIN 之后筛 NULL： SELECT code FROM airports LEFT JOIN flights ON airports.id = flights.origin WHERE flights.id IS NULL。 这个"左连接 + 判空"的模式在数据清理中几乎天天用到。

5.4 三种关系与中间表

表与表之间只有三种关系，而它们全都用同一种机制实现——外键：

一对多 最常用

一个机场有多班出发航班。外键放在"多"的那一侧： flights.origin → airports.id。 Django 里写 models.ForeignKey(Airport, on_delete=models.CASCADE, related_name="departures")。

一对一

一条记录恰好对应另一条。用 OneToOneField， 数据库层面加唯一约束。最常见的用途是"给内置的 User 加一个扩展资料表"—— 不要为了加两个字段就去改 Django 自带的用户模型。

多对多 需要中间表

ORM 做的事只有一件：把 Python 的方法调用翻译成 SQL，再把返回的行包装成 Python 对象。 它的价值不在于"不用学 SQL"，而在于：同一个模型定义同时决定了两件事——Python 对象的形状， 和数据库表的形状。

你写的 Pythonviews.py

QuerySet 是惰性的

这一行代码不会碰数据库

qs = Flight.objects.filter(duration__gt=500) —— 执行完这一行，数据库什么都不知道。 Django 只是构造了一个 QuerySet 对象，记下"我要查这些"。 真正执行发生在你第一次遍历它的时候（for f in qs、len(qs)、 list(qs)、qs[0]）。这叫惰性求值。

这个设计带来两个好处（可以任意链式拼接 .filter().filter().order_by()， 最后只发一条 SQL），以及一个坏处：你无法从代码的"看起来在做什么"判断它有没有查数据库。 所以你需要一个工具来看真实发生了什么——那就是下一小节的 N+1。

5.6 N+1：最经典的性能事故

N+1 问题的定义很简单：你想要 N 条数据，并为这 N 条数据各自又查了一次数据库， 于是发了 N+1 条 SQL。它的可怕之处在于——在小数据量下完全看不出来， 等数据涨上去之后突然变成 10 秒的响应时间，而代码一行都没改。

写法 A：N+1bad
flights = Flight.objects.all()      # 1 条 SQL

for f in flights:
    print(f.origin.city)            # 每个航班 1 条 SQL

# 总共 1 + N 条
写法 B：一次查完good
flights = Flight.objects.select_related("origin").all()

for f in flights:
    print(f.origin.city)            # 不会再有查询

# 总共 1 条（SQL 里多了个 JOIN）
方法用在生成什么
select_related("a")外键、一对一（"多对一"方向）一条带 JOIN 的 SQL
prefetch_related("a")多对多、反向外键（"一对多"方向）两条 SQL，在 Python 里拼起来
annotate(Count("a"))要的是"每条的关联数量"而不是关联对象本身一条带 GROUP BY 的 SQL
怎么发现自己写了 N+1 补充

Django 自带一个开关：在 settings.py 里把 DEBUG = True 时， 每条 SQL 都会记在 connection.queries 里。更省事的做法是装一个 django-debug-toolbar，它会在页面侧边显示这次请求一共发了几条 SQL。 养成"打开页面时瞄一眼 SQL 条数"的习惯，你会比 90% 的人少写很多慢代码。

5.7 迁移：模型改动怎么变成表结构

你改了 models.py，数据库里那张表不会自动跟着变。 数据库只认 SQL，不认 Python。迁移（migration）就是两者之间的桥：

改 models.py→ makemigrations 生成迁移文件→ migrate 执行 SQL→ 数据库结构变了

OK

生成的迁移文件是纯 Python，你可以打开看、甚至手改。它长这样：

    operations = [
        migrations.AddField(
            model_name="listing",

迁移系统的三个真相
  • 迁移文件必须提交进 Git。它们是数据库结构的历史记录。 如果只有你本地有，别人 clone 下来的项目就建不出正确的表。
  • 迁移文件一旦推送给别人执行过，就不要去改它。新建一个迁移来修正—— 这和"已推送的提交不做 rebase"是同一条原则。
  • 删字段会丢数据，且没有撤销按钮。Django 会问你"你确定要删吗"， migrate 执行完那个列就没了。生产环境上动结构之前，先备份。
一个 P2 里一定会遇到的坑

你给模型新增一个没有默认值的非空字段，然后 makemigrations， Django 会停下来问你："现有行该怎么填这个字段？" 如果你 Ctrl+C 跑掉， 会留下一个只有一半的迁移文件，之后所有命令都会报错。 正确做法是二选一：给字段加 default=… 或 null=True， 或者老老实实回答它的交互式提问。 一旦卡住了，删掉那个半成品迁移文件、改好模型重新 makemigrations 即可。

5.8 索引：为什么有的查询快一千倍

没有索引时，数据库找一个值只能把整张表从头读到尾（全表扫描）。 有索引时，它可以在一个排好序的结构上逐层缩小范围。

建索引的两种方式SQL vs Django
-- 裸 SQL
CREATE INDEX flights_origin_index ON flights (origin);

# Django：在模型的 Meta 里声明
class Flight(models.Model):
    origin = models.ForeignKey(Airport, on_delete=models.CASCADE,
                               related_name="departures")

    class Meta:
        indexes = [models.Index(fields=["origin"])]
        # 另外：外键字段 Django 会自动建索引，不用手动加
索引不是免费的，也不是越多越好

每建一个索引，数据库就多维护一棵树：每次 INSERT / UPDATE / DELETE 都要更新所有相关索引， 而且索引本身占磁盘（通常是被索引列的几倍）。所以：

  • 该建：WHERE 里频繁出现的列、JOIN 的 ON 列、ORDER BY 的列。
  • 不该建：取值只有两三种的列（比如 is_active）、几乎不查询的列、 写多读少的表上乱加。
  • 复合索引的顺序有讲究：(a, b) 能加速"只查 a"和"查 a 且 b"， 但加速不了"只查 b"——因为它是按 a 先排序的。这是最经典的索引误区。

5.9 事务与设计陷阱

事务：要么全做，要么全不做

课程里提到过"竞态条件"（race condition）：两个人同时出价，都读到"当前最高价 100"， 于是都认为自己的 101 合法——最终数据库里两条 101 的记录，拍卖结果错了。

把一组操作打包成不可分割的一步views.py
from django.db import transaction

@transaction.atomic
def bid(request, listing_id):
    listing = Listing.objects.select_for_update().get(id=listing_id)   # 加锁
    ...
    # 这里的所有数据库操作要么全部成功，要么全部回滚

事务保证的四个性质（ACID）里，P2 里最关键的是隔离性（Isolation）： 两个并发事务互相看不到对方的中间状态。而 select_for_update() 更进一步， 它把这一行锁住，让第二个请求必须等第一个提交完才能读—— 于是"读到旧价格"这件事从根本上不可能发生。

P2 里"出价"这一项的正确写法

课程要求"出价必须大于等于起拍价，且必须严格大于此前任何出价"。这句话翻译成代码时， 检查和写入之间不能有任何空隙：

五个设计陷阱

① 把"能算出来的"也存起来

存了 total_price 又存 quantity 和 unit_price， 三者早晚会不一致。先问：这个值能不能从别的字段推出来？能推就不要存。

② 用字符串存日期和金额

字符串比较 "2026-9-2" > "2026-10-1" 是成立的——因为按字典序。 日期用 DateField，金额用 DecimalField（不是 Float，浮点数会丢精度）。

③ 一张表一个"类型"字段，塞进所有东西

用一个 type 列区分"航班 / 火车 / 汽车"，于是大量列对大部分行都是 NULL。 这通常说明该拆成几张表。

④ 忘了唯一约束

"一个用户对一个商品只能有一条心愿单记录"——如果不在数据库层面加 unique_together，两次快速点击就能造出两条。应用层的判断挡不住并发。

⑤ 在视图里写裸 SQL 拼字符串

⑥ 在循环里查数据库

就是 5.6 节的 N+1。它在开发阶段永远不会暴露，因为它只在数据量上来之后才变成灾难。

6JavaScript：单线程的并发

先记住这一句

JavaScript 只有一个线程，同一时刻只能执行一段代码。它之所以看起来能"同时做很多事"， 是因为把等待（网络、定时器、用户点击）交给了浏览器，只在事情真的完成时才把回调塞回队列。 理解了"调用栈 + 任务队列"这个模型，setTimeout(fn, 0) 为什么排在 Promise 后面、 为什么会"卡死"、为什么 await 之后代码就换了个人执行——全都不需要背。

6.1 单线程意味着什么

在很多语言里，"同时做两件事"最简单的方式就是开两个线程。JS 不能这么做——这不是缺陷， 而是为浏览器这个特定场景做的取舍：如果一个页面有两个线程同时操作同一段 DOM， 谁说了算？锁、竞态、死锁会立刻从后端问题变成前端问题。

所以 JS 的选择是：你的代码永远只在一个线程上跑，绝不会有半路被打断的可能。 所有"等待"都外包给浏览器，完成之后通过回调通知你。

这个取舍买到了什么、付出了什么

买到了：你再也不需要在 JS 里考虑数据竞争——一个变量读出来之后， 在你用完它之前不可能被别的线程改掉。这消灭了一整类最难的 bug。

付出了：你的代码阻塞主线程时，页面真的会死。 一个 3 秒的 while 循环会让整个页面无法滚动、无法响应点击， 因为渲染和事件处理也在同一个线程上排队。 "不要阻塞主线程"是前端性能的第一条原则，原因就在这里。

6.3 作用域、闭包与 var 的陷阱

一个在 P3/P4 里几乎人人都会踩的坑JavaScript

    document.querySelectorAll("button")[i].addEventListener("click", function () {
        console.log(i);          // 点哪个都输出 3

        await markRead(emails[0].id);
        console.log("done");
    } catch (err) {
        console.error(err);
    }
}
关于 async/await 最容易误解的一点

await 不是"暂停整个程序"，它只是"暂停这个 async 函数"。 函数在 await 处挂起、控制权交回调用者，把后面的代码注册成微任务。 所以如果 await 后面的几行代码希望并行执行，这样写是错的：

串行：一共等 2 秒慢
const a = await fetch(url1);   // 等 1 秒
const b = await fetch(url2);   // 再等 1 秒
并行：只等 1 秒快
const [a, b] = await Promise.all([
    fetch(url1),
    fetch(url2),               // 两个请求同时发出
]);

状态码怎么读

200 成功 ｜ 201 创建成功（P3 发信成功返回的就是它）｜ 204 成功但没有内容 ｜ 400 你的请求有问题 ｜ 401/403 没登录 / 没权限 ｜ 404 找不到 ｜ 500 服务器自己崩了。 关键在 4xx 和 5xx 的区别：4xx 是"你错了"，5xx 是"我错了"。 写 API 时这个区分直接决定了日志该记给谁看。

6.9 六个会让你调很久的坑

① this 是谁取决于怎么调用

同一个函数，写成 obj.fn() 时 this 是 obj， 单独写 fn() 时是 undefined。解决办法：一律用箭头函数。 箭头函数没有自己的 this，它会捕获外层的那一个——这正是你要的。

② JSON.parse 会抛异常

如果服务器返回的不是合法 JSON，JSON.parse 会抛 SyntaxError。 当你不确定返回内容时（比如 500 错误页返回的是 HTML），先 response.text() 看一眼再决定。

③ localStorage 只能存字符串

localStorage.setItem("x", {a:1}) 存进去的是 "[object Object]"。 必须 JSON.stringify 存、JSON.parse 取。而且它永远不过期， 敏感信息不要放。

④ NodeList 与数组不是一回事

querySelectorAll 返回的 NodeList 有 forEach 但没有 map、filter。 要转换写 Array.from(nodes) 或 [...nodes]。

⑤ 隐式的全局变量

忘了写 let 就赋值，会在严格模式外静默创建一个全局变量， 污染整个页面。所有脚本文件开头写 "use strict";，或者用 ES Module 语法，能避免这类问题。

⑥ 在循环里给所有元素绑同一个变量

就是 6.3 节那个 var 的坑。用 let，或者改用事件委托。

7用户界面：从 CSS 动画到 React

先记住这一句

前端框架解决的不是"渲染性能"，而是"状态一多，你就记不住该更新哪块 DOM"这个问题。 React 的核心承诺只有一句：你只负责描述"界面在某个状态下应该长什么样"， 算出"哪几个 DOM 需要改"这件事交给它。 在你亲手写过一个"状态 A 变了之后忘了更新 B"的 bug 之后，这句话的分量才会真正显现。

7.1 交互的第一原则：不要让用户等

课程讲义里反复强调的一个体验原则，可以用一句话概括： 任何需要超过 100 毫秒的操作，都必须立刻给出反馈。

延迟用户的感觉该怎么做
< 100 ms即时什么都不用做
100 ms – 1 s稍有停顿，但还连着可以什么都不做，但给出按下状态（按钮变暗）更好
1 s – 10 s注意力开始漂移必须给进度指示（骨架屏、转圈、进度条）
> 10 s会去干别的，甚至以为坏了后台任务 + 完成通知
P3 Mail 的"归档"按钮体现的就是这条原则

归档一封邮件要发一个 PUT 请求，几百毫秒。如果你什么都不做， 用户点完按钮会觉得"没反应"，于是再点一次——结果发了两个请求。 正确做法是立刻把那一行从列表里移走（乐观更新），再发请求； 如果请求失败了，再把它放回去并提示错误。 先假装成功，再处理失败。这是所有现代界面处理网络延迟的默认姿势。

7.2 CSS 过渡与动画

课程讲义里讲了 @keyframes 那一套。它和 transition 的区别是： transition 是"状态变化时自动补间"，animation 是"按剧本演一遍"。

transition：A 状态 → B 状态CSS
.card {
    opacity: 1;
    transform: translateY(0);
    transition: opacity .2s ease, transform .2s ease;
}
.card.hidden {
    opacity: 0;
    transform: translateY(-8px);
}

/* 加上 .hidden 类，浏览器就自动在 0.2 秒内补间 */
/* 适合：悬停、显示/隐藏、消息滑入 */
@keyframes：完整的剧本CSS
@keyframes fade-out {
    0%   { opacity: 1; transform: translateY(0); }
    75%  { opacity: 1; }              /* 停一下 */
    100% { opacity: 0; transform: translateY(-8px); }
}

.post.removing {
    animation-name: fade-out;
    animation-duration: .4s;
    animation-fill-mode: forwards;    /* 停在最后一帧 */
}

/* 适合：需要多段、循环、或"必须播完"的效果 */

让 JS 知道动画什么时候结束

课程讲义里"删除一条"的标准写法JavaScript
element.parentElement.style.animationPlayState = "running";
element.parentElement.addEventListener("animationend", function () {
    element.parentElement.remove();     // 动画播完再真的删掉
});

这个模式很值得记住：CSS 负责"怎么动"，JS 负责"动完之后干嘛"。 animationend 事件是两者之间的握手点。没有它，你就只能用 setTimeout 猜一个时长——而一旦改了 animation-duration， 那个猜的时间就对不上了。

补充 为什么动画只该用 transform 和 opacity

浏览器的渲染有五个阶段：解析 → 样式计算 → 布局（Layout）→ 绘制（Paint）→ 合成（Composite）。 改一个元素的 width 或 top，会让整个页面重新布局—— 所有受影响的元素都要重新算位置，然后在主线程上重新绘制。 而 transform 和 opacity 可以完全跳过布局和绘制， 直接在合成阶段由 GPU 处理。

所以：动画要用 transform: translateX(...) 而不是 left， 要用 transform: scale(...) 而不是 width。 课程讲义没有展开这一层，但这是"为什么我的动画卡"这个问题的标准答案。

手写 SPA 很快就会变成这样JavaScript
function updateView() {
    // 用户登录了 → 显示用户名，隐藏登录按钮
    if (user) { nameEl.textContent = user.name; loginBtn.hidden = true; }

这就是"状态同步"问题：同一份数据（比如 user）在页面上有五个地方在用， 你必须记住每次它变化时要更新哪五个地方。漏掉一个，界面就会显示错误的信息—— 而且这种 bug 很难复现，因为它取决于用户的操作顺序。

框架的答案：声明式 + 接管更新

与其手写"数据变了要改哪里"，不如声明"界面长什么样取决于哪些数据"：

// 你写这个（声明：界面 = f(state)） function Comment({ comment }) { return <div className="comment"> <h3>{comment.author}</h3> <p>{comment.content}</p> </div>; } // 然后只要 comment 变了，这个 div 就会自己变对。 // 你从来不需要写"把 h3 的文字改掉"这句话。

7.4 React：组件、props、state

课程讲义用 CDN 的方式引入 React，这样不需要任何构建工具就能上手：

最小的 React 页面HTML
<div id="app"></div>

<script src="https://unpkg.com/react@17/umd/react.production.min.js"></script>
<script src="https://unpkg.com/react-dom@17/umd/react-dom.production.min.js"></script>
<script src="https://unpkg.com/@babel/standalone/babel.min.js"></script>

<script type="text/babel">
    function App() {
        const [count, setCount] = React.useState(0);
        return (
            <div>
                <h1>Count: {count}</h1>
                <button onClick={() => setCount(count + 1)}>+1</button>
            </div>
        );
    }
    ReactDOM.render(<App />, document.querySelector("#app"));
</script>

三个概念：

JSX

让你在 JS 里直接写类 HTML 的东西。它不是模板字符串，而是语法糖—— 会被 Babel 编译成一堆 React.createElement(...) 调用。 所以 class 要写成 className，因为 class 是 JS 保留字。

组件 = 函数

一个返回 JSX 的函数就是一个组件。它必须大写开头——小写会被当成 HTML 标签。 这也是为什么 <Hello /> 能用而 <hello /> 不行。

props：父传子的只读数据

<Hello name="Harry" /> 里的 name 在组件内部通过 props.name 读。子组件不能修改 props——想改就得让父组件改， 这是"单向数据流"的强制实现。

state：组件自己的记忆

const [count, setCount] = React.useState(0)。只有调用 setCount （或别的 set 函数）才能触发重新渲染。直接 count = 5 不会 ——因为那是普通变量，React 根本不知道它变了。

hooks 的三条铁律
  • 只能在组件（或自定义 hook）的最顶层调用。不能放在 if、for、回调里。React 靠"调用顺序"来把每一个 useState 对应到一份状态上，顺序一变就全乱了。
  • 状态更新是异步的，而且会合并。连写两次 setCount(count + 1)，count 是同一个旧值，最后只加 1。 要基于前一个值更新，用函数式写法：setCount(c => c + 1)。
  • 不要直接改状态对象。state.response = "x" 之后 React 不会重新渲染。 要造一个新对象：setState({...state, response: "x"}) （课程讲义里的例子用的正是这个展开语法）。

7.5 重新渲染与 diff

这是 React 最容易被误解的一点。状态变了之后，React 并不是把整棵 DOM 树重建一遍。 它做的是：拿新的描述和旧的描述比一比，只把不一样的地方改动真实 DOM。 下面这个演示让你看到这个比对过程到底产生了多少次改动。

补充 key 是干什么的

演示里用的是"按下标比较"。这在一维的、不重排的列表里没问题。但如果列表会重排、 或者中间会插入/删除，按下标比较就会张冠李戴——React 会把第 1 个位置的新内容 当成"第 1 个元素变了"，而不是"元素移动了"。

给列表项一个稳定且唯一的 keyJSX
{items.map(it => (
    <li key={it.id}>{it.text}</li>    // 不是 key={index}！
))}

key 让 React 知道"这一项还是原来那一项，只是位置变了"。 用数组下标当 key 等于没写 key——这是 React 里最著名的反模式。

7.7 状态、URL 与浏览器的历史

单页应用有一个容易被忽略的问题：页面的状态藏在 JS 变量里，而浏览器的地址栏一无所知。 于是用户按"后退"会直接跳出你的应用，刷新页面会回到初始状态，分享链接也带不上状态。

用 History API 把状态写回地址栏JavaScript
// 切换区块时：把状态和 URL 一起写进历史记录
function showSection(section) {
    history.pushState({section: section}, "", `section${section}`);
    renderSection(section);
}

// 用户按后退/前进时：浏览器会触发 popstate，把当时的状态还给你
window.onpopstate = function (event) {
    if (event.state) {
        renderSection(event.state.section);
    }
};

pushState 的三个参数是：(要存进历史记录的状态对象, 标题, 新的 URL)。 中间那个标题参数被绝大多数浏览器忽略，随便传个空字符串就行。 真正的关键是：页面内容变了，地址栏也要跟着变。 这条原则在 P3 Mail 里体现为"三种邮箱应该有各自的 URL"，在 P4 Network 里体现为"翻页页码应该进 URL"。

用 pushState 改 URL 不会触发页面加载

这是它的设计意图，但也意味着：如果你只在 pushState 里改了 URL 而忘了 renderSection，页面会静止不动——而用户看到地址栏变了， 以为自己在另一个页面。反过来，如果你的渲染只发生在 onpopstate 里， 那么用户主动点击时也不会更新。两个地方都要处理。

7.8 无障碍：不是可选项 补充

课程讲义没有专门讲这一节，但它和你已经学的 HTML 语义化是同一件事的另一面。 对动态界面来说，有几条几乎零成本却能显著改善体验的规则：

  • 用 <button> 而不是 <div onclick>。 前者自动可聚焦、可用 Enter/空格 触发、会被屏幕阅读器念成"按钮"。
  • 异步加载时用 aria-live 播报。 内容区域加上 aria-live="polite"，屏幕阅读器会在内容变化时读出来—— 否则动态插入的列表对盲人用户是"静默发生"的。
  • 加载状态不要只靠颜色。红色文字/绿色文字对色盲用户不可辨， 加个图标或者文字提示。
  • 表单控件要有关联的 <label for>。 这同时也是"点标签能聚焦到输入框"这个便利性的来源。

8测试与 CI/CD

先记住这一句

测试不是"证明程序是对的"，而是用一份可重复执行的代价，换回"改代码时不用怕"的权利。 一个没有测试的项目，改动的风险随代码量指数上升；有测试的项目， 改完跑一遍就知道有没有踩到别的东西。 自动化的价值不在"发现 bug"，而在"让你敢于重构"。

8.1 测试到底在买什么

课程讲义里有一句话点出了要害：手动测试的成本会随项目规模线性增长， 而自动化测试的成本几乎是常数。每次改完代码都手动点一遍所有功能， 在第一个项目里还能忍，到第五个项目时你会开始"这次应该没问题吧"—— 然后问题就来了。

手动测试自动化测试
第一次写要多久几分钟几十分钟
每次改完要多久几分钟 × 改了多少次几秒钟
会漏吗会（人会累、会走神）不会（同一份断言永远执行）
能拦住"改 A 弄坏 B"吗只能靠你记得去点 B能——只要 B 有测试
能拦住的 bug 类型一切只包括你想到并写下来的那些
测试唯一真正的价值

最后一行的对比很关键：测试不能发现你没想到的问题。 所以"多写测试就不会有 bug"是错的。但测试买到了另一样东西： 你敢改了。一个 M2M 关系要重构、一个函数要从视图里抽出来、 要把 forms.Form 换成 ModelForm—— 如果没有测试，每一次这样的改动都是一次赌博。

8.2 测试金字塔

单元测试 最多 最快

测一个函数、一个方法。不碰数据库、不碰网络、不发请求。 一秒钟能跑几百个。它们定位问题最精确——失败时你几乎立刻知道是哪一行错了。

集成测试 中间

测"几个部件合起来对不对"：一个视图能不能正确返回 200、数据是不是真的写进了数据库、 模板有没有渲染出正确的上下文。Django 的 TestCase + Client 就是为这一层准备的。

端到端测试 最少 最慢

启动真实浏览器，模拟真实点击。它测的是"用户能不能用"， 所以只有它能发现"JS 报错导致按钮点了没反应"这类问题。 代价是慢且脆——界面挪一个像素它都可能失败。

为什么是"金字塔"而不是"倒金字塔"？因为越往下越稳定、越快、越容易定位问题。 如果你靠一堆端到端测试来保证质量，那么每次失败你都要花很久才能查明到底是哪一层坏了。

8.3 Python 的 unittest 与 Django 的测试工具

纯 Python 的单元测试tests.py
import unittest
from functions import square

class SquareTestCase(unittest.TestCase):
    def test_positive(self):
        """正数的平方是正数"""
        for i in range(10):
            self.assertEqual(square(i), i * i)

    def test_negative(self):
        for i in range(-10, 0):
            self.assertEqual(square(i), i * i)

if __name__ == "__main__":
    unittest.main()

三个必须遵守的规则：测试类继承 unittest.TestCase、 方法名必须以 test_ 开头（否则根本不会被执行）、 第一个参数是 self。 方法上那一行 """…""" 不是装饰，它会在失败时作为说明打印出来—— 这是写"为什么测这个"最省地方的方式。

断言含义
assertEqual(a, b)a == b
assertTrue / assertFalse(x)真假判断
assertGreater(a, b) / assertLess大小比较
assertIn(x, container)x 在容器里
assertRaises(ValueError)配合 with 使用，断言某段代码会抛这个异常

        Flight.objects.create(origin=a1, destination=a2, duration=100)

    def test_departures_count(self):
        a = Airport.objects.get(code="AAA")
        self.assertEqual(a.departures.count(), 1)

    def test_index_status(self):
        c = Client()
        response = c.get("/flights/")
        self.assertEqual(response.status_code, 200)
        self.assertEqual(len(response.context["flights"]), 1)

    def test_invalid_id_returns_404(self):
        c = Client()
        response = c.get(f"/flights/{Max('id', 'flights') + 1}")
        self.assertEqual(response.status_code, 404)
三个关键点，每一个都很容易踩空
  • setUp 每个测试方法前都会跑一次，而且测试结束时数据库会被回滚。 所以测试之间互不影响，你不必担心"上一个测试留下的数据"。
  • 跑测试时 Django 会新建一个独立的测试数据库（你会看到 Creating test database for alias 'default'...）， 跑完就删掉。它绝对不会碰你的开发数据。
  • Client() 模拟的是一个浏览器，它不需要真的启动服务器。 c.get("/flights/") 走的是完整的 Django 请求流程—— 路由、中间件、视图、模板，全都真的跑一遍。这就是"集成测试"。
最常见的"测试通过了但功能是坏的"

self.assertEqual(response.status_code, 200) 只说明"页面没崩"。 一个把所有航班都漏掉的页面同样返回 200。断言要落到"内容"上： 上下文里有几条数据、渲染出的 HTML 里有没有那个关键词。 测试写得越像"用户会看到什么"，它越有用。

8.4 Selenium：驱动一个真正的浏览器

用代码点按钮tests.py
import unittest, os, pathlib
from selenium import webdriver

class Tests(unittest.TestCase):
    def setUp(self):
        self.driver = webdriver.Chrome()
        uri = pathlib.Path(os.path.abspath("index.html")).as_uri()
        self.driver.get(uri)

    def test_title(self):
        self.assertEqual(self.driver.title, "My Page")

    def test_increment(self):
        btn = self.driver.find_element_by_id("increase")
        btn.click()
        h1 = self.driver.find_element_by_tag_name("h1")
        self.assertEqual(h1.text, "Count: 1")

    def tearDown(self):
        self.driver.quit()     # 不写这行，每跑一次测试就多留一个浏览器进程

setUp 里启动浏览器、tearDown 里关掉它——这是 Selenium 的标准骨架。 忘了 tearDown 的话，跑几次测试你机器上就会挂满看不见的浏览器进程。

Selenium 的测试天生是"慢且脆"的

它慢是因为真的在启动浏览器、加载页面、等待渲染；它脆是因为任何一个 元素 id 改了、按钮位置变了、图片加载慢了一秒，测试就会失败。 所以端到端测试应该少而精：只覆盖最核心的用户路径 （登录 → 发帖 → 看到帖子），而不是每个按钮都跑一遍。

8.5 CI/CD：让"跑测试"变成自动的

测试写了但没人跑，等于没写。CI（持续集成）解决的就是这个问题： 每次推送代码，服务器自动跑一遍测试，失败就明确告诉你。

git push→ GitHub 收到通知→ 起一台干净的机器→ 装依赖 / 跑测试→ 通过 ✓ 或 失败 ✗

"起一台干净的机器"是关键：它上面没有你本地的任何一个包、任何一个环境变量、 任何一个"我上次手动改过的东西"。所以 CI 通过意味着"别人 clone 下来也能跑"。

.github/workflows/ci.ymlGitHub Actions
name: Testing

on: push

jobs:
  test_project:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Run Django unit tests
        run: |
          pip3 install --user django
          python3 manage.py test

逐行读一遍：on: push 表示每次推送都触发； runs-on: ubuntu-latest 指定用一台全新 Ubuntu； uses: actions/checkout@v2 是官方提供的"把仓库代码拉到这台机器上"的动作； run: | 后面是真正执行的命令。 uses 和 run 的区别是"用一个现成的动作"还是"执行一段命令"。

CI 最常暴露的三类问题
  • 依赖没写进 requirements.txt。你本地装过，所以能跑； 干净的机器上没有，于是 ModuleNotFoundError。
  • 写死了本地路径。C:\Users\你\data.csv 在 Ubuntu 上不存在。
  • 测试之间有隐藏的依赖。本地跑的顺序恰好能过，CI 上的顺序不行—— 这说明你的测试没有真正独立，是时候检查 setUp 了。

课程讲义在 CI/CD 一节的末尾介绍了 Docker。它的动机很直接： "在我机器上是好的"这句话之所以成立，是因为你的机器和服务器不一样。 Docker 把应用和它的运行环境（操作系统、Python 版本、依赖）一起打包成一个镜像， 于是"环境"也变成了可以被版本控制、被测试的产物。

Dockerfile怎么造这个镜像

RUN pip install -r requirements.txt

docker-compose.yml怎么把几个容器跑起来

为什么 CI 里常常配合 Docker？因为镜像里已经装好了所有依赖， 所以测试不需要每次重新 pip install，而且测试跑的环境和线上环境完全一致。

补充 课程没讲、但你迟早会需要的两件事
  • 覆盖率（coverage.py）只该当参考，不该当目标。 coverage run manage.py test 能告诉你"哪些代码从没被执行过"—— 这是找遗漏的好工具。但把"覆盖率必须 90%"当 KPI 会立刻催生一堆 assertTrue(True) 式的废话测试。用覆盖率找盲区，不要用它打分。
  • 测试要跑得快，否则没人跑。如果完整测试要 5 分钟，你就会开始 "这次跳过吧"。所以单元测试要尽量不碰数据库和网络—— 这也是测试金字塔底层的实际意义。

到这里，你已经能写出一个"正确、可维护、改不坏"的应用了。但还没考虑过两个问题： 一万个人同时用它会不会垮，以及有人恶意用它会不会被攻破。 这是最后一讲，也是把前面八讲全部串起来的一讲。

9扩展性与安全

先记住这一句

扩展性问的是"它能不能扛住更多人用"，安全问的是"它会不会被人攻破"。 这两个问题看起来无关，但它们的解法背后的思路完全一样： 先找出那个唯一的瓶颈/单点，然后再去消除它。 架构上叫"单点故障"，安全上叫"最短的那块板"——都是同一件事。

9.1 第一个问题：瓶颈在哪

在讨论"怎么扩展"之前，必须先知道现在被卡住的是哪一层。一个请求经过的所有环节—— DNS、网络、反向代理、应用服务器、数据库、磁盘——其中永远只有一个是当前的瓶颈。 优化其他环节是纯粹的浪费。

CPU 饱和

症状：CPU 打满、请求排队、响应时间随并发线性上升。
典型原因：大量 Python 计算、模板渲染太重、加解密。

数据库 I/O 饱和

症状：CPU 不高但响应慢、慢查询日志里一堆全表扫描。
Web 应用最常见的瓶颈就在这里，通常一个索引就能解决。

连接数耗尽

症状：Too many connections、请求卡在等待连接。
原因通常是 N+1 查询，或者连接池设得太小。

内存不足

症状：频繁 GC、被 OOM Killer 杀掉、swap 到磁盘。
原因通常是"一次把整张表读进内存"。

9.2 垂直扩展与水平扩展

垂直扩展 Vertical Scaling

换一台更大的机器。

优点：不需要改任何代码。
缺点：有物理上限，而且价格随配置非线性上涨；换机器时要停机。

而且它没有解决单点故障——这台机器挂了，服务就没了。

水平扩展 Horizontal Scaling

用更多台小机器。

优点：几乎无上限，可以按需增减；一台挂了还有其他台。
缺点：要求应用是"无状态"的——否则用户的请求落到不同机器上会看到不同的世界。

这是现代架构的默认选择。

无状态到底是什么意思

用户登录之后，服务器要把"这是谁"记在某个地方。如果记在这台服务器的内存里， 那么下次请求被负载均衡分到另一台机器时，用户就"掉线"了——这在用户看来就是 "我明明登录了，怎么刷新一下又让我登录？"

三种解法，讲义里都提到了：

  • 粘性会话（sticky sessions）：让负载均衡把同一个用户的请求永远发给同一台机器。 代价是分摊不均，而且那台机器挂了就全丢。
  • 把会话放进数据库：所有机器都能读到。代价是每个请求多一次数据库查询。
  • 把会话放进共享缓存（Redis）：同样是共享的，但比数据库快一个数量级。 这是生产环境的标准做法。

9.3 负载均衡与自动伸缩

负载均衡器挡在所有应用服务器前面，决定"这个请求该发给谁"。讲义里给了三种分配策略：

策略怎么做什么时候合适
随机随便挑一台最省事。服务器多、请求量大的时候效果已经足够好
轮询（Round-Robin）按顺序一台一台发最公平。服务器配置相同时的首选
最少连接发给当前连接数最少的请求耗时差异大时更聪明——因为轮询会把新请求发给正在忙的那台

负载均衡器自己也是一个单点故障：它挂了，整个站点就没了。 所以生产环境会有备用的负载均衡器，以及"服务器还活着吗"的心跳检测—— 检测不到心跳的机器会被自动踢出队列。

自动伸缩（autoscaling）是在这之上的自动化：流量上来了自动加机器，下去了自动减。 这里有个需要理解的权衡：扩得快会导致成本失控，扩得慢会导致用户体验下降—— 所以大多数系统用"基于指标的阈值 + 冷却时间"来控制，而不是无脑跟着流量走。

9.4 缓存：把计算变成查找

缓存的本质是用空间换时间：把算过的东西存起来，下次直接用。 问题从来不是"要不要缓存"，而是"什么时候让它失效"——这是缓存唯一的难点。

层次缓存什么怎么控制失效
浏览器CSS、JS、图片Cache-Control: max-age=86400（存 1 天）
浏览器（协商）内容是否变过ETag：浏览器下次带上它，服务器答 304 Not Modified 就不用重传
CDN静态资源、甚至整个页面靠上面的响应头；发布时改文件名（带哈希）来强制刷新
应用层一次查询的结果、一个复杂页面片段Django 的 per-view / template-fragment / low-level cache API
数据库查询结果、索引页数据库自己管理
Django 里最省事的一种缓存views.py
from django.views.decorators.cache import cache_page

@cache_page(60 * 15)      # 这份响应缓存 15 分钟
def index(request):
    listings = Listing.objects.filter(is_active=True)   # 15 分钟内只查一次
    return render(request, "auctions/index.html", {"listings": listings})
缓存最危险的一类 bug

把带用户身份的内容缓存成了所有人共享的。 如果你给一个"显示当前用户名"的页面加了 @cache_page， 那么第一个访问者的名字会被缓存在那里，之后所有人看到的都是他的名字。 这类 bug 在测试环境永远发现不了（只有一个测试账号），一上线就是重大隐私事故。 凡是"因人而异"的内容，要么不缓存，要么把用户标识写进缓存键。

9.5 数据库的扩展路线

数据层永远是最后被解决、也最难解决的一层——因为应用服务器可以随便加， 但数据只有一份。讲义给了三条路线：

路线做法代价
垂直分区把不同的表放到不同的数据库上（用户库、订单库）跨库 JOIN 没了，要在应用层拼
水平分区把同一张表的不同行放到不同数据库上（国内航班 / 国际航班）按什么分？跨分区查询怎么办？
数据库复制同一份数据存多份，读写分离写还是只有一个点；副本有延迟
单主复制 Single-Primary

只有一台机器能写，其他副本只读。写完之后数据异步同步到副本。

优点：不会有冲突，简单可靠。
缺点：写能力无法扩展；副本有复制延迟—— 用户刚写完刷新页面可能看不到自己的数据（"读己之写"问题）， 这是真实项目里很常见的用户投诉来源。

多主复制 Multi-Primary

多台机器都能写，写能力上去了。

代价是三种冲突，讲义里点名了：

  • 更新冲突：两台机器同时改了同一行，谁的版本算数？
  • 唯一性冲突：两台机器同时注册了同一个用户名。
  • 删除冲突：一台删了、一台改了。

解决这些冲突需要应用层的复杂逻辑——所以除非确实需要，优先选单主。

9.6 安全的第一性原理

攻击者的目标永远是让系统把数据当代码执行，或者把数据当指令执行。 这句话听起来抽象，但下面这四种攻击全都是它的具体形态：

SQL 注入

你本来想传一个"值"，但因为它被拼进了 SQL 语句里，数据库把它当指令解析了。

XSS（跨站脚本）

你本来想存一段"文字"，但因为它被插进了 HTML 文档里，浏览器把它当代码执行了。

CSRF（跨站请求伪造）

你本来想发一个"请求给银行"，浏览器却把它当成了"你本人授权的操作"——因为它自动带上了你的 cookie。

路径穿越

你本来想读"uploads/图片.jpg"，但 ../../etc/passwd 被当成了合法路径。

防御的思路也统一：在所有"数据会变成代码"的边界上，强制数据只能保持为数据—— 用参数化查询、用 HTML 转义、用 token 区分"是不是用户本人发起的"。

9.7 HTTPS 与两种密码学

HTTP 的内容是明文，中间的任何一跳都能看到和修改。HTTPS 在下面加了一层 TLS， 同时保证三件事：机密性（看不到内容）、完整性（改一个字节就会被发现）、 身份真实性（对面真的是它自称的那个域名）。

对称加密（秘密密钥）

加密和解密用同一把钥匙。

快，适合加密大量数据。
但有个死结：双方怎么安全地共享这把钥匙？如果能在安全信道上交换密钥， 那还要加密干什么？

公钥加密（非对称）

一把公钥加密，一把私钥解密（反过来也行——那就是签名）。

公钥可以随便公开。
慢得多（通常是几百倍），所以只用来做两件事： 握手时协商出对称密钥，以及签发证书证明身份。

HTTPS 同时用了两者：用非对称加密安全地协商出一把对称密钥，然后用对称密钥传输数据。

证书：把"公钥"和"域名"绑在一起

光有公钥还不够——你怎么知道这把公钥真的是 bank.com 的，而不是中间人递给你的？ 所以需要证书颁发机构（CA）：它用自己的私钥给你的证书签名， 证明"这把公钥属于 bank.com"。浏览器里预装了一堆 CA 的公钥，于是可以验证这条签名链。 地址栏的小锁，就是"这条链验证通过"的意思。

补充 讲义之外，但你上线前一定要做的三件事
  • 把 cookie 标成 HttpOnly 和 Secure。 HttpOnly 让 JS 读不到它（XSS 偷不走会话）， Secure 让它只在 HTTPS 上发送。没有 HttpOnly 的会话 cookie 是 XSS 攻击最爱的目标。
  • 打开 SECURE_HSTS_SECONDS（HSTS）。 它告诉浏览器"以后访问我这个域名永远只用 HTTPS"， 从而堵住"用户第一次输入 http:// 被劫持"这个窗口。
  • 设置 X-Frame-Options: DENY 或 Content-Security-Policy。 前者禁止别人把你的页面嵌进 iframe（防点击劫持：诱导用户在你不知情的页面上点按钮）， 后者能大幅削弱 XSS 的危害——它规定"这个页面只允许从这些来源加载脚本"。

课程讲义没有展开这几项，但它们是 Django 里几行配置就能打开的，没有理由不做。

9.8 密码不该被"存起来"

讲义里有一句话必须划重点：数据库里存的不是密码，是密码的哈希。 哈希是单向的——从哈希推不出原文。用户登录时，你把输入的密码用同样的方法哈希一遍， 和存的哈希比对。

但"单向"并不等于"安全"，因为攻击者可以反过来算： 把常见密码（字典里那几百万个）全部哈希一遍，做成一张对照表。 这张表叫彩虹表。

为什么"慢"在这里是优点

正常的哈希函数追求"快"（第 3 章讲 dict 时，我们要它快到 O(1)）。 密码哈希反过来：它要慢到让每一次尝试都有成本。 设密钥空间是 \(2^{n}\)，每次尝试耗时 \(t\)， 那么穷举的平均代价是：

\[ T \;=\; \frac{2^{\,n}}{2}\times t \]

密码强度 \(n\) 是指数项，函数速度 \(t\) 只是系数。 所以让 \(t\) 从 1 微秒变成 100 毫秒，攻击成本只涨 10 万倍； 而让密码长度增加 20 位，成本涨 100 万倍。 两者都要做——这也解释了为什么"至少 12 位"比"必须包含符号"更值得强调： 长度直接买指数，符号只是让字典大一点。

为什么"过滤掉 <script>"永远不够

因为能执行 JavaScript 的地方远远不止 <script>： onerror / onload / onmouseover 等事件属性、 javascript: 开头的链接、<svg> 里的动画回调、 <iframe srcdoc>、甚至 CSS 的 expression()（老 IE）。 黑名单式过滤注定会被绕过。

正确的做法是白名单式转义：把所有 < > & " ' 都转成实体，让它们在任何语境下都只能是文字。 这正是 Django 模板默认做的事——所以第 4 章那个 |safe 才需要你格外小心： 去掉自动转义，等于亲手把这一层保护关掉。

场景怎么写才安全
Django 模板里输出变量什么都不用做，默认就转义。除非确有必要，不要加 |safe
必须输出 HTML（比如 Wiki 的 Markdown）先用 markdown2 渲染，再用 bleach 之类的库白名单过滤标签
JS 里插入用户内容textContent，不是 innerHTML
把数据传给 JS（var x = ...）用 {{ value|json_script:"data" }}，不要手拼引号
用户可控的 URL（跳转）校验目标是站内相对路径，否则会变成"开放重定向"钓鱼

9.11 CSRF 与其他攻击面

CSRF 的攻击形态

第 4 章已经讲了这个攻击的原理。这里补充它的两种常见变形：

  • 自动提交的隐藏表单——页面加载就提交，用户完全没感觉。
  • 图片标签伪装——<img src="https://bank.com/transfer?to=evil&amount=10000">。 所以第 1 章强调"GET 不能有副作用"不只是洁癖：如果转账是 GET， 一张图片就能完成攻击，连表单都不需要。

Django 的 {% csrf_token %} + 中间件已经自动处理了标准表单场景。 但你要知道它保护不了什么： @csrf_exempt 装饰过的接口（比如 P3 Mail 的 API）就完全没有这层保护。 课程这么做是为了让你专注在前端逻辑上，而真实项目里给 API 加 CSRF 保护是必须的。

点击劫持 Clickjacking

攻击者把你的页面放进一个透明 iframe，盖在一个诱人的按钮上。 用户以为在点"领取奖品"，实际点的是你页面上的"确认转账"。 防御：X-Frame-Options: DENY，一行配置。

开放重定向

你的登录页写成 /login?next=<用户输入>。 攻击者发一个链接，域名是你的、路径是你的，点完却跳到他的钓鱼站。 防御：只允许相对路径。

密钥泄露

把 SECRET_KEY、数据库密码、API key 提交进了 Git。 即使后来删掉了，Git 历史里还在——必须轮换密钥，而不只是删代码。 防御：环境变量 / .env + .gitignore。

没有限流

登录接口可以被无限次尝试密码（暴力破解），搜索接口可以被无限次调用（拖垮服务器）。 防御：给每个 IP / 账号加速率限制——讲义里点名的 rate limiting，它同时防住了暴力破解和拒绝服务攻击。

越权访问 IDOR

你把 URL 从 /orders/12 改成 /orders/13， 看到了别人的订单——因为视图只检查了"登录了没"，没检查"这是不是你的"。 防御：查询里带上所有权条件，见 4.5 节。 P4 Network 的规格里专门有这么一条要求。

DEBUG 忘了关

生产环境 DEBUG = True 时，任何报错页面都会显示 完整源码、settings 内容、环境变量。这是一份送给攻击者的地图。 上线前检查 DEBUG、ALLOWED_HOSTS、SECRET_KEY。

9.12 上线前的检查清单

安全
  • DEBUG = False，ALLOWED_HOSTS 里是真的域名
  • SECRET_KEY 从环境变量读，且没有进过 Git 历史
  • 所有 cookie 带 HttpOnly / Secure
  • 全站强制 HTTPS，并开启 HSTS
  • 所有写操作都用 POST/PUT/DELETE，且带 CSRF 保护
  • 所有"值得查询的输入"都经过服务端校验（不信任前端校验）
  • 每个涉及他人数据的视图都检查了所有权
  • 登录 / 注册 / 搜索接口有限流
  • 依赖没有已知漏洞（pip-audit）
性能与可靠
  • 所有列表查询都带了 select_related / prefetch_related
  • 高频 WHERE / JOIN 的列都建了索引
  • 没有把大表一次性读进内存
  • 静态文件交给 CDN 或 Nginx，不经过 Django
  • 会话存在共享缓存里，而不是数据库
  • 有数据库备份，并且真的做过一次恢复演练
  • 500 错误会写进日志并通知你，而不是只显示给用户
  • 关键路径有监控（响应时间、错误率、队列长度）
  • 容量有明确上限，并知道瓶颈在哪一层
这份清单的使用方式

不要等到上线那天才逐条检查。上面的每一条都对应前面某一章的某个知识点—— 你在写代码的时候想到了，它就是一行；等到上线前才想起来，它可能是一次重构。 把清单当成"我是不是把前面九讲该做的事都做了"的自我检查表，而不是发布前的过关考试。

10.2 P0 · Search

做什么：复刻 Google 的三个页面——普通搜索、图片搜索、高级搜索——全部用 HTML 和 CSS， 一行后端代码都不写。

规格拆解
  • 至少三个页面：index.html、图片搜索页、高级搜索页
  • 主搜索页右上角有链接到另外两页；那两页也要有链接回来
  • 主搜索框居中、圆角；按钮在下方居中
  • 搜索时跳到 Google 的结果页
  • 高级搜索页有四个输入框（全部词 / 精确短语 / 任意词 / 排除词），竖直排列、左对齐
  • 高级搜索的按钮是蓝底白字
  • "I'm Feeling Lucky" 直接跳到第一条结果（可能经过一次重定向提示，这是正常的）
  • CSS 要贴近 Google 自己的美学
真正在考什么

这个项目看起来最简单，但它教的是整个课程里最基础也最容易被忽视的一课： "URL 就是接口"。

Google 没有给你 API 文档。你要做的是打开 Google 搜索一次， 看地址栏变成了什么，然后照着把表单的 action 和 name 属性配对上去。

这正是第 1 章 1.4 节讲的全部内容：name 决定参数的键， method 决定它放在哪，action 决定发给谁。 "I'm Feeling Lucky" 那一条尤其典型——它没有对应的按钮， 只有 Google URL 里一个隐藏参数（btnI）。你要靠观察发现它。

三个关键参数（自己动手去核实一遍）
  • 普通搜索：https://www.google.com/search?q=你的查询。
  • 图片搜索：换到 /imghp 或 tbm=isch 这类路径/参数—— 自己去点一次图片搜索，看地址栏。
  • 高级搜索：四个输入框各自对应一个参数名（比如精确短语、排除词都有各自的键）。 它们是高级搜索页的 URL 里的查询参数，不是结果页的。

注意 Google 的参数偶尔会变。不要背别人博客里的参数名，自己去地址栏读。 这也是这个项目想训练的习惯。

常见坑
  • 文件放进了子文件夹。GitHub Pages 要求 index.html 在分支根目录， 多套一层的话 Pages 找不到首页。
  • 忘了 <meta name="viewport">。移动端检查会失败。
  • 高级搜索页的输入框没有 name。没有 name 就不会被提交—— 这是第 1 章 1.4 节的第一个知识点。
  • 用 <a> 冒充按钮。见 1.3 节。

10.3 P1 · Wiki

做什么：一个类维基百科。可以查看条目、新建、编辑、搜索、随机跳转。

这个项目最重要的一个设定：没有数据库

Wiki 项目一个模型都不需要写。条目就是 entries/ 目录里的 Markdown 文件，课程已经给你写好了 util.py，里面有恰好三个函数：

  • list_entries() —— 返回所有条目名的列表
  • get_entry(title) —— 返回该条目的 Markdown 内容，不存在则返回 None
  • save_entry(title, content) —— 新建或覆盖一个条目

用它，不要自己重写。这三个函数里已经处理好了路径拼接、 文件名大小写、目录不存在等等细节；自己写一遍只会引入 bug。 而"不用数据库也能做出一个 Web 应用"这件事本身，就是一个重要的认知校正—— 你会在这一讲里第一次真切感受到"Django 只是把 HTTP 请求翻译成函数调用"这句话。

路由要做的事容易漏掉的细节
/wiki/TITLE显示条目条目不存在时要有错误页；页面的 <title> 里要包含条目的名字
首页列出全部条目要求是可点击的链接，不是纯文字列表
搜索查询串精确匹配时直接重定向到该条目；否则列出所有"包含该子串"的条目——搜 ytho 必须能找到 Python
新建页标题 + 内容的表单标题已存在要报错；内容框要用 textarea
编辑页同上textarea 要预填现有内容；保存后重定向回该条目页
随机页随便打开一个条目—
两个几乎所有人都会卡住的地方

① 忘了 |safe。Django 默认转义 HTML，所以 Markdown 渲染出来的 <h1> 会原样显示成文字。这是这个项目里最常见的失败点（第 4 章有详细说明）。

② 编辑页的 textarea 是空的。预填内容要写在 <textarea>...</textarea> 的标签之间， 而不是写在 value 属性里——textarea 没有 value 属性。 这是 HTML 里少有的"内容写在外面会错"的控件。

如果你在 Codespaces 上遇到 403

提交表单时报 403 - CSRF Origin checking error， 需要在 settings.py 里加上 CSRF_TRUSTED_ORIGINS = ["https://你的-codespace-地址-8000.preview.app.github.dev"]。 官方项目页的提示里专门写了这一条。

10.4 P2 · Commerce

做什么：一个拍卖网站。发布商品、出价、评论、心愿单、关闭拍卖。 这是六个项目里最需要"想清楚"的一个——代码不难，难在数据结构设计。

先设计数据，再写代码

规格要求至少三个模型（商品 / 出价 / 评论）。在设计阶段先把下面这些问题回答清楚， 你会省下后面大量的返工：

  • 当前价格怎么来？存在 Listing 上的一个字段， 还是每次都从 Bid 里取最大值？ 前者是冗余，两人同时出价可能不一致；后者永远正确但要查一次。 提示：课程要求的"出价必须严格大于当前最高价"，用一个查询就能同时做到查询和校验。
  • 关闭拍卖时"谁赢了"怎么表达？是给 Listing 加一个 winner 外键，还是靠"最高出价者"推出来？
  • 心愿单是多对多吗？一个用户收藏多个商品，一个商品被多个用户收藏—— 这是典型的 ManyToManyField（第 5 章 5.4 节）。
  • 删掉一个商品时，它的出价和评论怎么办？这就是 on_delete 要回答的问题。
要求关键点
三个模型商品、出价、评论。可以再加一个分类模型
发布商品标题、描述、起拍价必填；图片 URL 和分类可选
首页默认路由就是活跃商品列表；每条要显示标题、描述、当前价、图片（如果有）
商品页登录用户可加/删心愿单、可出价、可评论；发布者可关闭拍卖，最高出价者获胜
出价校验必须 ≥ 起拍价，且严格大于此前任何出价——相等也不行
关闭后商品变为非活跃；获胜者要看到提示
分类页列出全部分类；点进去只显示该分类下仍然活跃的商品
Admin管理员能查看、添加、编辑、删除商品、评论和出价三者全部
最常失分的五点
  • 出价校验漏了"相等"。规格原文是"必须大于任何其他出价"—— 等于当前最高价是不允许的。只判 >= 起拍价 不够。
  • 关闭拍卖没有真的把商品置为非活跃，或者没有记录获胜者。
  • 图片只在存在时显示——没有图片的商品不能显示一个裂开的图。
  • Admin 只注册了商品。规格明确要求评论和出价也能被管理。
  • 分类页显示了已关闭的商品。规格要的是"该分类下活跃的商品"。
想让这个项目拿满分？加上 5.9 节的并发处理

用 @transaction.atomic + select_for_update() 把"读当前价 + 校验 + 写入" 包成一个不可分割的操作。这不在规格要求里，但它是这个项目唯一真正的技术难点， 也是你在真实工作里会反复用到的模式。

10.5 P3 · Mail

做什么：一个单页邮件客户端。收件箱 / 发件箱 / 归档，发信、看信、归档、回复。

这个项目的后端是给你写好的

官方原话是："我们已经替你写好了全部 Python 代码，你只需要写 HTML 和 JavaScript。" 接口也已经定好，你要做的就是正确地调用它们：

方法路径行为
GET/emails/<mailbox>mailbox 是 inbox/sent/archive，返回按时间倒序的邮件数组
GET/emails/<id>单封邮件；不存在或无权访问返回 404
POST/emails发信。recipients 是逗号分隔的字符串。成功返回 201
PUT/emails/<id>更新 archived 或 read 字段

每封邮件的 JSON 字段是：id、sender、recipients（数组）、 subject、body、timestamp、read、archived。

评分只看 inbox.js。官方原话："为了评分，我们只会考虑 inbox.js！" 所以别把逻辑写进模板里。

要求关键点
发信提交后 POST /emails，然后加载"已发送"邮箱
邮箱列表每封邮件独立成一个盒子，显示发件人、主题、时间戳
已读 / 未读未读白底，已读灰底——两种背景色必须能看出来
查看邮件显示发件人、收件人、主题、时间戳、正文；然后 PUT 把它标为已读
归档 / 取消归档收件箱显示"归档"，归档箱显示"取消归档"，已发送箱两个都没有；操作后再加载收件箱
回复跳到写信界面，收件人预填原发件人；主题预填 Re: foo（如果原主题已以 Re: 开头就不重复加）；正文预填一行引用说明
五个最常见的失分点
  • 没做"已读/未读"的背景色区分。这是规格里明确写的一条，也是最多人漏的一条。
  • 打开邮件后忘了 PUT 标记已读。只做了 GET。
  • "已发送"里也显示了归档按钮。规格说归档只适用于收件箱/归档箱。
  • 归档之后没有重新加载收件箱。
  • 忘记 await。结果 emails.length 是 undefined， 列表永远是空的。第 6 章 6.8 节的演示专门演的就是这个。
这个项目真正在教的东西

前后端分离下的状态同步。页面不刷新，但服务器上的数据变了； 你要保证"用户看到的"和"服务器上真实的"始终一致。 这里没有标准的 Django 表单帮你做这件事了——你得自己决定： 是先发请求再更新界面（简单但慢），还是先更新界面再发请求（快但要处理失败回滚）。 前者叫悲观更新，后者叫乐观更新，是第 7 章 7.1 节讲的"不要让用户等"的具体实现。

10.6 P4 · Network

做什么：一个社交网络。发帖、个人主页、关注、点赞、编辑、分页。 这是课程里规模最大的一个项目，也是唯一一个明确要求"服务端授权"的。

要求关键点
发帖登录用户用 textarea 写内容并提交
所有帖子导航栏的 "All Posts" 显示所有用户的帖子，最新的在前；每条要显示发帖人、内容、日期时间、点赞数
个人主页点用户名进入；显示关注者数和正在关注数、该用户的帖子（倒序）；对已登录的其他人显示"关注/取关"按钮
关注导航栏的 "Following" 只显示你关注的人的帖子；只有登录用户能看到
分页每页 10 条；有更多时显示 "Next"；不在第一页时显示 "Previous"
编辑自己的帖子有 "Edit" 按钮，替换成 textarea，保存时不刷新整个页面；
服务端必须阻止任何人编辑别人的帖子
点赞任何帖子都能点赞/取消赞；用 fetch 异步通知服务器；不刷新页面
这个项目最容易被扣分的一条

"不能通过任何途径编辑别人的帖子"必须在服务端实现。 规格里这句话是独立的一条。只在界面上不显示 Edit 按钮不算数—— 任何人手改一下 fetch 的 URL 就能改别人的帖子。

服务端必须这样检查views.py

这就是第 9 章 9.11 节讲的 IDOR（越权访问）。 判断原则：凡是"某个用户只能操作自己的东西"的功能，服务端都要有这一行。

这个项目的三个技术难点
  • 分页。后端用 Django 的 Paginator 类， 前端用 Bootstrap 的分页组件。注意"Previous 只在不在第一页时显示"这条—— 它要求后端把"当前是第几页、还有没有下一页"这些信息也返回给前端。
  • 关注关系。这是一个自指的多对多： User 关注 User。你自己的 User 模型里写一个 ManyToManyField("self", ...)，或者单独建一个 Following 模型。
  • 点赞计数。每个帖子要显示点赞数，也就是"每个帖子的点赞数"这个聚合查询。 如果用循环去数、或者在模板里写 post.likes.count， 那就是第 5 章 5.6 节的 N+1 问题——一页 10 个帖子就是 10 次额外查询。 正确做法是 annotate(Count("likes"))。
其他容易漏的点
  • 不能关注自己。自己的主页上不应该出现关注按钮。
  • "Following" 页面必须要求登录。用 @login_required。
  • 帖子卡片要显示全部四个字段——包括日期时间和点赞数，很多人只做了用户名和内容。
  • 点赞和编辑都不能触发整页刷新。规格里明确要求用 fetch。

  1. 它解决我自己的什么麻烦？给自己做的东西，你才会知道做得对不对。
  2. 它的核心数据结构是什么？如果说不出至少三个模型和它们的关系， 说明这个想法还不够具体，或者太小了。
  3. 哪一部分必须是 JavaScript？如果答案是"没有"，那你选的是一个静态网站， 不满足"用 JavaScript"这条硬要求。

做出来之后，把它真正部署起来、真正用起来。 一个你自己每天在用的工具，比一个功能更多但没人打开的项目有价值得多—— 而且面试时你可以直接说"这个我一直在用"，这是完全不同的分量。

11速查与总结

11.1 常见误解澄清

下面这些说法在初学阶段几乎人人都会认同，但它们要么是错的，要么是"对得让人误入歧途"。 逐条过一遍，看看有没有中招的。

误解 1 · "Django 的 View 就是视图"

错。Django 的 View 承担的是别的框架里 Controller 的角色——它接收请求、调用模型、决定用哪个模板。 而 Django 的 Template 才是别的框架说的 "View"。 名字不重要，那条"视图决定发生什么、模板决定长什么样"的边界才重要。

误解 2 · "用 ORM 就一定安全，不会有 SQL 注入"

基本对，但有两个真实的口子。.extra()、.raw()、 RawSQL() 会把你写的字符串直接交给数据库；而 order_by(用户输入) 这类"把输入当标识符用"的地方， 参数化保护不了（它只能保护值）。 判断标准：这个用户输入是作为"一个值"传进去的，还是被拼进了 SQL 的结构里？

误解 3 · "前端框架让页面变快了"

不一定。React 需要额外做一次 diff 计算，纯渲染速度未必比手写 DOM 操作快。 它真正的价值是把"哪块 DOM 该更新"从你的职责里拿走了—— 在一个有几十个状态的页面上，你不可能手写出比它更可靠的更新逻辑。 你买的是"不会忘更新"和"改坏了看得出来"，不是毫秒数。

误解 4 · "测试覆盖率越高，代码质量越好"

过了一定程度就不成立。覆盖率能告诉你"哪些代码从未被执行过"—— 这是找盲区的好工具。但把它当 KPI 会立刻催生一堆 assertTrue(True) 式的废话测试。 用覆盖率找遗漏，不要用它打分。

误解 5 · "HTTP 是无状态的，所以服务器不记得我"

说反了。HTTP 协议本身没有携带身份的能力，但服务器当然"记得"你—— 它靠的是你在第一次请求之后拿到的那个 cookie。 更准确的说法是："服务器不会主动记住你，是你每次请求都自报家门。" 这个区别很实际：清掉 cookie，你就变成了另一个人。

误解 6 · "GET 和 POST 的区别就是参数放哪儿"

那只是表象。真正的区别是语义：GET 表示"读取"， POST 表示"修改"。由这条语义推出了一整串后果：GET 可缓存、可收藏、可被爬虫预取、 会进浏览器历史，所以 GET 绝对不能有副作用。 如果你把"删除"做成 GET，某天一个爬虫扫过你的站点，数据就没了。

误解 7 · "有了 CSS 框架就不用学 CSS 了"

恰恰相反。框架帮你省掉的是"写按钮样式"这种重复劳动， 但它不能帮你解决"为什么这个间距不对""为什么这个元素压住了那个"—— 那些问题的答案全在盒模型、层叠、特异度里。 框架让你少写 CSS，但不会让你少懂 CSS。

误解 8 · "上线前把 DEBUG 关掉就安全了"

关掉 DEBUG 是最低要求，不是安全措施。 它只是不再把源码和配置展示给攻击者。真正的安全来自： 用户输入永远不信任（服务端校验）、数据永远不当代码（转义与参数化）、 权限永远在服务端检查（不能只藏按钮）。 这三条才是分界线。

误解 9 · "扩展性就是加机器"

加机器只能解决应用层的问题。你的会话存在单台机器的内存里、数据库只有一台、 缓存没做——那么加多少台应用服务器都没用。 扩展性的本质是找出那个唯一的瓶颈并消除它，然后重复这个过程。 而每一轮之后瓶颈都会跑到别的地方去，所以这件事永远没有"做完"的时候。

误解 10 · "学完这门课我就会做网站了"

你会的是"从零做出一个能用的网站"，这是一件很实在的能力。 但还有一整片没被覆盖：部署与运维（容器编排、监控告警）、 更高阶的数据库（分库分表、一致性权衡）、实时通信（WebSocket）、 以及后面那些框架（Django REST Framework、TypeScript、Next.js）。 不过——这门课给你的那张"从上到下贯通的心智地图"是通用的。 后面学任何东西，你都知道它该插在地图的哪个位置。

11.4 回到最开始那句话

本文开篇说：Web 开发里几乎所有的复杂度，都源自"HTTP 是无状态的、一问一答的、纯文本的"。 现在你已经走完了全部九讲，可以回头检验一下这句话了：

你学到的它在补 HTTP 的哪个缺口
HTML / CSS纯文本要能被"解释成结构"和"画成样子"
表单与 URL 参数一问一答里，用户如何把自己的意图塞进那行文本

HTTPS纯文本——所以中间任何一跳都能看和改，必须加密
负载均衡 / 数据库复制一问一答的机器只有一台时会挂，需要很多台
