记忆架构 One-Page Report：Claude Code vs Cline

源码级对照 · 全架构覆盖 + 主要带注释代码 · 2026-09-07

Claude Code（claude-code-src，本地核对）Cline（github.com/cline/cline @ main，2026-09-07 快照） 口径：两家都是"文件记忆"路线，但 Claude Code 把记忆做成框架自动管理的双轨注入系统（入口全量 + 小模型挑选），Cline 把记忆做成用户可编辑的规则文件体系 + 确定性门控（toggle / frontmatter 条件），会话内则都靠"摘要压缩"续命，实现深度不同。

1 · 全架构一图流

Claude Code：双轨注入 + 四级压缩

CLAUDE.md（项目/用户指令记忆）→ MEMORY.md 入口（≤200行/25KB，全量注入）→ memdir 描述清单（只读 frontmatter）→ 小模型挑选 ≤5 条（相关才注入）→ system prompt
microCompact（清旧工具结果）→ autoCompact（摘要替换，20k 预留）→ reactiveCompact（API 超限兜底）→ /compact 手动（四级调度链）

Cline：规则文件体系 + 确定性门控

custom instructions（全局）→ .clinerules/（文件或目录，逐文件 toggle）→ frontmatter 条件规则（paths: glob 门控）→ workflows（按需手动触发）→ system prompt
Auto Compact（SDK 摘要压缩）→ checkpoints（回滚到压缩前）→ FileContextTracker（外部改文件→stale 提醒）→ focus chain（-[ ] 清单跨压缩保主线）

2 · 六维架构对照表

维度Claude CodeCline
跨会话记忆载体markdown 文件：CLAUDE.md（项目/用户指令）+ MEMORY.md 入口 + memdir 记忆目录（一文件一条，frontmatter 存 description）；另有团队级记忆目录markdown 文件：~/.clinerules/（全局）+ 项目 .clinerules/ 目录（rules / workflows / hooks / skills 子目录）；兼容导入 Cursor / Windsurf / Agents 规则（external-rules.ts）+ 远程托管规则
谁写入记忆模型自己用文件工具写 + 用户显式输入通道（MemoryUpdateNotification 弹通知）；无后台自动提取用户/团队手工维护（进 git 版本管理），UI 提供创建/删除/开关；Memory Bank 场景下模型按指令更新 memory-bank/*.md
带什么进上下文双轨：入口文件无条件全量（物理限容 200 行/25KB）+ memdir 按任务小模型挑选 ≤5（只读描述清单，选完才读全文）规则默认全量拼接；门控是确定性的：逐文件 toggle 开关 + YAML frontmatter paths: glob 条件（命中当前工作区路径才激活）；workflows 完全按需（手动触发）
会话内压缩四级：microCompact（白名单清旧工具结果，冷/热缓存两种模式）→ autoCompact（结构化摘要，20k 预留输出，分级 buffer，连续失败 3 次熔断）→ reactiveCompact（prompt-too-long 报错兜底）→ /compact 手动Auto Compact 单级：接近窗口上限时 LLM 摘要替换历史（SDK createContextCompactionPrepareTurn；手动入口 sdk-compaction.ts）；不支持摘要的模型回退规则截断；压缩产物为 sidecar，正式 transcript 不被替换，可经 checkpoint 回滚
防"记忆变垃圾"入口文件双上限截断 + 注入去重（轨道 B 排除轨道 A）+ 挑选提示词"不确定就不选、允许空选"规则生命周期由用户管理（扫描↔toggle 同步、删除即清理）；条件规则天然限域（paths 不命中不注入，paths: [] 显式关闭）
上下文新鲜度memoryAge（按 mtime 衰减记忆新鲜度）；压缩游标 lastSummarizedMessageId 防孤儿 tool_result独有：FileContextTracker 用 chokidar 监听上下文中文件的外部修改（区分 Cline 自改/用户改），标记 stale 并提醒重读；focus chain（- [ ] 清单）帮助跨多次压缩维持任务主线

3 · Claude Code 写侧：事实是如何被记下来的（补全最后一环）

在展开"存了什么 → 怎么挑 → 怎么注入"之前，先回答最根本的问题：这些 .md 文件最初是怎么出现的？答案出人意料地朴素——Claude Code 没有任何后台记忆提取管道，事实全部由模型自己在对话中用普通的 Write/Edit 工具记下来。框架唯一做的事，是把一套"怎么记"的规约注入系统提示词（buildMemoryLines()，memdir.ts:199-266）。读侧（§4-§6）有小模型参与，写侧是纯提示词工程 + 普通工具调用。

3.1 模型每轮都带着的"记事手册"（系统提示词原文节选）

① 记什么 —— 四种类型（memoryTypes.ts · TYPES_SECTION_INDIVIDUAL）：

<type>
    <name>user</name>
    <description>The user's role, goals, preferences, responsibilities...</description>
</type>
<type>
    <name>feedback</name>
    <description>Guidance from the user about how to approach work — what to avoid
    and what to keep doing. Record from failure AND success. Include *why* so you
    can judge edge cases later. Structure content as: rule/fact, then **Why:**
    and **How to apply:** lines.</description>   ← 强制带 Why/How：否则将来无法判断边界
</type>
<type>
    <name>project</name>
    <description>...not derivable from code or git history. Convert relative dates
    to absolute dates (e.g., "Thursday" → "2026-03-05").</description>  ← 防时间腐烂
</type>
<type>
    <name>reference</name>
    <description>Pointers to external systems (Linear, Slack, Grafana...).</description>
</type>

② 不记什么 —— 反向清单（WHAT_NOT_TO_SAVE_SECTION）：
- 代码模式/架构/文件路径 —— "读当前项目就能推导"
- git 历史 —— "git log 是权威"
- 调试方案 —— "修复在代码里，上下文在 commit message 里"
- CLAUDE.md 已有的内容
- 临时任务状态

These exclusions apply even when the user explicitly asks you to save.
↑ eval 验证过的硬门（0/2 → 3/3）：用户说"存下这周 PR 列表"，
  正确行为不是照存，而是反问"哪条让你意外？"——防记忆库退化成流水账

3.2 两步写入流程 + 一个完整例子

规约原文（memdir.ts howToSave）：
**Step 1** — write the memory to its own file using frontmatter format
**Step 2** — add a pointer in MEMORY.md. It is an index, not a memory —
            each entry one line, under ~150 characters. Never write memory
            content directly into MEMORY.md.
四条维护纪律：字段随内容更新 / 按主题组织非按时间 / 错了就删改 /
            写新前先查有没有可更新的旧记忆（防重复）
显式指令：用户说"记住X"→ 立刻存最合适的类型；说"忘掉X"→ 找到并删除

━━━ 实例：用户说"以后回答尽量用中文，我不看英文" ━━━

模型发起两次普通工具调用（没有任何特殊记忆 API）：

Write(~/.claude/memories/feedback_language.md)
---
name: 中文回复偏好
description: 用户要求所有回复使用中文
type: feedback
---
所有回复使用中文。

**Why:** 用户明确表示不看英文。
**How to apply:** 每次生成回复时默认中文，代码和技术术语除外。

Edit(~/.claude/memories/MEMORY.md)
- [中文回复偏好](feedback_language.md) — 所有回复默认中文

下次会话：MEMORY.md 全量注入（轨 A）→ 小模型选中（轨 B）→ 正文注入 → 中文回答。
写侧与 §4-§6 的读侧闭环完成。

3.3 记下来之后怎么信：读侧防呆反过来又成了写侧维护

TRUSTING_RECALL_SECTION（原文）：
"A memory that names a specific function, file, or flag is a claim that it
existed *when the memory was written*."
- 记忆提到文件路径 → 先确认文件还存在
- 记忆提到函数/flag → 先 grep
"The memory says X exists" is not the same as "X exists now."

MEMORY_DRIFT_CAVEAT：
"If a recalled memory conflicts with current information, trust what you
observe now — and update or remove the stale memory rather than acting on it."
↑ 冲突时以当前观察为准，且【顺手删改过期记忆】——读取触发维护
写入方式成本/代价
Claude Code模型按提示词规约自己调 Write/Edit，零后台进程漏记"模型没意识到该记"的事实；收益是零基础设施、全程用户可见、文件可 git 管理
Hermes后台 background_review 管道自动提取 + write approval gate每轮额外推理与审批延迟
Cline Memory Bank同样是模型写 md，但靠用户复制的 prompt 方法论驱动零代码，但无 frontmatter/类型/去重等结构化规约
至此完整闭环：写侧（§3 规约驱动模型自记）→ 存储（§4 索引+文件两层）→ 检索（§5 小模型挑选）→ 注入（§6 双轨+去重）→ 读侧冲突又回流写侧维护。Claude Code 的取舍：不追求自动提取所有事实，只靠一套 eval 反复调优的规约让模型在正常对话中"顺手"记录。

4 · Claude Code 存储：记忆库在磁盘上长什么样

全部记忆就是工作目录下的一堆 markdown 文件——没有数据库。沿用全文的例子，假设用户长期做接口性能分析，记忆库是这样：

memory/
├── MEMORY.md            ← 入口文件（轨道 A：每次请求全量注入）
├── perf-baseline.md     ← 详细记忆，一条一个文件（轨道 B：按需挑选）
├── report-style.md      ← 同上
└── coffee.md            ← 同上（与本任务无关的"噪音记忆"）

MEMORY.md（入口，只放浓缩事实）

# 自动记忆入口
- 用户在做订单服务的接口性能优化
- 报告必须用 markdown 表格、注明单位 ms
- 订单接口 P99 基线 320 ms

perf-baseline.md（详细记忆，frontmatter 带 description）

---
description: 性能基线参数：订单接口 P99 阈值 320 ms，采样窗口 10 s
---
2026-06 压测标定记录：jmeter 500 并发、采样窗口 10 s，
P99 基线 320 ms；强依赖 order-service→inventory 链路，
压测前需预热缓存 3 分钟……（几百行细节）

description 与正文的分工是整个设计的支点：description 一句话、给检索看；正文几百行、给命中后的任务看。coffee.md 也有自己的 description（"团队咖啡偏好记录"），它在库里合法存在，只是很少被选中。

入口为什么敢全量注入：物理限容

export const MAX_ENTRYPOINT_LINES = 200
// ~125 chars/line at 200 lines. At p97 today; catches long-line
// indexes that slip past the line cap (p100 observed: 197KB
// under 200 lines).
// ↑ 真实事故：200 行内写了 197KB——单限行数挡不住
export const MAX_ENTRYPOINT_BYTES = 25_000

超限走两级截断（memdir.ts · truncateEntrypointContent）：先按行切；仍超 25KB 再按字节切，且回退到最近的换行符——绝不把一条记忆从中间劈开（半条记忆比没有更糟，模型会把半句当完整事实用）。截断也不静默，末尾追加：

> WARNING: MEMORY.md is 244KB (limit: 24KB) — index entries
are too long. Only part of it was loaded. Keep index entries
to one line under ~200 chars; move detail into topic files.

连模型都被明确告知"超限了，细节请移到主题文件"——降级必须让消费方知情。

5 · Claude Code 检索：一次挑选的完整过程（逐个提示词）

用户第 10 轮提问："帮我分析这次压测的接口延迟，出报告"。挑选分三步：

第一步：扫描清单——只读文件头，不读正文（memoryScan.ts）

const FRONTMATTER_MAX_LINES = 30   // 每个文件只读前 30 行
const MAX_MEMORY_FILES = 200       // 清单硬上限

// 产出"目录卡"（formatMemoryManifest），按修改时间新→旧：
- perf-baseline.md (2026-08-30T02:11:04Z): 性能基线参数：订单接口 P99 阈值 320 ms，采样窗口 10 s
- report-style.md (2026-08-12T09:40:11Z): 用户偏好：报告用 markdown 表格，注明单位
- coffee.md (2026-06-01T08:00:00Z): 团队咖啡偏好记录

清单体积 O(条数)，与每条记忆多长无关——500 个记忆文件也就几 KB。这是后面"用小模型挑选"在成本上可行的前提。入口 MEMORY.md 不进清单（它已经在轨道 A 了）。

第二步：把清单 + 任务发给小模型（Sonnet），系统提示词全文如下

system（SELECT_MEMORIES_SYSTEM_PROMPT，原文，注释为讲解）:

You are selecting memories that will be useful to Claude Code as it
processes a user's query. You will be given the user's query and a list
of available memory files with their filenames and descriptions.

Return a list of filenames for the memories that will clearly be useful
(up to 5). Only include memories that you are certain will be helpful
based on their name and description.
- If you are unsure if a memory will be useful in processing the user's
  query, then do not include it in your list. Be selective and discerning.
  // ↑ 宁缺毋滥：这是"挑选"与"检索排序"的本质区别
- If there are no memories in the list that would clearly be useful,
  feel free to return an empty list.
  // ↑ 允许空选：无关任务一条不带（噪音记忆比没有记忆更伤）
- If a list of recently-used tools is provided, do not select memories
  that are usage reference or API documentation for those tools ...
  DO still select memories containing warnings, gotchas, or known issues
  about those tools — active use is exactly when those matter.
  // ↑ 精妙细节：正在用的工具不带用法文档，但"坑"恰恰此刻最该带

user（实拼出来的消息）:

Query: 帮我分析这次压测的接口延迟，出报告

Available memories:
- perf-baseline.md (2026-08-30T02:11:04Z): 性能基线参数：订单接口
  P99 阈值 320 ms，采样窗口 10 s
- report-style.md (2026-08-12T09:40:11Z): 用户偏好：报告用 markdown
  表格，注明单位
- coffee.md (2026-06-01T08:00:00Z): 团队咖啡偏好记录

第三步：结构化输出 + 白名单过滤 + 失败降级

const result = await sideQuery({
  model: getDefaultSonnetModel(),          // 便宜的小模型干挑选
  max_tokens: 256,                          // 挑选不需要长输出
  optional: true,                           // 挑选失败可降级，不阻塞主请求
  output_format: {
    type: 'json_schema',
    schema: { properties: { selected_memories: { type: 'array',
                items: { type: 'string' } } }, ... },
  },
  ...
})
// 小模型实际返回：
//   {"selected_memories": ["perf-baseline.md", "report-style.md"]}
// 白名单过滤：幻觉出的文件名直接丢弃；解析/调用失败一律返回 []
return parsed.selected_memories.filter(f => validFilenames.has(f))
成本账：这次挑选总共消耗约 300 token（清单+任务+256 上限的输出），换来的是不注入几百行的正文和无关的 coffee.md。清单模式把挑选成本与记忆库规模解耦，库涨到几百条，挑选成本几乎不变。

7 · 四级压缩·实例解剖（Claude Code 生存侧）

级别触发时机动作信息损失
① microCompact工具结果"老化"后旧工具输出 → 一行占位符几乎为零（环境快照可复原）
② autoCompact逼近有效窗口旧消息 → 结构化摘要有损，主力
③ reactiveCompactAPI 报 "prompt too long"紧急压缩后重试同②，兜底
④ /compact 手动用户敲命令同②，用户控制时机用户自担

① microCompact 前后（真实可复现）

--- 压缩前 ---
[user] 分析这个接口的日志
[tool] ……（第1轮读的 30000 字符日志原文）……
[tool] ……（第2轮 grep 结果 8000 字符）……
[tool] ……（刚产生的压测数据）……

--- microcompact 后 ---
[user] 分析这个接口的日志
[tool] [Old tool result content cleared]   ← 最旧的被清
[tool] ……（第2轮 grep 结果）……            ← 保留最近 N 条
[tool] ……（刚产生的压测数据）……            ← 刚产生的不清

白名单只有"输出是环境快照"的工具（Read/Shell/Grep/Glob/WebSearch/WebFetch/Edit/Write）；模型推理和用户指令永不清。清了刚产生的结果会导致模型重复调用工具——所以保留最近 N 条。

① 的经济学：冷热缓存分治

export async function microcompactMessages(messages, ...) {
  // 缓存已冷（距上次回复超阈值分钟）→ 前缀反正
  // 要整体重算，此时清旧结果"免费"：先清再发请求
  const timeBasedResult = maybeTimeBasedMicrocompact(messages, querySource)
  if (timeBasedResult) return timeBasedResult
  // 缓存还热 → 走 cached 路径，原地编辑旧结果
  // 且尽量不破坏 KV 缓存前缀的连续性（清错反而更贵）
  if (feature('CACHED_MICROCOMPACT'))
    return await cachedMicrocompactPath(messages, querySource)
}

API 的 prompt 缓存（前缀不变≈1/10 价）决定了"清不清、怎么清"要看缓存状态——这是大多数自研压缩会漏掉的账。

② autoCompact 的摘要产物

[CONTEXT SUMMARY] 用户要求分析订单接口延迟分布；
已定位 5 个慢查询模式；P99 基线 320 ms；
输出要求：markdown 表格 + ms 单位。
下一步：拟合慢请求分布并出报告。
……（其后接未压缩的最近若干轮原文）

触发线 = (窗口 − 20k 输出预留) − 分级缓冲（13k/30k/50k 按窗口大小），预留值来自摘要输出的 p99.99 实测（17,387 token）；连续失败 3 次熔断。压缩后由 SessionMemory 游标记录"摘要覆盖到哪条消息"，下次增量压缩。

③ 兜底与 ④ 手动的协作

// ③ 只认 "prompt too long" 这一种错误；只试一次防死循环
if (hasAttempted || aborted) return null
try { return await compactConversation(..., true, ...) }
catch { return null }          // 再失败交给上层提示用户

// ④ /compact 调度链：
//   无自定义指令→先试 session-memory 压缩（便宜）→成功即返回

4.1 条件规则：frontmatter paths: 的确定性门控 apps/vscode/src/core/context/instructions/user-instructions/rule-conditionals.ts:39-103

// 规则文件头可写：
// ---
// paths:
//   - "src/api/**"
// ---
// paths 指令（glob 匹配当前工作区路径，命中才激活这条规则）
const evaluatePathsConditional = (frontmatterValue, context) => {
  if (!isNonEmptyStringArray(frontmatterValue)) return { passed: true }
  // 类型不对 → fail-open（忽略条件，规则照常生效）
  const patterns = frontmatterValue.map(p => p.trim()).filter(Boolean)
  if (patterns.length === 0) return { passed: false }
  // ↑ 空数组 → fail-closed：这是用户"显式禁用规则"的合法写法
  const candidatePaths = (context.paths || []).map(toPosix).filter(Boolean)
  if (candidatePaths.length === 0) return { passed: false }
  // ↑ 没有路径证据 → 路径限域规则一律不激活（保守）
  const matchedPatterns = []
  for (const pattern of patterns) {
    const matcher = picomatch(pattern, { dot: true })
    if (candidatePaths.some(c => matcher(c))) matchedPatterns.push(pattern)
  }
  return { passed: matchedPatterns.length > 0, matched: matchedPatterns }
}

// 首轮激活辅助：从用户消息里启发式抽"像路径的 token"当证据
// （先剔除代码块和 URL 防误报）—— extractPathLikeStrings(text)

9 · Memory Bank 专题：从原生功能退回"方法论"

现状核对（2026-09-07，main 分支）：Memory Bank 在 v3.13（2025-08）曾是原生功能；当前源码中已无专门实现（全仓库检索仅剩 docs/best-practices/memory-bank.mdx）。它现在的形态是一套文档方法论 + 可复制指令：把 Memory Bank 指令放进 .clinerules/memory-bank.md，让模型按指令维护 6 个 markdown 文件（projectbrief / productContext / activeContext / systemPatterns / techContext / progress），配合"initialize / update memory bank"口令。官方推荐的分工：Auto Compact 管例行的上下文续命，Memory Bank 管里程碑级的项目记忆沉淀。

这个演化的含义

  • 会话内记忆（压缩）必须框架做——模型自己无法在窗口耗尽时自救；
  • 跨会话记忆（文档）可以纯 prompt 做——只要文件结构约定清楚，模型读写文件即可；
  • 于是 Cline 把前者做进代码（Auto Compact），后者留给方法论（.clinerules + Memory Bank），这与 Claude Code 的取舍相反：CC 把跨会话记忆也做成了框架能力（memdir 挑选注入）。

两家跨会话记忆的真实差距

Claude CodeCline
自动携带每次请求自动注入（双轨）规则自动拼；Memory Bank 需口令触发读取
按需挑选小模型从描述清单挑选 ≤5paths 条件规则（声明式）
容量治理200 行/25KB 硬上限 + 截断无限（用户自律 + git 审查）

10 · 结论：一句话记住两家

Claude Code：记忆是框架的自动系统——限容的入口文件永远在场，详细记忆由小模型按任务挑选，四级压缩兜底，用户几乎不用管。
Cline：记忆是用户的作品——.clinerules 规则库进 git、逐文件开关、glob 条件限域；框架只负责两件硬事：把规则确定性拼进 prompt，以及在窗口耗尽时用摘要（或截断）续命，再用 checkpoint 和文件监听兜住"记错"与"过期"。
共同点：两边都不用数据库/向量库——markdown 文件 + git 就是两家共同的记忆底座；差异在"谁来决定带什么"（模型判断 vs 声明式规则）与"跨会话记忆是否框架化"（是 vs 方法论）。
