2 · 记忆的四层载体：先分清再深入

层载体谁写入怎么进上下文生命周期
① 指令记忆
CLAUDE.md 体系		CLAUDE.md / CLAUDE.local.md / .claude/rules/*.md用户/团队手写（或经 /remember 从 auto-memory 晋升）每次请求全量拼进 system prompt（按优先级逆序，越近优先级越高）永久，进 git
② 跨会话记忆
auto-memory (memdir)		memory/ 目录：MEMORY.md 索引 + 一题一文件模型自己：对话内自记 + 轮末提取子代理 + autoDream 蒸馏双轨：MEMORY.md 无条件全量（≤200行/25KB）+ 小模型按任务挑选 ≤5 条正文跨会话，用户可见可删可 git
③ 会话笔记
SessionMemory		{projectDir}/{sessionId}/session-memory/summary.md后台 fork 子代理周期性 Edit/compact 的首选便宜摘要源；产物以 current_session_memory 附件类型存在单会话（会话即生命周期）
④ 变体目录
团队 / 子代理		team 记忆目录（TEAMMEM）/ agent 专属 memory 目录同 ②，目录不同同 ②，@提及某 agent 时只搜它的目录同 ②
为什么分四层：指令（该怎么做事）、事实（世界是什么样）、进度（这次干到哪了）三类信息的读者和时效完全不同——指令要每次都在场，事实要按需挑选，进度只服务当前会话。Claude Code 用四个独立机制分别承载，而不是一个大而全的记忆库。

3 · 层①：CLAUDE.md 体系——不止一个文件

多数人以为 CLAUDE.md 是"一个文件"，源码里它是一棵带优先级的树，外加 @include 引用与 paths 条件规则：

// src/utils/claudemd.ts:1 —— 层级与加载顺序（docstring 原文）
// Files are loaded in the following order:
// 1. Managed memory (eg. /etc/claude-code/CLAUDE.md) - Global instructions for all users
// 2. User memory (~/.claude/CLAUDE.md) - Private global instructions for all projects
// 3. Project memory (CLAUDE.md, .claude/CLAUDE.md, and .claude/rules/*.md in project roots)
// 4. Local memory (CLAUDE.local.md in project roots) - Private project-specific instructions
//
// Files are loaded in reverse order of priority, i.e. the latest files are
// highest priority with the model paying more attention to them.
// ↑ 逆序加载 = 后加载的排后面 = 离当前目录越近优先级越高
//
// Memory @include directive:
// - Syntax: @path, @./relative/path, @~/home/path, or @/absolute/path
// - Works in leaf text nodes only (not inside code blocks or code strings)
// - Included files are added as separate entries before the including file
// - Circular references are prevented by tracking processed files
// - Non-existent files are silently ignored
// ↑ CLAUDE.md 可以拆模块：@./api-style.md 把规范分文件组织，引用环自动防

// src/utils/claudemd.ts:249 —— .claude/rules/*.md 支持条件生效（paths globs）
// @param returns Object with content and globs (undefined if no paths or match-all pattern)
const { frontmatter, content } = parseFrontmatter(rawContent)
if (!frontmatter.paths) return { content, paths: undefined }  // 无 paths = 恒生效
const patterns = splitPathInFrontmatter(frontmatter.paths)    // picomatch glob
// If all patterns are ** (match-all), treat as no globs (undefined)
// ↑ .claude/rules/api-style.md 头部写 paths: ["src/api/**"] → 只在动 API 时生效
容易被忽略的一点：CC 在 CLAUDE.md 层已经有"声明式路径门控"（.claude/rules 的 paths frontmatter，picomatch 匹配当前工作路径）。也就是说"该不该带这条指令"在 CC 里有两套机制并存——规则文件用 glob 确定性判断，跨会话记忆用小模型语义判断；载体越接近"人工策展的指令"越确定，越接近"模型沉淀的事实"越语义化。

4 · 层②写侧·通道一：对话内自记——模型每轮都带着的"记事手册"

事实记下来的第一通道：框架把一套"怎么记"的规约注入系统提示词（buildMemoryLines()，memdir.ts:199-266），模型在正常对话中用普通 Write/Edit 工具顺手记。没有任何特殊记忆 API。

4.1 记什么 / 不记什么（规约原文节选）

① 四种类型（memoryTypes.ts · TYPES_SECTION_INDIVIDUAL）：
<type><name>user</name><description>The user's role, goals, preferences, responsibilities...</description></type>
<type><name>feedback</name><description>Guidance from the user about how to approach work — what to
  avoid and what to keep doing. Record from failure AND success. Include *why* so you can
  judge edge cases later. Structure content as: rule/fact, then **Why:** and **How to apply:** lines.
</description></type>                          ← 强制 Why/How：否则将来无法判断边界
<type><name>project</name><description>...not derivable from code or git history. Convert relative
  dates to absolute dates (e.g., "Thursday" → "2026-03-05").</description></type>  ← 防时间腐烂
<type><name>reference</name><description>Pointers to external systems (Linear, Slack, Grafana...).</description></type>

② 反向清单（WHAT_NOT_TO_SAVE_SECTION）：
- 代码模式/架构/文件路径 —— "读当前项目就能推导"
- git 历史 —— "git log 是权威"          - 调试方案 —— "修复在代码里"
- CLAUDE.md 已有的内容                   - 临时任务状态

These exclusions apply even when the user explicitly asks you to save.
↑ eval 验证过的硬门（0/2 → 3/3）：用户说"存下这周 PR 列表"，
  正确行为是反问"哪条让你意外？"——防记忆库退化成流水账

4.2 规约的真实源码：buildMemoryLines

// src/memdir/memdir.ts:199-266 —— 写侧规约的唯一来源（节选，注释为讲解）
export function buildMemoryLines(displayName, memoryDir, extraGuidelines?, skipIndex = false): string[] {
  const howToSave = [
    '## How to save memories', '',
    'Saving a memory is a two-step process:', '',
    '**Step 1** — write the memory to its own file (e.g., `user_role.md`) using this frontmatter format:',
    ...MEMORY_FRONTMATTER_EXAMPLE,
    `**Step 2** — add a pointer to that file in \`MEMORY.md\`. It is an index, not a memory —
     each entry one line, under ~150 characters: \`- [Title](file.md) — one-line hook\`.
     Never write memory content directly into \`MEMORY.md\`.`, '',
    `- \`MEMORY.md\` is always loaded into your conversation context — lines after
     ${MAX_ENTRYPOINT_LINES} will be truncated, so keep the index concise`,
    // ↑ 物理上限直接告诉模型：200 行截断不是秘密，是模型也知道的预算
    '- Keep the name, description, and type fields up-to-date with the content',
    '- Organize memory semantically by topic, not chronologically',
    '- Update or remove memories that turn out to be wrong or outdated',
    '- Do not write duplicate memories. First check if there is an existing memory you can update.',
  ]
  const lines: string[] = [
    `# ${displayName}`, '',
    `You have a persistent, file-based memory system at \`${memoryDir}\`. ${DIR_EXISTS_GUIDANCE}`,
    // DIR_EXISTS_GUIDANCE（原注释）：Claude was burning turns on `ls`/`mkdir -p` before
    // writing → 目录由 ensureMemoryDirExists() 预建，提示词明说 "do not run mkdir
    // or check for its existence"
    'If the user explicitly asks you to remember something, save it immediately as whichever
     type fits best. If they ask you to forget something, find and remove the relevant entry.', '',
    ...TYPES_SECTION_INDIVIDUAL,     ...WHAT_NOT_TO_SAVE_SECTION, '',
    ...howToSave, '',                ...WHEN_TO_ACCESS_SECTION, '',
    ...TRUSTING_RECALL_SECTION, '',
    '## Memory and other forms of persistence',   // 与 plan/tasks 划界：只在本会话
    ...,                                          // 有用的进 plan/tasks，不配进 memory
  ]
  lines.push(...buildSearchingPastContextSection(memoryDir))   // 见 §10.3
  return lines
}

4.4 一个完整例子

用户说："以后回答尽量用中文，我不看英文。"
模型（按"explicitly asks → save immediately"）发起两次普通工具调用：

Write(~/.claude/projects/<slug>/memory/feedback_language.md)
---
name: 中文回复偏好
description: 用户要求所有回复使用中文
type: feedback
---
所有回复使用中文。

**Why:** 用户明确表示不看英文。
**How to apply:** 每次生成回复时默认中文，代码和技术术语除外。

Edit(.../memory/MEMORY.md)
- [中文回复偏好](feedback_language.md) — 所有回复默认中文

下次会话：MEMORY.md 全量注入（轨 A）→ 小模型选中（轨 B）→ 正文注入 → 中文回答。

5 · 层②写侧·通道二：轮末提取子代理（extractMemories）

对话内自记依赖模型"意识到该记"；漏掉的怎么办？每轮查询结束（模型产出无工具调用的最终回复）时，stopHooks fire-and-forget 启动一个 fork 出来的提取代理，自动把本轮新消息沉淀成记忆文件：

6 · 层②写侧·通道三：autoDream——记忆的夜间蒸馏

前两条通道按轮次工作，频率高、视野窄（只看本轮）。autoDream 是累积式蒸馏：积累足够多会话后，fork 一个子代理对整个记忆库做一次反思性整理（对应 /dream 技能的自动化版）：

// src/services/autoDream/autoDream.ts 文件头（原文）
// Background memory consolidation. Fires the /dream prompt as a forked
// subagent when time-gate passes AND enough sessions have accumulated.
//
// Gate order (cheapest first):          ← 门按成本从低到高排
//   1. Time: hours since lastConsolidatedAt >= minHours (one stat)
//   2. Sessions: transcript count with mtime > lastConsolidatedAt >= minSessions
//   3. Lock: no other process mid-consolidation

const DEFAULTS: AutoDreamConfig = { minHours: 24, minSessions: 5 }
// ↑ 阈值由 statsig 旗标 tengu_onyx_plover 下发；默认 24 小时 + 5 个会话
const SESSION_SCAN_INTERVAL_MS = 10 * 60 * 1000
// Scan throttle: when time-gate passes but session-gate doesn't, the lock
// mtime doesn't advance, so the time-gate keeps passing every turn.
// ↑ 时间门过了但会话门没过时，每 10 分钟才重扫一次会话数——防每轮空扫

// 与 extractMemories 同款受限工具（复用 createAutoMemCanUseTool），
// runForkedAgent 共享缓存；任务注册进 DreamTask 供 UI 展示进度

/dream 蒸馏提示词：四阶段（consolidationPrompt.ts 原文节选）

# Dream: Memory Consolidation
You are performing a dream — a reflective pass over your memory files.
Synthesize what you've learned recently into durable, well-organized memories...

## Phase 1 — Orient
- `ls` the memory directory / Read MEMORY.md / Skim existing topic files
  so you improve them rather than creating duplicates

## Phase 2 — Gather recent signal
1. Daily logs (logs/YYYY/MM/YYYY-MM-DD.md) if present — append-only stream
2. Existing memories that drifted — facts contradicting the codebase now
3. Transcript search — grep narrowly, don't read whole files:
   grep -rn "<narrow term>" <transcripts>/ --include="*.jsonl" | tail -50
Don't exhaustively read transcripts. Look only for things you already suspect matter.

## Phase 3 — Consolidate
- Merging new signal into existing topic files rather than near-duplicates
- Converting relative dates to absolute dates
- Deleting contradicted facts — fix it at the source

## Phase 4 — Prune and index
Update MEMORY.md so it stays under 200 lines AND under ~25KB. It's an **index**,
not a dump. Remove stale pointers; demote verbose entries (over ~200 chars →
move detail into topic file); resolve contradictions.
为什么需要夜间蒸馏：轮末提取是"增量追加"，天然碎片化；蒸馏是"全局整理"——合并重复主题、删除被推翻的事实、把索引瘦身回 200 行内。前三条通道负责"记住"，这条通道负责"记好"。

7 · 层②写侧·通道四：/remember——记忆的"晋升与治理"

auto-memory 记得越多，越需要决定"什么该升级成正式规范、什么该删"。/remember 技能做这件事，且被设计成提案-审批流（模型只提案，不动手）：

// src/skills/bundled/remember.ts —— 注册门（原文）

// proposed changes, grouped by action type. Do NOT apply changes — present

// 第 2 步：给每条 auto-memory 找归宿（原文表格）

// | CLAUDE.md          | 项目规范，所有贡献者该遵守（"use bun not npm"）      |
// | CLAUDE.local.md    | 个人偏好，不适用他人（"I prefer concise responses"） |
// | Team memory        | 跨仓库的组织级知识（"staging is at staging.internal"）|

const MAX_MEMORY_FILES = 200      // 清单硬上限
const FRONTMATTER_MAX_LINES = 30  // 每个文件只读前 30 行（frontmatter 界内）

export async function scanMemoryFiles(memoryDir, signal): Promise<MemoryHeader[]> {
  const entries = await readdir(memoryDir, { recursive: true })
  const mdFiles = entries.filter(f => f.endsWith('.md') && basename(f) !== 'MEMORY.md')
  // ↑ 入口文件不进清单——它已经在轨道 A 里了
  const headerResults = await Promise.allSettled(mdFiles.map(async (relativePath) => {
    const { content, mtimeMs } = await readFileInRange(
      filePath, 0, FRONTMATTER_MAX_LINES, undefined, signal)
    // 只读前 30 行：description 在 frontmatter 里，几百行正文根本不碰
    const { frontmatter } = parseFrontmatter(content, filePath)
    return { filename: relativePath, filePath, mtimeMs,
             description: frontmatter.description || null,
             type: parseMemoryType(frontmatter.type) }
  }))
  return headerResults.filter(fulfilled).map(r => r.value)
    .sort((a, b) => b.mtimeMs - a.mtimeMs)   // 新 → 旧
    .slice(0, MAX_MEMORY_FILES)
}
// 单趟设计（原注释）：readFileInRange 内部 stat 并返回 mtimeMs，
// "read-then-sort rather than stat-sort-read"——N≤200 时省一半系统调用

export function formatMemoryManifest(memories): string {
  return memories.map(m => {
    const tag = m.type ? `[${m.type}] ` : ''
    const ts = new Date(m.mtimeMs).toISOString()
    return m.description ? `- ${tag}${m.filename} (${ts}): ${m.description}`
                         : `- ${tag}${m.filename} (${ts})`
  }).join('\n')
}
// ↑ [type] 前缀与 ISO 时间戳都在清单里——小模型免费用上"类型"与"新鲜度"

export async function findRelevantMemories(query, memoryDir, signal,
                                            recentTools = [], alreadySurfaced = new Set(), parentSpan?) {

    .filter(m => !alreadySurfaced.has(m.filePath))
  // ↑ 挑选前就剔除之前轮次已注入的（"so the selector spends its 5-slot
  //   budget on fresh candidates"）

  const selectedFilenames = await selectRelevantMemories(query, memories, signal, recentTools, parentSpan)
  return selectedFilenames.map(f => byFilename.get(f)).filter(Boolean)
    .map(m => ({ path: m.filePath, mtimeMs: m.mtimeMs }))
}

async function selectRelevantMemories(...) {
  const validFilenames = new Set(memories.map(m => m.filename))
  const manifest = formatMemoryManifest(memories)
  const toolsSection = recentTools.length > 0
    ? `\n\nRecently used tools: ${recentTools.join(', ')}` : ''
  try {

      model: getDefaultSonnetModel(),      // 便宜的小模型

      max_tokens: 256,
      output_format: { type: 'json_schema', schema: { type: 'object',
        properties: { selected_memories: { type: 'array', items: { type: 'string' } } },
        required: ['selected_memories'], additionalProperties: false } },
      signal, querySource: 'memdir_relevance',
      optional: true,                      // 可选调用：失败可降级，不阻塞主请求
    })
    const parsed = jsonParse(textBlock.text)
    return parsed.selected_memories.filter(f => validFilenames.has(f))
    // ↑ 白名单过滤：小模型幻觉出的文件名在这里被丢弃

触发时机：每个用户轮最多一次 + 一排跳过条件

① 触发点：每个用户轮一次，不是模型的每次循环迭代
  （query.ts:452 原注释：Fired once per user turn — the prompt is invariant
   across loop iterations, so per-iteration firing would ask sideQuery
   the same question N times.）

② 零等待预取：与主 API 请求并行发出，消费点只 poll settledAt，从不阻塞
  （query.ts:1905 注释：If not settled yet, skip (zero-wait) and retry
   next iteration.）
  → 挑选的几百 ms 藏在主请求延迟里；没赶上这轮就不注入，绝不等它。

③ 跳过条件（attachments.ts:2419-2451），任一命中一次都不 call：
   - 自动记忆已禁用 / 灰度旗标 tengu_moth_copse 未开 / poor 模式
   - 没有真实用户消息
   - 用户输入只有单个词：!/\s/.test(input.trim())
     （"Single-word prompts lack enough context"——全是误报）
   - 会话累计注入达 60KB（MAX_SESSION_BYTES=61440，约 3 次满注入；
     计数靠扫描历史消息 → /compact 后自动重置）
   另：扫描清单为空 → 直接 return []，请求都不发

④ 两层防重复：挑选前 alreadySurfaced 剔除旧面孔；
   注入前 readFileState 再查——模型自己 Read/Write 过的不再注入
成本账：挑选约 300 token/轮（清单+任务+256 上限输出），被会话总闸 60KB 兜住；每轮注入 ≤5 条 × 4KB = 20KB。遥测注记：logMemoryRecallShape 在本快照的外部构建中是导出空实现（stub），选择率统计只在内部构建生效。

export function isSnipMarkerMessage(message: Message): boolean {
  if (message.type !== 'system') return false
  return (message as Record<string, unknown>).subtype === 'snip_marker'
}

13 · 结论：Claude Code 记忆设计的五条哲学

① 一切皆 markdown + 文件工具——四层载体、四条写侧通道、三条读侧机制，没有任何一步进数据库或向量库；记忆天然可审计（memory_saved 通知、文件可 git、用户可手改）。 ② 描述/正文分离是全系统的支点——检索只读每文件前 30 行的 frontmatter，命中才读正文；description 写给小模型看，正文写给命中后的任务看。索引（MEMORY.md）便宜到可以每轮全量，正文贵到必须按需挑选。 ③ 每一层都有物理限容，降级必告知——200 行/25KB（索引）、30 行（清单头）、4KB/条 × 5 条/轮（注入）、60KB/会话（挑选总闸）、2000/节与 12k（会话笔记）；所有截断都附带"我截了、为什么、你该做什么"的 WARNING。半条记忆比没有更糟，静默降级比截断更糟。 ④ 模型自主判断 + 框架确定性兜底的分工——"记什么、挑什么、信什么"交给模型（规约 + 小模型，语义灵活）；"限容、去重、白名单、游标、路径安全、熔断"交给代码（确定性、可测试）。两头都不越界。 ⑤ 缓存经济学贯穿始终——挑选预取零等待（藏在主请求延迟里）、提取/蒸馏/笔记全部 fork 共享父缓存、microCompact 分冷热两路（冷清热 cache_edits）、压缩代理被迫带工具定义就靠强提示词禁用。窗口管理方案若不考虑 KV 缓存计价，账就是错的。

一句话：Claude Code 把"记忆"做成了一个文件系统的缓存问题——写入靠模型在规约下顺手完成，读取靠分层过滤（全量索引 + 语义挑选 + 可搜索），每一层都有明确的容量预算与降级协议，而所有昂贵操作都被 prompt 缓存的经济学约束塑形。
