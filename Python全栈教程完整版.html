00 · Web 基础：互联网是怎么工作的（+ LLM 时代学习法）

这一章对标 CS50W 的第 0 讲：先搞清楚"网页是怎么到你面前的"，后面学任何框架都不会迷路。框架会过时，这些原理十年不变。

0.1 一个网页是怎么到你面前的（用餐厅理解一切）

先建立整张地图，后面所有章节都在这张图上展开：

你在浏览器输入 myblog.com 回车
        │
        ▼
浏览器发出一个 HTTP 请求  ──────►  某台服务器上的程序收到请求
（"把首页给我"）                    （读数据库、拼出 HTML）
        │                                  │
        ▼                                  │
浏览器收到 HTTP 响应  ◄────────────────────  ┘
（HTML/CSS/JS 或 JSON）
        │
        ▼
浏览器把代码渲染成你看到的页面

用餐厅类比（这个类比后面会一直用）：

餐厅 Web 世界
你（顾客） 用户 + 浏览器
服务员 HTTP 协议（负责传话，规矩固定）
餐厅装修、菜单、餐桌 前端（你看得见的部分）
后厨 后端（服务器上跑的程序）
菜谱 后端代码（Django 就是一套好用的厨具）
食材仓库 数据库（存文章、用户、评论）
菜单上"怎么点菜"的规矩 API

全栈工程师 = 前端 + 后端 + 数据库都会，能把一道菜从菜单设计到出餐全流程打通。

0.2 HTTP：服务员的"传话规矩"

浏览器和服务器之间的每次往来，都是一个 HTTP 请求 和一个 HTTP 响应。亲手看一次（别只是读）：

curl -i https://example.com

你会看到类似这样的输出：

HTTP/2 200                          ← 状态行：协议 + 状态码
content-type: text/html; charset=UTF-8   ← 响应头：这段内容是什么
...

<!doctype html>                     ← 响应体：真正的内容
<html>
<head><title>Example Domain</title></head>
...

一个请求由四部分组成：

  1. 方法（method）：想干什么——"拿数据"还是"提交数据"
  2. 路径（URL）：对什么资源操作
  3. 请求头（headers）：附加说明（"我能接受中文"、"我是谁"[登录凭证]）
  4. 请求体（body）：提交的数据（比如注册时的用户名密码）

常用方法（背下来，一共 5 个）

以后 MyBlog 的 API 就全靠它们，同一个路径配合不同方法就是不同操作（这就是 REST 风格）：

方法 含义 MyBlog 中的例子
GET 读取 GET /api/posts/ 拿文章列表
POST 创建 / 提交 POST /api/posts/ 发新文章
PUT / PATCH 修改 PATCH /api/posts/1/ 改标题
DELETE 删除 DELETE /api/posts/1/ 删文章

状态码：服务员的回话

状态码 含义 记忆点
200 / 201 成功 / 创建成功 一切正常
301 / 302 重定向 "搬去新地址了，去那儿"
400 请求有错 "你提交的表单不对"
401 / 403 没登录 / 没权限 "工牌呢？"/"这不归你管"
404 找不到 "没有这个页面/资源"
500 服务器内部错误 "厨房着火了"（你的代码崩了）

规律：2xx 都是好的，4xx 是客户端（你发请求的）问题，5xx 是服务端问题。调试时第一眼看状态码，立刻知道该查前端还是后端。

0.3 网页的三种"生产方式"（理解本教程主线的钥匙）

同样是展示一篇文章列表，历史上有三种做法。理解了这三种，你就理解了为什么要有 Django 模板、为什么要学 React：

方式一：静态页面。服务器上放一个写死的 HTML 文件，谁来都是同一份。改一个字要重新写文件。适合纯展示，没法存用户数据。

方式二：服务端渲染（SSR）—— Django 模板的做法。请求来了，Django 当场查数据库、把数据"塞进"HTML 模板，做一份新鲜的 HTML 发给你：

浏览器: GET /posts/  ──►  Django 查库 ──► 填进模板 ──► 返回完整 HTML

第 3 章你会亲手写一遍。特点：HTML 是后端做的。

方式三：前后端分离（SPA）—— 本教程主线。后端只提供 JSON 数据接口（API），前端 React 负责拿数据、画页面：

第一次请求：服务器返回 React 应用（一个"空壳" HTML + JS）
之后的交互：JS 在浏览器里调用 GET /api/posts/ 拿到 JSON，自己渲染成页面

特点：HTML 在用户的浏览器里做，后端只管数据。这就是 MyBlog 最终的形态，DRF（后端造数据）+ React（前端画界面）。

三种方式没有绝对好坏，很多大公司混着用。但对学习者和大多数新项目，"分离"是当前主流，也是招聘要求的主流。

0.4 动手：亲手发一个表单请求（CS50W 经典实验）

HTML 是网页的"骨架"。新建 form.html，浏览器打开它：

<!DOCTYPE html>
<html>
<head>
  <meta charset="utf-8">
  <title>我的第一个表单</title>
</head>
<body>
  <h1>搜索引擎实验</h1>

  <!-- 一个表单：提交时会发一个 GET 请求 -->
  <form action="https://www.bing.com/search" method="get">
    <input type="text" name="q" placeholder="想搜什么？">
    <button type="submit">去必应搜索</button>
  </form>
</body>
</html>

输入"django"点提交，注意观察浏览器的地址栏变成了：

https://www.bing.com/search?q=django

发生了什么？点击按钮 → 浏览器把输入框的值装进 URL 的 ?q=django（这叫 query 参数）→ 发出 GET /search?q=django → 必应服务器从 URL 里取出 q 的值去查搜索结果。这就是"前端收集用户输入 → 后端处理"最原始的形态，第 6 章你在 React 里写的登录表单，本质是同一件事，只是用 JS 发请求、不用跳转页面。

再认识几个最常用的 HTML 标签（会查、会改即可，不用背）：

<h1>~<h6>  标题           <a href="...">  链接
<p>        段落           <img src="..."> 图片
<div>      盒子（布局用）  <ul> <li>       列表
<table>    表格           <form> <input>  表单

CSS 是"皮肤"，负责颜色、字体、布局。原理是选择器选中元素，套上样式：

<style>
  h1 { color: #2c7be5; }        /* 所有 h1 变蓝色 */
  .card {                        /* class="card" 的元素 */
    border: 1px solid #ddd;      /* 盒子模型：边框 */
    padding: 16px;               /* 内边距 */
    margin: 8px;                 /* 外边距 */
  }
</style>

本教程不深抠 CSS——React 项目里我们会用现成的简单样式，把时间花在架构和逻辑上。想补 UI 功底，推荐 MDN 的 CSS 教程。

0.5 JSON 与 API：前后端之间的"集装箱"

API（Application Programming Interface） 就是上面说的"点菜规矩"：后端公开声明"有什么资源、用什么方法、传什么参数、返回什么格式"，前端照着规矩调用。

而 JSON 是约定好的数据格式——一门所有语言都认识的"普通话"。Python 的字典转成 JSON 几乎一模一样：

{
  "id": 1,
  "title": "我的第一篇博客",
  "author": "小明",
  "tags": ["django", "python"],
  "is_published": true
}

亲手看一个真实 API：浏览器地址栏直接访问

https://jsonplaceholder.typicode.com/posts/1

返回的就是 JSON（一个假的文章接口，第 2 章和第 5 章都会拿它练手）。MyBlog 做完后，你的 /api/posts/1 长得和它一样——所谓全栈，就是自己把这条链路造出来。

0.6 浏览器开发者工具：你的 X 光机

按 F12 打开，三个面板从头用到尾：

  • Elements：看页面的 HTML/CSS 长什么样，改了立刻生效（不影响真服务器）
  • Console：看 JS 报错、随手执行 JS
  • Network：最有用——看页面发了哪些请求、每个请求的状态码/耗时/响应内容

实验：打开必应搜一个词，切到 Network 面板，找到那条 search?q=xxx 请求，点开看它的状态码 200、响应体。以后联调时"页面没数据"，第一件事就是来 Network 看：请求发出去没？状态码多少？响应里写了什么？——答案基本都在这。

0.7 LLM 时代学习法：把 AI 变成 24 小时私教

这是 2026 年学编程和 2016 年最大的区别。AI 用对了能快一倍，用错了会让你"学了个寂寞"。核心原则：AI 是私教，不是枪手。

五个立刻能用的问法模板

  1. 学概念："用新手能懂的话 + 一个生活类比解释 Django 的 ORM，然后给一个'博客文章'的代码例子"
  2. 要练习："就 Python 字典给我出 5 道由易到难的练习题，不要先给答案，我答一道你批改一道"
  3. 代码审查：贴上自己写的代码，"帮我 review：哪里有问题、为什么、怎么改。不要直接重写我的代码"
  4. 调试（最重要的场景）："我期望得到 A，实际得到 B，完整报错如下（贴全），相关代码如下（贴全），运行环境是 Windows + Django 5。帮我定位原因，一步步教我怎么排查"
  5. 追问："为什么 Django 要分成项目和 app 两层？不分行不行？"——多问为什么，AI 时代便宜的是答案，值钱的是理解

三个警惕

  1. 不读直接抄 = 没学。抄完必须让 AI 逐行讲一遍，然后自己合上代码重写一遍。
  2. AI 会一本正经地胡说（幻觉），尤其是旧版本 API。教程知识以官方文档为准：Django 和 React 的官方文档都有中文版，AI 说的是否对，去文档搜一下就知道。
  3. 别让 AI 替你写整个项目。自己动手的比例低于 50%，面试手写代码和实际工作会立刻露馅。

建议节奏

自己先干 15-20 分钟 → 卡住就记录问题 → 一次性带着完整上下文问 AI → 追问为什么 → 最后把你的理解讲给 AI 听（"我来复述一下，你听听对不对"）。最后这步是费曼学习法，能瞬间暴露你以为懂了但其实没懂的地方。

1.6 类与对象

Django 的模型、视图都是用类写的，所以类必须看懂。类的本质：把数据和操作数据的函数打包在一起。

class Post:
    def __init__(self, title, author):
        self.title = title        # self 相当于"这个对象自己"
        self.author = author
        self.views = 0

    def read(self):               # 类里定义的函数叫"方法"
        self.views += 1
        return f"《{self.title}》 已被阅读 {self.views} 次"

post = Post("第一篇文章", "小明")   # 实例化，不需要 new 关键字
print(post.title)                  # 第一篇文章
print(post.read())                 # 《第一篇文章》 已被阅读 1 次
print(post.read())                 # 《第一篇文章》 已被阅读 2 次

继承——Django 里你会天天写 class Post(models.Model)，意思就是继承 Django 提供的 Model 类：

class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} 在叫"

class Dog(Animal):                # Dog 继承 Animal
    def speak(self):              # 重写父类方法
        return f"{self.name}：汪汪"

dog = Dog("旺财")
dog.speak()    # 旺财：汪汪

一个 .py 文件就是一个模块，用 import 引入：

1.8 异常处理

程序出错不能直接崩掉，用 try/except 兜住：

try:
    num = int(input("输入一个数字: "))
    result = 10 / num
    print(result)
except ValueError:
    print("那不是数字")
except ZeroDivisionError:
    print("不能除以零")
finally:
    print("无论如何都会执行（常用于关闭资源）")

1.9 虚拟环境与 pip（重点！）

虚拟环境（venv） 是每个 Python 项目的"独立包厢"。项目 A 要 Django 5、项目 B 要 Django 3，混在一起会打架，虚拟环境让每个项目用自己的包和版本。

# 在项目目录下创建虚拟环境（生成一个 .venv 文件夹）
python -m venv .venv

# 激活 —— Git Bash：
source .venv/Scripts/activate
# 激活 —— PowerShell：
# .\.venv\Scripts\Activate.ps1
# 激活 —— macOS/Linux：
# source .venv/bin/activate

# 激活成功后，命令行开头会出现 (.venv) 标记
# 退出虚拟环境：
deactivate

激活后，python 和 pip 都指向这个虚拟环境里的版本。以后每个项目都要先激活自己的 venv 再干活。

pip 是包管理器（相当于前端的 npm）：

pip install requests            # 安装
pip list                        # 看装了什么
pip freeze > requirements.txt   # 把依赖清单导出成文件
pip install -r requirements.txt # 按清单安装（拿到别人项目时先执行这个）

注意 Windows 上 pip freeze 可能会带出 pip、setuptools 自身，它们留着无妨；也可以用 pip freeze --exclude pip setuptools 导出。

1.10 两个"认识即可"的概念

这两个概念现在不需要深究，但 Django 代码里会见到，先混个脸熟：

装饰器：写在函数定义上方的 @xxx，作用是"给函数包一层附加功能"。比如 Django 的 @login_required 表示"这个视图必须登录才能访问"：

@login_required
def my_view(request):
    ...

上下文管理器 with：自动帮你"用完收拾干净"（比如自动关闭文件）：

with open("data.txt", "w", encoding="utf-8") as f:
    f.write("hello")
# 离开 with 块，文件自动关闭，不用手动 f.close()

1.11 综合练习：命令行待办清单

不依赖任何框架，纯 Python 写一个小程序，把本章知识全用上。新建 todo.py，自己先试着写，写不出来再看参考实现。

需求： 1. 程序启动后循环显示菜单：1. 添加待办 2. 列出待办 3. 完成待办 4. 退出 2. 待办数据保存到 todos.json，重启程序不丢失（提示：json.dump / json.load） 3. 完成待办后标记 done: true，列表里显示 ✅

参考实现（先自己写再看） 
import json
import os

FILE = "todos.json"


def load_todos():
    if not os.path.exists(FILE):
        return []
    with open(FILE, "r", encoding="utf-8") as f:
        return json.load(f)


def save_todos(todos):
    with open(FILE, "w", encoding="utf-8") as f:
        json.dump(todos, f, ensure_ascii=False, indent=2)


def main():
    while True:
        print("\n1. 添加待办  2. 列出待办  3. 完成待办  4. 退出")
        choice = input("> ").strip()

        if choice == "1":
            todos = load_todos()
            title = input("要做什么: ").strip()
            todo = {"id": len(todos) + 1, "title": title, "done": False}
            todos.append(todo)
            save_todos(todos)
            print(f"已添加: {title}")

        elif choice == "2":
            todos = load_todos()
            if not todos:
                print("没有待办事项")
            for t in todos:
                mark = "✅" if t["done"] else "⬜"
                print(f'{mark} [{t["id"]}] {t["title"]}')

        elif choice == "3":
            todos = load_todos()
            todo_id = int(input("完成第几项: "))
            for t in todos:
                if t["id"] == todo_id:
                    t["done"] = True
            save_todos(todos)

        elif choice == "4":
            print("再见")
            break


if __name__ == "__main__":
    main()

02 · JavaScript 基础：从 Python 视角学 JS

本章目标：掌握读懂和编写 React 代码所需的现代 JS（ES6+）。你已经会 Python 了，所以这章我们大量用"Python 里对应什么"来对照着学，速度会很快。

2.1 JS 在哪里运行

  • 浏览器里：所有网页的交互逻辑都是 JS 写的
  • Node.js 里：让 JS 脱离浏览器运行，相当于"JS 版的 Python 解释器"，也是前端构建工具的地基

你已装好的 Node 自带 node 命令，用法和 Python 一样：node 进入交互模式，node xxx.js 运行脚本文件。

// hello.js
console.log("我的 JS 第一课");   // console.log 就是 Python 的 print

node hello.js

2.2 变量与基本类型

现代 JS 只用 let 和 const 声明变量（var 是历史遗留，别用）：

const name = "小明";     // const = 不可重新赋值，默认都用这个
let age = 25;           // let = 可以重新赋值

age = 26;               // ✅
// name = "小红";        // ❌ 报错 TypeError

基本类型：number（不区分整数浮点）、string、boolean（小写 true/false）、null、undefined（声明了但没赋值）。

坑 1：=== 和 ==

1 == "1"    // true  —— == 会偷偷转类型，别用！
1 === "1"   // false —— 以后一律用 === 和 !==

坑 2：字符串拼接用 +，但模板字符串更好用（对应 Python 的 f-string）：

const name = "Django";
const msg = `正在学习 ${name}`;   // 反引号 ` 包起来，${} 嵌变量

2.3 函数与箭头函数

普通函数：

function add(a, b) {
  return a + b;
}

箭头函数——React 代码里 90% 的函数长这样：

const add = (a, b) => {
  return a + b;
};

// 函数体只有一句 return 时，可以更短：
const add = (a, b) => a + b;
const double = (n) => n * 2;
const sayHi = () => console.log("hi");

默认参数和 Python 一样：

const createPost = (title, author = "匿名") => {
  console.log(`${title} - ${author}`);
};

2.4 对象与解构

JS 的对象长得像 Python 字典，但键不用加引号，取值用 .：

const post = {
  id: 1,
  title: "我的第一篇博客",
  views: 100,
};

post.title          // '我的第一篇博客'（也可写成 post["title"]）
post.author = "小明"; // 新增

解构赋值——从对象/数组里一把取出字段，React 里天天用：

const { id, title } = post;          // 相当于 id = post.id; title = post.title
const [first, second] = ["a", "b"];  // 数组解构：first='a', second='b'

展开运算符 ...——React 更新数据的核心操作（创建新对象而不是改旧对象）：

const updated = { ...post, views: 200 };   // 复制 post 并覆盖 views
const merged = [...arr1, ...arr2];         // 合并数组

2.5 数组方法（React 必备）

Python 列表推导能干的事，JS 用这些方法干。map 和 filter 是 React 的命根子，必须练熟：

const nums = [1, 2, 3, 4, 5];

nums.map((n) => n * 2);              // [2,4,6,8,10]  —— 对应 [n*2 for n in nums]
nums.filter((n) => n % 2 === 0);     // [2,4]         —— 对应 [n for n in nums if ...]
nums.find((n) => n > 3);             // 4             —— 找第一个满足的
nums.reduce((sum, n) => sum + n, 0); // 15            —— 累加
nums.includes(3);                    // true          —— 对应 3 in nums

处理"一堆字典"（API 返回的数据都是这种）：

const posts = [
  { id: 1, title: "a", views: 10 },
  { id: 2, title: "b", views: 99 },
];

const titles = posts.map((p) => p.title);          // ['a', 'b']
const hot = posts.filter((p) => p.views > 50);     // [{id:2,...}]
const post2 = posts.find((p) => p.id === 2);       // {id:2,...}

2.6 异步：async / await（最重要的一节）

前端到处是异步：请求接口要等网络返回、读文件要等磁盘。JS 的做法是不阻塞等待，先干别的，等结果回来再继续。

Promise 表示"一个将来才有结果的操作"，可以理解为一张取餐号：

// 3 秒后取到结果
const p = new Promise((resolve) => {
  setTimeout(() => resolve("饭好了"), 3000);
});

async/await 让异步代码写起来跟同步代码一样（和 Python 的 asyncio 语法几乎一样）：

// 函数前加 async
const cook = async () => {
  console.log("点单");
  const result = await p;    // await = 在这里等结果，但不卡住整个程序
  console.log(result);       // "饭好了"
};

请求网络数据用 fetch——这就是以后 React 获取后端数据的方式：

const loadPosts = async () => {
  try {
    const res = await fetch("https://jsonplaceholder.typicode.com/posts");
    const data = await res.json();   // 把响应体解析成 JS 对象（注意也要 await）
    console.log(data);               // 100 篇文章的数组
  } catch (err) {
    console.log("请求失败:", err);    // 对应 Python 的 except
  }
};

loadPosts();

2.7 模块：import / export

代码按文件拆分，互相导入。和 Python 的 import 意图一样，语法不同：

// utils.js —— 导出
export const API_URL = "http://127.0.0.1:8000/api";

export const formatDate = (d) => d.slice(0, 10);

export default function greet() {   // 默认导出（一个文件只能有一个）
  return "hello";
}

// main.js —— 导入
import greet from "./utils.js";                     // 默认导出：不需要花括号
import { API_URL, formatDate } from "./utils.js";   // 具名导出：必须花括号

React 项目的每个组件都是一个模块。

2.8 npm：JS 界的 pip

npm 是 JS 的包管理器，package.json 是项目的"依赖清单 + 脚本配置"（相当于 requirements.txt + 一组命令）。

npm install            # 安装 package.json 里的全部依赖（相当于 pip install -r）
npm install axios      # 安装某个包并写入 package.json（相当于 pip install）
npm run dev            # 运行 package.json 里 scripts.dev 定义的命令

目录里的两个东西：

  • node_modules/：所有下载的包（巨大，永远不要提交到 git，.gitignore 里已写好）
  • package-lock.json：精确版本锁定（要提交）

npm 下载慢可换国内镜像：npm config set registry https://registry.npmmirror.com

3.5 模型与 ORM：用 Python 操作数据库

ORM 是什么（本章最重要的概念）

数据存在数据库的表里，操作表要用 SQL（INSERT INTO blog_post ...）。ORM（对象关系映射）让你用 Python 类和对象代替手写 SQL：

数据库世界 Python 世界
表 blog_post 类 Post
一行数据 一个 Post 实例
一列（字段） 一个属性

你写 Post.objects.all()，Django 翻译成 SELECT * FROM blog_post;。好处：换数据库不用改业务代码，且全程类型安全。

定义模型

blog/models.py：

from django.db import models


class Post(models.Model):
    title = models.CharField("标题", max_length=100)
    content = models.TextField("正文")
    author = models.CharField("作者", max_length=50, default="匿名")  # 第 4 章会升级成真正的用户
    created_at = models.DateTimeField("创建时间", auto_now_add=True)  # auto_now_add：创建时自动记录

    class Meta:
        ordering = ["-created_at"]   # 默认按创建时间倒序（新的在前）

    def __str__(self):
        return self.title            # 决定在 Admin 里显示什么名字

常用字段速查：CharField（短文本，必须给 max_length）、TextField（长文本）、IntegerField、BooleanField、DateTimeField、FloatField、ForeignKey（马上讲）。

迁移：把模型变成真实的表

改了模型，就要跑"迁移"两步曲（Django 日常最高频命令）：

python manage.py makemigrations   # 第一步：对比模型和数据库，生成"施工图纸"（blog/migrations/0001_initial.py）
python manage.py migrate          # 第二步：按图纸施工，真正建表

打开 blog/migrations/0001_initial.py 看看——施工图纸就是一份 Python 描述。为什么分两步？ 因为线上项目不能随手改表结构，图纸先经过 review/测试再施工，安全可控。项目根目录会多出一个 db.sqlite3——开发期用的轻量级数据库文件，零配置，第 7 章上线再换 PostgreSQL。

ORM 实操（打开 python manage.py shell 跟着敲）

>>> from blog.models import Post

# 增
>>> Post.objects.create(title="第一篇文章", content="Hello Django", author="小明")
<Post: 第一篇文章>
>>> Post.objects.create(title="第二篇", content="学 ORM", author="小红")

# 查
>>> Post.objects.all()                      # 全部（QuerySet，类似列表）
>>> Post.objects.count()                    # 2
>>> Post.objects.get(id=1)                  # 取一条（没有或有多条会报错）
>>> Post.objects.filter(author="小明")       # 条件查询，返回列表
>>> Post.objects.filter(title__contains="文章")   # 双下划线 = 深入条件：标题含"文章"
>>> Post.objects.filter(title__icontains="django")  # i 开头 = 忽略大小写
>>> Post.objects.first()                    # 第一条（因为 Meta 里按时间倒序 = 最新的）

# 改
>>> p = Post.objects.get(id=1)
>>> p.title = "第一篇文章（改）"
>>> p.save()

# 删
>>> Post.objects.get(id=2).delete()

objects 这个东西叫管理器（Manager），模型的增删改查都从它出发。以后你在 DRF 视图里写的 Post.objects.all() 就是这里练的功夫。

模型关系：一篇文章有多条评论

数据库表示"一对多"用外键（ForeignKey）：评论表里存一列"属于哪篇文章"。blog/models.py 加：

class Comment(models.Model):
    post = models.ForeignKey(
        Post,                              # 关联到哪张表
        on_delete=models.CASCADE,          # 文章删除时，它的评论一起删
        related_name="comments",           # 反向查询的名字：post.comments
    )
    author = models.CharField("评论人", max_length=50, default="匿名")
    content = models.TextField("内容")
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["created_at"]

    def __str__(self):
        return f"{self.author} 的评论"

两个参数的含义值得停下来理解：

  • on_delete 决定"爹没了，孩子怎么办"：CASCADE 一起删（博客评论的正确选择）、SET_NULL 置空（适合"文章删了，作者记录保留"）、PROTECT 有孩子就不许删爹。
  • related_name 给"从一查多"起名字。没有它默认叫 comment_set，起了之后：
>>> from blog.models import Post, Comment
>>> post = Post.objects.get(id=1)
>>> Comment.objects.create(post=post, author="路人甲", content="写得好！")
>>> Comment.objects.create(post=post, author="路人乙", content="学习了")
>>> post.comments.all()      # 反向查：这篇文章的所有评论
>>> post.comments.count()    # 2

别忘了迁移：makemigrations + migrate。

04 · DRF：把 Django 变成 JSON API 服务器

本章目标：理解"序列化"，从手写 JSON 一步步进化到 ViewSet + Router，给 MyBlog 建成一套带认证、分页、过滤的规范 REST API。这一章做完，后端部分就基本完工了——第 5 章开始 React 只是换战场。

4.1 为什么要序列化（用例子搞懂这个核心概念）

数据库里的数据是 Python 对象，没法直接塞进 HTTP 响应发给浏览器。回忆第 0 章：前后端之间的"普通话"是 JSON。所以后端必须完成一次翻译：

Python 对象（Post 实例） ──序列化──► JSON 字符串 ──► 发给前端
JSON 字符串 ──反序列化──► Python 数据 ──► 校验、存入数据库

不装 DRF 时，翻译得自己写。blog/views.py 里试一下：

from django.http import JsonResponse
from .models import Post

def post_list_raw(request):
    posts = Post.objects.all()
    data = [
        {"id": p.id, "title": p.title, "content": p.content, "author": p.author}
        for p in posts
    ]
    return JsonResponse(data, safe=False)

挂上路由访问 /api/raw-posts/，能看到 JSON。能跑，但问题一大堆：每加一个字段要手动同步；发文章时的数据校验要手写；认证、分页、格式统一全都要自己造。翻译和校验这种高度模式化的活，就该交给工具——这就是 DRF。

安装并注册：

pip install djangorestframework djangorestframework-simplejwt

# settings.py
INSTALLED_APPS = [
    # ...
    "rest_framework",
    "blog",
]

4.2 序列化器（Serializer）：翻译官上岗

blog/serializers.py（新建）：

from rest_framework import serializers
from .models import Post


class PostSerializer(serializers.ModelSerializer):
    class Meta:
        model = Post
        fields = ["id", "title", "content", "author", "created_at"]

ModelSerializer 会自动照着 Post 模型生成字段——模型改了，序列化器跟着变，不用手动同步。它双向工作：

  • 序列化：Post 对象 → JSON（GET 接口用它）
  • 反序列化：前端提交的 JSON → 校验 → Python 数据（POST/PUT 接口用它，校验不过自动返回 400 和错误详情）

现在读文章接口可以写成：

from rest_framework.decorators import api_view
from rest_framework.response import Response
from .models import Post
from .serializers import PostSerializer

@api_view(["GET"])
def post_list(request):
    posts = Post.objects.all()
    serializer = PostSerializer(posts, many=True)   # many=True：翻译一批
    return Response(serializer.data)

@api_view 让普通函数视图获得 DRF 能力（解析 JSON、内容协商、可浏览界面）。这是函数视图（FBV）写法，直观、适合自定义逻辑。

测试：浏览器访问 http://127.0.0.1:8000/api/posts/。你会发现一个惊喜——DRF 自带一个可浏览的 API 界面（browsable API）：页面本身就是这个接口的人类友好版，能直接看 JSON、发测试请求。这是 DRF 招人喜欢的招牌功能，开发期全靠它调试。

4.3 视图进化：从 40 行到 4 行

标准的"增删改查 + 单个详情"，每个资源都是同一套模式。DRF 提供了逐级封装：

写法 代码量 适用场景
函数视图 @api_view 多 逻辑特殊的自定义接口（如统计、登录）
APIView 类 中 需要精细控制每个方法时
ViewSet + Router 最少 标准的增删改查（本项目主力）

直接看最终形态。blog/views.py：

from rest_framework import viewsets, permissions
from .models import Post
from .serializers import PostSerializer


class PostViewSet(viewsets.ModelViewSet):
    """一个类 = 文章的增删改查全套接口"""
    queryset = Post.objects.all()
    serializer_class = PostSerializer
    permission_classes = [permissions.IsAuthenticatedOrReadOnly]

IsAuthenticatedOrReadOnly 的含义：读（GET）随便，写（POST/PUT/DELETE）必须登录——博客的天然规则。

myblog/urls.py 用 Router 自动注册路由：

from django.contrib import admin
from django.urls import path, include
from rest_framework.routers import DefaultRouter
from blog.views import PostViewSet

router = DefaultRouter()
router.register(r"posts", PostViewSet)

urlpatterns = [
    path("admin/", admin.site.urls),
    path("api/", include(router.urls)),
]

访问 /api/posts/（列表）和 /api/posts/1/（详情）。Router 自动生成了一整套路由：

URL 方法 动作
/api/posts/ GET / POST 列表 / 创建
/api/posts/{id}/ GET / PUT / PATCH / DELETE 详情 / 修改 / 删除

4 行代码 = 6 个接口。不是魔法，只是把 4.2 里你会手写的东西模式化了——所以前面先手写一遍再上工具，你才知道它在帮你干什么。

4.4 让列表更好用：分页与搜索

文章多了不可能一次全吐。settings.py 加全局配置：

REST_FRAMEWORK = {
    "DEFAULT_PERMISSION_CLASSES": [
        "rest_framework.permissions.IsAuthenticatedOrReadOnly",
    ],
    "DEFAULT_PAGINATION_CLASS": "rest_framework.pagination.PageNumberPagination",
    "PAGE_SIZE": 10,
}

刷新 /api/posts/：返回结构变成了 {"count": 总数, "next": 下一页URL, "previous": ..., "results": [...]}——分页是前端分页组件的直接数据来源。

搜索功能，给 ViewSet 加一个方法（学过的 ORM 双下划线派上用场）：

class PostViewSet(viewsets.ModelViewSet):
    serializer_class = PostSerializer
    permission_classes = [permissions.IsAuthenticatedOrReadOnly]

    def get_queryset(self):
        queryset = Post.objects.all()
        keyword = self.request.query_params.get("search")   # /api/posts/?search=django
        if keyword:
            queryset = queryset.filter(title__icontains=keyword)
        return queryset

4.5 用户系统：注册、登录与 JWT

JWT 是什么（类比工牌）

JWT（JSON Web Token）是最流行的接口认证方案。流程很像公司进门：

  1. 你在前台登记（登录），领到一张工牌（token，一段长字符串）
  2. 之后每次进实验室（请求受保护的接口），出示工牌即可，不用再报身份证
  3. 工牌有有效期，过期了去前台续一张（refresh token）

好处：后端不用在数据库里存"谁登录了"（无状态），天然适合前后端分离。

5.4 state：组件自己的记忆

props 是别人给的，state 是组件自己管理、可以变化的数据。state 一变，React 自动重新渲染组件——这就是 UI = f(state)：界面是状态算出来的，你只管改状态，React 负责更新页面。

计数器（React 的"Hello World"）：

import { useState } from "react";

function Counter() {
  // useState 返回两个值：[当前状态, 修改状态的函数]
  const [count, setCount] = useState(0);

  return (
    <>
      <p>点了 {count} 次</p>
      {/* 点击 → setCount → state 变化 → React 自动重新渲染 */}
      <button onClick={() => setCount(count + 1)}>+1</button>
    </>
  );
}

注意 onClick={() => setCount(count + 1)} 传的是函数，不是 onClick={setCount(count + 1)}（那样页面加载时就立刻执行了）。

不可变性：永远创建新数据，不要改旧的

React 判断"要不要重新渲染"的依据是 state 有没有变化，它用 === 对比新旧值。 所以改 state 必须用"造新数据"的方式（第 2 章的展开运算符派上用场）：

const [posts, setPosts] = useState(["第一篇"]);

// ❌ 错误：直接改旧数据，引用没变，React 不刷新
posts.push("第二篇");
setPosts(posts);

// ✅ 正确：用展开运算符造新数组
setPosts([...posts, "第二篇"]);

// ✅ 修改对象同理
const [user, setUser] = useState({ name: "小明", age: 25 });
setUser({ ...user, age: 26 });

这是新手第一大坑，记住口诀：setState 时，永远给新对象/新数组。

子组件怎么改父组件的数据：回调函数

props 只读，但你可以把"修改函数"作为 props 传下去（第 6 章的评论功能就是这么干的）：

// 父组件
function App() {

5.7 useEffect：组件的"副作用"

副作用 = 渲染之外的事：请求接口、操作定时器……最常见的就是"组件一出现就去拿数据"。

import { useState, useEffect } from "react";

function PostList() {
  const [posts, setPosts] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    // effect 里不能直接 await，标准写法：里面定义异步函数再调用
    const loadPosts = async () => {
      try {
        const res = await fetch("https://jsonplaceholder.typicode.com/posts");
        const data = await res.json();
        setPosts(data.slice(0, 10));   // 拿 10 篇够演示了
      } catch (err) {
        setError("加载失败，请稍后重试");
      } finally {
        setLoading(false);             // 无论成败，停止转圈
      }
    };
    loadPosts();
  }, []);   // ⚠️ 依赖数组：[] 表示"只在组件第一次出现时执行一次"

  if (loading) return <p>加载中...</p>;
  if (error) return <p>{error}</p>;

  return (
    <ul>
      {posts.map((p) => (
        <li key={p.id}>{p.title}</li>
      ))}
    </ul>
  );
}

第二个参数（依赖数组）决定 effect 何时重新执行：

useEffect(() => {...}, []);        // 只在首次渲染后执行（拿列表数据）
useEffect(() => {...}, [id]);      // id 变了就执行（切换文章详情）
useEffect(() => {...});            // ⚠️ 每次渲染都执行，几乎总是错的

一个细节：useEffect 里的异步操作发生在渲染之后，所以需要 loading 这类状态先渲染"加载中"。"渲染 → 触发副作用 → 改 state → 重新渲染" 这个循环是 React 应用的心跳。

6.2 先过一关：CORS（跨域）

兴冲冲在 React 里写个 fetch("http://127.0.0.1:8000/api/posts/")，你会撞上人生第一个 CORS 报错：

Access to fetch at 'http://127.0.0.1:8000/api/posts/' from origin
'http://localhost:5173' has been blocked by CORS policy

为什么被拦？ 浏览器有一条安全铁律叫同源策略：协议、域名、端口三者必须完全一致，页面里的 JS 才能自由请求。localhost:5173 和 127.0.0.1:8000 端口不同 = 跨域 = 浏览器把响应拦下（注意：请求其实发出去了，是浏览器把响应藏起来了，这是浏览器的自我保护，防止恶意网站偷用你在别处的登录态）。

解法是"服务器白名单"：Django 明确告诉浏览器"5173 是我自己人，放行"。装官方扩展：

pip install django-cors-headers

# settings.py
INSTALLED_APPS = [
    "corsheaders",        # 放在靠前位置
    "rest_framework",
    # ...
]

MIDDLEWARE = [
    "corsheaders.middleware.CorsMiddleware",   # 必须放最前面（在 CommonMiddleware 之前）
    "django.middleware.security.SecurityMiddleware",
    # ... 其他保持不变
]

# 开发期：只放行 Vite 的开发服务器
CORS_ALLOWED_ORIGINS = [
    "http://localhost:5173",
    "http://127.0.0.1:5173",
]

重启 runserver，CORS 报错消失。记住这个报错的长相，以后在别人项目里见到就知道怎么回事。

6.3 axios：比 fetch 更顺手的请求工具

cd frontend
npm install axios

新建 src/api.js——整个前端唯一发请求的地方，集中管理 baseURL 和登录态：

import axios from "axios";

const api = axios.create({
  baseURL: "http://127.0.0.1:8000/api",   // 第 7 章部署时改成 "/api" 即可
});

// 请求拦截器：每次发请求前，自动从 localStorage 取工牌带上
api.interceptors.request.use((config) => {
  const token = localStorage.getItem("access");
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// 响应拦截器：收到 401（工牌过期/无效）时，清空登录态并送去登录页
api.interceptors.response.use(
  (res) => res,
  (err) => {
    if (err.response?.status === 401) {
      localStorage.removeItem("access");
      localStorage.removeItem("refresh");
      localStorage.removeItem("username");
      if (!location.pathname.startsWith("/login")) {
        location.href = "/login";
      }
    }
    return Promise.reject(err);
  }
);

export default api;

拦截器（interceptor） 就是"所有请求/响应的统一关卡"：带工牌、处理过期这两件事写一次，全站 200 个请求全部生效——这就是封装的价值。

6.6 详情页：文章 + 评论

src/pages/PostDetailPage.jsx——本章信息量最大的一页，认真读：

import { useEffect, useState } from "react";
import { useParams, Link } from "react-router-dom";
import api from "../api";

function PostDetailPage({ user }) {
  const { id } = useParams();                 // URL 里的文章 id
  const [post, setPost] = useState(null);
  const [comments, setComments] = useState([]);
  const [commentText, setCommentText] = useState("");
  const [error, setError] = useState(null);

  useEffect(() => {
    const load = async () => {
      try {
        // 两个请求互不依赖，Promise.all 并行发，更快
        const [postRes, commentRes] = await Promise.all([
          api.get(`/posts/${id}/`),
          api.get("/comments/", { params: { post: id } }),
        ]);
        setPost(postRes.data);
        setComments(commentRes.data);
      } catch (err) {
        setError("文章不存在或加载失败");
      }
    };
    load();
  }, [id]);    // id 变了（切换文章）就重新加载

  const handleComment = async (e) => {
    e.preventDefault();
    try {
      // 后端要求评论带 post 字段；author 由后端从 token 里取
      const res = await api.post("/comments/", { post: Number(id), content: commentText });
      setComments([...comments, res.data]);   // 追加到列表（不可变更新！）
      setCommentText("");
    } catch (err) {
      alert("评论失败：" + JSON.stringify(err.response?.data || err.message));
    }
  };

  if (error) return <p>{error} <Link to="/">回首页</Link></p>;
  if (!post) return <p>加载中...</p>;

  return (
    <article>
      <h1>{post.title}</h1>
      <p className="meta">作者：{post.author}</p>
      <div>{post.content}</div>

      <h2>评论（{comments.length}）</h2>
      {comments.map((c) => (
        <p key={c.id}>
          <b>{c.author}</b>：{c.content}
        </p>
      ))}

      {/* 登录了才显示评论框；没登录引导去登录 */}
      {user ? (
        <form onSubmit={handleComment}>
          <input
            value={commentText}
            onChange={(e) => setCommentText(e.target.value)}
            placeholder="说点什么..."
          />
          <button type="submit">发表评论</button>
        </form>
      ) : (
        <p>
          <Link to="/login">登录</Link> 后才能评论
        </p>
      )}
    </article>
  );
}

export default PostDetailPage;

三个工程要点：① Promise.all 并行请求；② useEffect 依赖 [id] 实现路由参数变化时重新加载；③ 发评论成功后用响应数据更新本地 state 而不是重新请求一遍列表——小应用两种都行，但要知道前者更高效。

07 · 部署上线：让全世界访问你的博客

本章目标：把本地跑得好好的 MyBlog 部署到一台 Linux 云服务器上，配上域名和 HTTPS。这一章做完，你的简历上可以写"独立完成全栈项目并部署上线"。

7.1 开发环境 vs 生产环境

本地跑得好好的，上生产前必须理解这五个差别：

开发环境 生产环境
后端服务器 runserver（Django 自带，单线程、不安全，仅供开发） Gunicorn（专业 WSGI 服务器）
前端 Vite 开发服务器（5173，带热更新） npm run build 出来的静态文件，交给 Nginx 托管

前后端地址 5173 和 8000 两个端口，需要 CORS 同一个域名，CORS 问题自然消失

  1. 设置 root 密码（或 SSH 密钥）
  2. 防火墙/安全组只开放 22（SSH）、80（HTTP）、443（HTTPS）——千万别开 8000，后端必须藏在 Nginx 后面

apt update

7.3 代码上服务器：走 Git

第 0 章装好了 Git，现在它开始发光。把 MyBlog 推到 GitHub 或 Gitee（私有仓库），然后在服务器上：

顺手检查项目根目录的 .gitignore，确保这些没被提交：.venv/、node_modules/、db.sqlite3、__pycache__/。

7.4 后端：Gunicorn + 生产配置

服务器上建虚拟环境、装依赖：

python3 -m venv .venv
source .venv/bin/activate      # 服务器是 Linux，路径没有 Scripts
pip install -r requirements.txt
pip install gunicorn "psycopg[binary]"

myblog/settings.py 改成生产配置：

DEBUG = False
ALLOWED_HOSTS = ["你的域名.com", "你的服务器IP"]

进阶提醒：SECRET_KEY 和数据库密码不该写死在代码里（git 会带走它们）。规范做法是读环境变量：SECRET_KEY = os.environ.get("SECRET_KEY")，个人项目初期可先简化，但仓库务必保持私有。

切 PostgreSQL（生产标配，SQLite 单文件扛不住并发）：

apt install -y postgresql
sudo -u postgres psql

CREATE USER myblog WITH PASSWORD '换成强密码';
CREATE DATABASE myblog OWNER myblog;
\q

# settings.py 的 DATABASES 换成
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "myblog",
        "USER": "myblog",
        "PASSWORD": "换成强密码",
        "HOST": "127.0.0.1",
        "PORT": "5432",
    }
}

初始化数据库并收集静态文件：

python manage.py migrate
python manage.py createsuperuser
python manage.py collectstatic      # 把后台和 DRF 界面的静态文件归拢到 staticfiles/

用 Gunicorn 试跑：

gunicorn myblog.wsgi:application --bind 127.0.0.1:8000 --workers 3

没有报错、curl 127.0.0.1:8000/api/posts/ 有 JSON 返回，就 Ctrl+C，把它交给 systemd 托管（开机自启、崩了自动拉起）。新建 /etc/systemd/system/myblog.service：

[Unit]
Description=MyBlog Gunicorn Service

User=ubuntu
WorkingDirectory=/home/ubuntu/myblog

7.5 前端：build 出静态文件

前端项目在本地 build 就行（服务器不用装 Node）。部署前改一处代码——frontend/src/api.js 的 baseURL：

const api = axios.create({
  baseURL: "/api",    // ← 不再写完整地址！前端和 API 将在同一个域名下
});

这个改动的妙处：前端和接口同域之后，开发期配置的 CORS 整个都不需要了（同源策略只拦"跨域"，同域随便走）。如果你在 Nginx 里也配了 /api/ 代理（下面会配），一切自洽。

本地构建：

cd frontend
npm run build        # 产出 dist/ 目录——压缩混淆后的最终静态文件

传到服务器：

# 本地 Git Bash 执行
scp -r dist/* root@你的服务器IP:/var/www/myblog/
# 若目录不存在，先在服务器上：mkdir -p /var/www/myblog

7.6 Nginx：门卫上岗

新建 /etc/nginx/sites-available/myblog：

server {
    listen 80;
    server_name 你的域名.com;      # 没有域名就先写服务器 IP

    # ① React 静态文件（用户访问的所有普通路径）
    root /var/www/myblog;
    index index.html;

    location / {
        # 找得到文件就给文件；找不到（如 /posts/3）就回 index.html，
        # 让前端路由接管 —— SPA 必须这样配，否则刷新 404
        try_files $uri /index.html;
    }

    # ② Django 后台的静态资源
    location /static/ {
        alias /home/ubuntu/myblog/staticfiles/;
    }

    # ③ 接口和后台转交给 Gunicorn
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /admin/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
    }
}

启用并重载：

ln -s /etc/nginx/sites-available/myblog /etc/nginx/sites-enabled/
rm /etc/nginx/sites-enabled/default      # 移除默认站
nginx -t                                  # 语法检查，必须显示 ok
systemctl reload nginx

浏览器访问 http://你的服务器IP ——你的博客上线了。注册、发文章、评论，全流程再走一遍。systemctl status myblog 和 journalctl -u myblog -n 50（看后端日志）是你接下来的好朋友。

7.7 HTTPS：certbot 一键搞定

有域名（把它解析到服务器 IP 后）：

apt install -y certbot python3-certbot-nginx
certbot --nginx -d 你的域名.com

certbot 自动改 Nginx 配置加 443 监听和证书自动续期。浏览器地址栏的小锁，5 分钟到手。

09 · Node.js 与运行时：代码到底是怎么跑起来的

建议在读完全套主线（08 之前任一时刻）后来啃本章。这一章回答一个你天天在用、但可能从没想明白的问题：你写下的代码是死的文本，是谁、怎么把它变成"正在运行"的东西的？搞懂"运行时（runtime）"，JS、Python、以后学 Go/Java 的新东西，全都豁然开朗。

9.1 什么是运行时（Runtime）

先给一个尽量直白的定义：

运行时 = 让代码跑起来的那套程序。它负责：读入并执行你的代码（解释或编译）、提供语言之外的内置能力（读写文件、网络、定时器）、管理内存（垃圾回收）。

一个关键认知——"语言"和"运行时"是两个东西：

  • 语言：语法规则、数据类型、控制结构的定义（JS 的语言规范叫 ECMAScript；Python 的语言规范是语言参考手册）
  • 运行时：这门语言的具体"实体化"。同一门语言可以有多个运行时

用你已经会的 Python 建立直觉：

概念 Python 世界 JS 世界
语言 Python 语言 ECMAScript（JS 标准）
运行时 CPython（最常用）、PyPy、MicroPython 浏览器、Node.js、Bun、Deno
引擎（执行核心） CPython 的虚拟机（执行字节码） V8（Chrome/Node）、SpiderMonkey（Firefox）、JavaScriptCore（Safari）
内置能力 os、json、sys 这些标准库 fs、http、setTimeout（由运行时提供）

这解释了很多"玄学"问题：

  • 为什么 alert() 在浏览器能跑，在 Node 里报 alert is not defined？ 因为 alert 不是 JS 语言的，是浏览器运行时提供的。语言只规定语法，"自带哪些函数"取决于宿主环境。
  • 为什么 fs（读文件）在浏览器里没有？ 浏览器运行时出于安全不给你文件系统，Node 运行时在服务器上给。
  • console.log 是语言的一部分吗？ 不是。console 是运行时提供的调试输出对象（浏览器和 Node 都提供了，所以两边都能用）。
  • Python 换成 PyPy 会快一些，语法没变 —— 同理，你的 JS 代码放在 V8（Node）和 JavaScriptCore（Bun）里跑，底层行为一致、性能细节不同。

所以准确的说法是：你这几年学的是"在 CPython 运行时上跑的 Python"和"在 Node/浏览器运行时上跑的 JS"。

9.2 引擎：运行时的心脏（V8 vs CPython）

运行时里真正"执行代码"的核心叫引擎。以 JS 世界最出名的 V8（Google 用 C++ 写，Chrome 和 Node 共用）为例，执行一条语句的旅程：

源代码 (你写的 .js)
   │  ① 解析（词法+语法分析）
   ▼
抽象语法树 AST
   │  ② 编译成字节码
   ▼
Ignition 解释器：逐条执行字节码（程序启动，快）
   │  ③ 发现某段函数被反复调用（"热点代码"）
   ▼
TurboFan 优化编译器：把热点代码直接编译成机器码（跑得飞快）
   │  ④ 如果假设落空（比如函数参数类型变了）→ "去优化"，退回字节码
   ▼
机器码

这套"边解释、边观察、热点编译成机器码"的技术叫 JIT（即时编译）。对比一下：

  • CPython：主流路线是把源代码编译成字节码，交给一个 C 写的虚拟机解释执行（3.13+ 正在实验性加入 JIT）。所以纯计算场景 Python 比 JS 慢不少。
  • V8：解释起步 + 激进 JIT。热点代码接近原生速度。

还有一层——内存管理。两者都帮你自动回收垃圾，但策略不同：

  • CPython：以引用计数为主（对象一没人引用立刻回收），辅以分代 GC 处理循环引用
  • V8：分代垃圾回收——新对象放"新生代"频繁快速清理，活下来的晋升到"老生代"低频深度清理

你不需要会调 GC，但要知道：内存溢出、内存泄漏是运行时层面的事，排查时看的堆快照（Node 里 heapdump/Chrome DevTools）就是引擎内存的现场照片。

9.3 Node.js = V8 + libuv + 内置库

V8 只会"算"：执行对象、函数、运算。它不知道怎么读文件、监听网络端口——这些"和外界打交道"的能力，是 Node 运行时在 V8 之外补上的。Node 的构成：

┌─────────────────── Node.js 运行时 ───────────────────┐
│                                                      │
│   你的 JS 代码                                        │
│      │                                               │
│   内置模块层:  fs / http / path / crypto / os ...     │ ← JS/C++ 混合实现
│      │                                               │
│   绑定层 (bindings): 把 C++ 能力暴露成 JS 函数         │
│      │                                               │
│   ┌──────────┐        ┌──────────────────────┐       │
│   │ V8 引擎   │        │ libuv                │       │
│   │ 执行+GC   │        │ 事件循环 + 线程池      │       │
│   └──────────┘        └──────────────────────┘       │
└──────────────────────────────────────────────────────┘

2009 年 Ryan Dahl 创造 Node 时的核心洞察：服务器程序的瓶颈通常不是"计算"，而是"等 I/O"（等数据库返回、等磁盘、等网络）。与其每个请求挂起一个线程干等，不如让一个线程 + 事件循环同时照看成千上万个"正在等待"的任务。

libuv 就是这个事件循环的 C 库实现：

  • 网络 I/O：注册到操作系统的事件通知机制（Linux 的 epoll、macOS 的 kqueue、Windows 的 IOCP），谁就绪就回调谁——不用线程干等
  • 文件读写、DNS、加密等真阻塞的操作：丢进线程池（默认 4 个线程）执行，完成后把回调扔回主线程

所以关于"Node 是单线程"这句话的准确理解是：

执行你 JS 代码的主线程只有一个（同一时刻只做一件事），但运行时内部有线程池和操作系统在并行干活。单线程换来的是：没有死锁、没有竞态、不用考虑 GIL 那类问题；代价是：一个耗时计算就会卡住所有人（CPU 密集是弱项，后面有实验）。

对照 Python 记忆：Django/Flask 默认是"同步框架"，靠多进程（Gunicorn workers）扛并发，受进程数限制；asyncio 生态（FastAPI）用的"事件循环"和 Node 的 libuv 是同一个思想。区别在于 Python 要你显式写 async def，而 Node 从出生起整个生态就是事件驱动的。

9.4 亲手做四个实验（比读十篇文章有用）

新建 runtime-lab/ 目录，边跑边看。

实验 1：证明主线程是单线程的（阻塞一切）

01-block.js：

console.log("start");
setTimeout(() => console.log("timer 回调（预期 100ms）"), 100);

// 用一个空循环把主线程占住 3 秒（纯计算，故意阻塞）
const start = Date.now();
while (Date.now() - start < 3000) {}

console.log("同步代码结束");

运行 node 01-block.js。注意看："timer 回调"出现在约 3 秒之后而不是 100ms——定时器到点了，但主线程被同步循环占着，回调只能排队。这就是"CPU 密集任务拖垮 Node 服务"的最小复现：如果你的接口里有这种大循环，整个进程的所有请求都得等它。

实验 2：证明 I/O 是非阻塞的

先造个大文件：head -c 10M /dev/urandom > big.txt（Git Bash 可用；或用 Python 生成），然后 02-async-io.js：

const fs = require("node:fs");

console.log("① 发起读文件请求");
fs.readFile("big.txt", "utf8", () => console.log("③ 文件读完了"));
console.log("② 主线程立刻继续干别的，没干等");

输出顺序一定是 ①②③——readFile 把活交给 libuv，主线程马上返回。"你先去忙，好了叫我"，这就是回调的本质。

实验 3：宏任务 vs 微任务（必考题）

03-microtask.js：

console.log("1 同步");

setTimeout(() => console.log("4 宏任务: setTimeout"), 0);

Promise.resolve().then(() => console.log("3 微任务: Promise"));

console.log("2 同步");

输出：1 → 2 → 3 → 4，即使 setTimeout 写的是 0 毫秒。规则：

异步回调分两个队列：微任务（Promise 的 .then、await 的续体、queueMicrotask）和宏任务（setTimeout、I/O 回调）。执行顺序是：跑完当前同步代码 → 清空全部微任务 → 取一个宏任务 → 又清空全部微任务 → …。微任务永远插队。

为什么要有微任务？因为 Promise 链要求"状态一变，后续立刻、在同一次事件循环内执行"，不能等下一轮。

实验 4：await 的真面目

04-await.js：

async function main() {
  console.log("a 同步执行");
  await null;            // 从这里开始，函数剩余部分被包装成微任务
  console.log("c 微任务里执行");
}
main();
console.log("b 同步代码还没跑完呢");
// 输出: a → b → c

async/await 只是 Promise + 微任务的语法糖：await 把后面的代码"挂起"成微任务，函数立即返回，事件循环继续。理解了这一点，async 函数"看起来同步、实际异步"的所有反直觉现象（比如你没法用 try 在外面同步接住它的错误、它在事件循环的哪个阶段执行）都有了统一解释。

Node 特有的一层：nextTick 与阶段

Node 的事件循环按阶段转圈：timers（到期定时器）→ pending → poll（I/O）→ check（setImmediate）→ close，每跑完一个回调就把微任务清空一次。另外 Node 有个比 Promise 微任务优先级还高的 process.nextTick。浏览器没有这些概念（浏览器的循环更简单），所以"同样的事件循环代码，Node 和浏览器输出可能有差异"——面试常问的 setImmediate vs setTimeout(0) 之争就出在这里。日常记住一条就够：微任务（Promise）快于定时器类宏任务。

9.5 浏览器运行时 vs Node 运行时

同一个 V8，两种宿主，能力清单完全不同：

浏览器运行时 Node 运行时
引擎 V8 / SpiderMonkey / JavaScriptCore V8
全局对象 window globalThis（推荐写法，两边通用）
操作 DOM ✅（document、DOM API） ❌
读文件系统 ❌（沙箱安全） ✅ fs
网络 fetch、WebSocket http 服务器、fetch（18+）
进程能力 ❌ ✅ process、子进程
典型用途 用户界面 服务器、命令行工具、构建工具

注意 fetch、setTimeout、console 两边都有——因为两边运行时都决定提供它（Node 18 起 fetch 由 undici 实现），不是因为语言规定。

顺带认识两个新运行时，理解了"运行时"再看它们就毫无神秘感：

  • Deno：Node 作者的"修正版"——V8 + Rust，默认安全（不授权不能碰文件/网络）、原生 TypeScript 支持、URL 导入
  • Bun：性能激进的新运行时，用 JavaScriptCore 引擎（不是 V8），自带包管理器和打包器，兼容大部分 Node API

它们证明了本章的核心观点："JS 语言"没变，变的是"谁、用什么组件、在什么环境里执行它"。

9.6 动手：不用任何框架写一个 HTTP 服务器

第 6 章 React 调的 /api/posts/ 背后是 Django；现在用 30 行纯 Node 造一个最小服务器，看看"框架之下"是什么：

05-server.js：

import http from "node:http";

const posts = [
  { id: 1, title: "理解运行时", author: "小明" },
  { id: 2, title: "事件循环", author: "小红" },
];

const server = http.createServer((req, res) => {
  // req：请求对象（方法、URL、头）；res：用来写响应
  console.log(req.method, req.url);

  if (req.url === "/api/posts") {
    res.writeHead(200, { "Content-Type": "application/json; charset=utf-8" });
    res.end(JSON.stringify(posts));       // 对象 → JSON（第 1 章学的）
  } else {
    res.writeHead(404, { "Content-Type": "application/json; charset=utf-8" });
    res.end(JSON.stringify({ error: "Not Found" }));
  }
});

server.listen(3000, () => {
  console.log("服务器跑在 http://localhost:3000");
});

node 05-server.js 后访问 http://localhost:3000/api/posts，你得到了和 DRF 一样的 JSON。

体会三件事：① Node 的 http 模块本身就是 Web 服务器——Python 世界里这层由 Gunicorn/WSGI 充当，Django 只管业务；Node 里运行时直接把端口监听能力给了你。② Express/Django 那些框架做的事，本质就是帮你整理路由分发、解析请求体、统一错误处理——现在你知道它们抽象掉了什么。③ req.url、JSON 响应——第 0 章 HTTP 知识的代码版。

9.7 工程层面：模块系统与 process

两代模块系统（你在第 2 章用的 import/export 是新一代 ESM）：

// CommonJS（Node 老一代，2020 前所有教程都是它）
const fs = require("node:fs");
module.exports = { hello };

// ESM（语言标准，Node 14+ 完整支持，现代默认）

export function hello() {}

Node 里用 ESM 的条件：package.json 里写 "type": "module"，或文件后缀 .mjs。老代码里 require 还到处都是，必须认识。

process 对象——Node 运行时给你的"进程遥控器"，部署章其实已经用到了它的近亲：

9.8 再深一层：工程与排错的细节

这一节是"用的时候回来查"型内容，不必一次读完。

Node 是怎么找到你 require/import 的模块的

解析顺序（面试常考）：

  1. 内置模块优先：require("fs") 命中 Node 自带的，不是你 node_modules 里的同名包
  2. 相对/绝对路径：./utils → 尝试补后缀 utils.js、utils.json、utils/index.js……
  3. 裸包名（import axios from "axios"）：从当前目录的 node_modules 开始找，找不到就往上一级目录继续找，直到文件系统根——这就是为什么嵌套目录里也能引到根目录装的包，以及为什么 npm ls 能显示依赖树

包自己的 package.json 里的 main / exports 字段决定"别人 import 这个包名时实际加载哪个文件"。

CommonJS 的模块缓存与循环依赖

CJS 模块首次被 require 时执行一次，之后全部命中缓存：

// counter.js
let count = 0;
setTimeout(() => { count = 100 }, 50);
module.exports = { getCount: () => count };

// a.js
const c = require("./counter");
console.log(c.getCount());   // 0 —— 拿到的是同一个模块实例

推论一：模块级状态天然是"单例"（数据库连接池就这么实现）。推论二：循环依赖会拿到"半成品"——A require B、B 又 require A 时，后加载的一方拿到的是 A 还没填完的 exports。ESM 用"先解析全部依赖再执行"的方式把这问题消灭了大半，但设计上仍应避免循环依赖。

版本号与 lock 文件（为什么两个人 npm install 结果不同）

package.json 里的 "axios": "^1.7.0" 是 semver 语义化版本约束：主版本.次版本.补丁；^ 允许升级次版本（1.x 内最新），~ 只允许补丁级（1.7.x）。所以同一份 package.json 不同时间安装可能得到不同小版本——package-lock.json 就是把"实际装到的精确版本"锁死，保证任何机器、任何时间装出完全一致的依赖。CI/部署环境用 npm ci（严格按 lock 装），比 npm install 更快更严格。

管理多个 Node 版本

不同项目可能要求不同 Node 版本（就像 Python 的虚拟环境问题）。Windows 上用 nvm-windows 或 fnm：

nvm install 22        # 装一个版本
nvm use 22            # 切换

项目根目录放一个 .nvmrc 文件写上版本号（如 22），团队所有人版本一致。

CPU 密集怎么办：worker_threads

单线程卡死的解法不是"换语言"，是把重活扔给工作线程：

// main.js
import { Worker } from "node:worker_threads";

const worker = new Worker(new URL("./heavy.js", import.meta.url));
worker.on("message", (result) => console.log("算完了:", result));
// 主线程全程不卡，接口照常响应

heavy.js 里的计算跑在独立线程，结果用消息传回来。多个进程的方案则是 cluster 模块（按 CPU 核数起多个 Node 进程分摊请求）——第 7 章 Gunicorn 起多个 worker 是完全同构的思路。

内存与泄漏排查（生产排错必备）

setInterval(() => console.log(process.memoryUsage().heapUsed), 5000);
// heapUsed：堆内存用量。健康的服务它是"锯齿形"（涨了又被 GC 压回去）
// 持续单边上涨 = 泄漏

三大常见泄漏源：① 挂在全局/模块级的大数组越积越多；② setInterval、事件监听器用完忘了清（clearInterval/removeListener）；③ 缓存只写不删。排查工具：node --inspect 启动后用 Chrome 访问 chrome://inspect，在 Memory 面板拍两张堆快照做对比，谁在涨一目了然。VS Code 里直接 F5 也能给 Node 代码打断点，比 console.log 强一个量级，值得花半小时学会。

10.1 动态类型的痛（先痛一下才有动力）

你写 JS 时一定遇到过（或迟早会遇到）这些场景：

// ① 拼错属性名，运行时才炸
const post = await api.get("/posts/1");
console.log(post.titel.toUpperCase());   // undefined.toUpperCase → 白屏

// ② 函数参数全靠记忆，传错没人拦
function createPost(title, views) { ... }
createPost(100, "我的文章");              // 参数顺序反了，静默写出脏数据

// ③ 重构像拆弹：改了字段名，谁知道哪些地方还在用？

根因：JS 是动态类型语言——类型属于"值"，直到代码真正跑起来那一刻才知道。 Python 其实也是动态类型，但 Python 生态大项目普遍用类型注解 + mypy/pyright 检查；JS 生态的答案是 TypeScript。

TS = JS + 静态类型系统。你写的还是 JS 的思维和运行方式，但多了一个"编译期检查员"帮你抓错。

收益三件套：错误在保存文件时暴露（而不是用户访问时）；IDE 智能提示变成可信赖的文档（输入 post. 直接列出所有合法字段）；重构不再靠祈祷（改名一个字段，所有引用处立刻标红）。代码量超过几百行、或多人协作，这三大收益会指数级放大。

10.2 TS 的本质：只管检查，不参与运行（本章核心）

直接上结论，然后动手证明：

TypeScript 不会出现在运行时。TS 编译器（tsc）或构建工具（Vite/esbuild）把 .ts 文件转译成纯 JS，类型标注在转译时被全部擦除。真正在 Node/浏览器运行时里跑的，是擦除后的 JS——上一章学的运行时对此一无所知。

这意味着：

  • 类型检查发生在"编译期"（写代码/构建时），运行时没有任何类型保护
  • TS 是"纸面契约"：它保证你的代码声明了 title: string，但不保证运行时拿到的数据真的是 string（数据来自接口/用户输入时尤其如此）
  • 没有"TS 虚拟机"这种东西——没有哪个引擎直接执行 TS

动手实验（5 分钟，做完终生难忘）：

mkdir ts-lab && cd ts-lab && npm init -y && npm i -D typescript

demo.ts：

function greet(name: string): string {     // 类型标注！
  return `你好, ${name}`;
}

const msg: string = greet("TS");
console.log(msg);

编译并查看产物：

npx tsc demo.ts        # 编译，生成 demo.js
cat demo.js            # 看看里面剩什么
node demo.js           # 用 Node 跑的是纯 JS

demo.js 长这样——所有类型痕迹消失：

function greet(name) {
    return `你好, ${name}`;
}
var msg = greet("TS");
console.log(msg);

再故意写个类型错误 greet(123)，运行 npx tsc demo.ts——编译阶段直接报错拒绝生成，错误根本没机会跑到运行时。这就是 TS 的工作方式：把错误从"生产事故"提前变成"保存文件时的红线"。

对应概念：tsc 这步叫转译（transpile）——源语言到同级别的语言（TS→JS），区别于编译成机器码（C→机器码）。Vite 开发时用 esbuild 转译（快，但不检查类型），所以 Vite 项目里 tsc --noEmit（只检查不产出）是单独一步。这是第 5 章模板里 build: "tsc -b && vite build" 的含义。

// 原始类型

let isPublished: boolean = false;

// 数组

let post: { id: number; title: string } = { id: 1, title: "a" };

// 函数：参数和返回值都标

  return a + b;
}

但别当"标注狂魔"——TS 的类型推断（inference）很强：

经验法则：局部变量靠推断；函数签名（参数必标）、模块边界（导出的函数/组件）、数据模型（接口返回）显式标注——这三处是"契约"，值得写明。

四个特殊类型（面试常客）

类型 含义 什么时候用
any 关闭检查，啥都能塞 尽量别用；用它的那天往往是偷懒的一天

void 没有返回值 回调函数、事件处理器
never 永远不会有值 抛异常/死循环的函数；类型系统里的"不可达"

// b.foo.bar();                              // ❌ 编译不过：先检查再用

10.4 interface / type 与结构化类型

描述对象形状的两种写法，功能大体重叠：

interface Post {
  id: number;
  title: string;
  content: string;
  author: string;
  createdAt: string;          // ISO 字符串，比如 "2026-09-12T08:00:00Z"
  tags?: string[];            // ? = 可选字段
  readonly id: number;        // readonly = 创建后不可改
}

// type 也能描述对象，还擅长联合/别名
type ID = number | string;
type RequestState = ...;      // 10.6 见

选择建议：团队统一即可。常见惯例是"数据模型用 interface、联合与工具场景用 type"。继承方面 interface 可以 extends，type 用 & 交叉：

interface Commentable { comments_count: number }
interface DetailedPost extends Post, Commentable {}
// 或 type DetailedPost = Post & Commentable;

结构化类型（structural typing）——TS 判断类型兼容的方式，和 Python 的鸭子类型神似但发生在编译期：

interface Logger { log(msg: string): void }

const myLogger = {
  log: (msg: string) => console.log(msg),
  extra: "多余的字段完全没关系",
};

const l: Logger = myLogger;   // ✅ 只要"形状"满足（有 log 方法），不看血统/名字

TS 只问一个问题："你有没有我需要的成员，类型对不对？"——不看叫什么名字、从哪来。这和 Python 的 duck typing 精神一致，只是检查从运行时提前到了编译期。

10.5 收窄与泛型：类型系统的两把利刃

收窄（narrowing）：联合类型怎么安全地用

function formatId(id: number | string) {
  // 这里 TS 只知道 id 是 number | string，禁止 id.toFixed() 这种假设
  if (typeof id === "number") {
    return `编号-${id.toFixed(0)}`;      // 这个分支里，TS 确认 id 是 number
  }
  return `编号-${id.toUpperCase()}`;     // 这个分支里，确认是 string
}

typeof、in、===、真值判断都会让 TS 自动缩窄类型——在分支里"精确知道"当前是什么。这就是"动态数据 + 静态检查"共存的工作方式。

泛型（Generics）：类型的"参数"

没有泛型时，写"返回和输入同类型"的函数只能退到 any。泛型让类型成为函数的参数：

function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

const n = first([1, 2, 3]);       // T 推断为 number → n: number | undefined
const s = first(["a", "b"]);      // T 推断为 string

你早就在用泛型了：Array<number>、Promise<Post[]>——尖括号里的就是类型参数。全栈里最实用的场景是给 API 请求封装类型：

async function apiGet<T>(url: string): Promise<T> {
  const res = await fetch(url);
  return res.json();              // 开发者用类型"担保"结构，见 10.7 的诚实提醒
}

const posts = await apiGet<Post[]>("/api/posts/");   // posts: Post[]，全链路有提示

工具类型：站在 Post 模型上体会

TS 内置一批"类型变换器"，正好用 MyBlog 的数据模型演示（对照第 0/4 章：列表页、发文章、PATCH 接口各需要什么字段）：

interface Post {
  id: number;
  title: string;
  content: string;
  author: string;
  createdAt: string;
}

type PostSummary   = Pick<Post, "id" | "title">;        // 列表页只要这两个字段
type PostDraft     = Omit<Post, "id" | "createdAt">;    // 发文章时还没有 id 和时间
type PatchPost     = Partial<PostDraft>;                // PATCH：所有字段可选
type PostsById     = Record<number, Post>;              // { 1: Post, 2: Post } 映射表

体会一下价值：后端加字段、前端模型改一处，所有依赖这个模型的函数签名联动报错/更新——这就是"重构不再靠祈祷"。

10.6 可辨识联合：React 状态建模的最佳实践

一个组件的请求状态有三种：加载中 / 成功 / 失败。用三个 boolean？会写出 loading=true && error!=null 的矛盾状态。TS 的可辨识联合（discriminated union）从类型上杜绝它：

type RequestState<T> =
  | { status: "loading" }                          // 只有 status
  | { status: "success"; data: T }                 // success 才有 data
  | { status: "error"; message: string };          // error 才有 message

status 是"判别标签"——组件里收窄后，每个分支只能访问自己该有的字段：

function PostList({ state }: { state: RequestState<Post[]> }) {
  if (state.status === "loading") return <p>加载中...</p>;
  if (state.status === "error") return <p>出错了：{state.message}</p>;
  return state.data.map(p => <PostCard key={p.id} post={p} />);   // 这里才有 data
}

对比第 5 章用 loading / error / posts 三个 state 组合的方式：联合类型把"不可能的状态"在类型层面消灭了。这是 TS 对 React 项目最大的单项提升。

// api.ts
import axios from "axios";
import type { Post, Comment, Page, LoginResponse } from "./types";

const api = axios.create({ baseURL: "/api" });

api.interceptors.request.use((config) => {
  const token = localStorage.getItem("access");
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

export async function getPosts(keyword?: string): Promise<Post[]> {
  const res = await api.get<Page<Post>>("/posts/", {
    params: keyword ? { search: keyword } : {},
  });
  return res.data.results;
}

export function createPost(draft: { title: string; content: string }) {
  return api.post<Post>("/posts/", draft);
}

export function getComments(postId: number): Promise<Comment[]> {
  return api.get<Comment[]>("/comments/", { params: { post: postId } }).then(r => r.data);
}

export function login(username: string, password: string): Promise<LoginResponse> {
  return api.post<LoginResponse, any, { username: string; password: string }>(
    "/auth/login/", { username, password }
  ).then(r => r.data);
}

10.8 tsconfig：检查员的执法尺度

npx tsc --init 生成配置，全栈项目最该关注这几项：

{
  "target": "ES2022",            // 转译成哪个年代的 JS
  "module": "ESNext",            // 模块系统（配合打包器）
  "strict": true,                // ⭐ 总开关：开启全部严格检查，新项目必开
  "noEmit": true,                // Vite 项目：转译交给 esbuild，tsc 只检查
  "jsx": "react-jsx"             // React 项目
}

strict 打开后最有感的两条：变量不允许隐式 any、可能为 null 的值使用前必须判空。它会在短期内让你痛苦，长期让你写的代码不需要调试空指针。

最后一个诚实提醒（呼应 10.2）：TS 的担保止步于编译期。接口真正返回的数据结构，运行时 TS 管不着——后端悄悄把 count 改成字符串，TS 不会知道。严谨的方案是在运行时校验外来数据（zod 是事实标准：const Post = z.object({...}); Post.parse(data)）。个人项目可先不做，但要建立这个意识：类型声明是"信任的前端"，运行时校验是"信任的边界"。

10.9 类型工具箱再进一步

同样属于"用到时回来查"的进阶件，先混个脸熟。

从"值"里取类型：typeof 与 keyof

const config = { host: "127.0.0.1", port: 8000 };

type Config = typeof config;              // { host: string; port: number } —— 从值反推类型
type ConfigKey = keyof Config;            // "host" | "port" —— 取所有键的联合

// 泛型约束 + 索引访问：写一个"键名打错就编译报错"的取值函数
function getConfig<K extends keyof Config>(key: K): Config[K] {
  return config[key];
}
const port = getConfig("port");           // ✅ 类型是 number
// getConfig("prot");                     // ❌ 编译期直接抓出拼写错误

typeof（类型世界的，和 JS 运行时的 typeof 运算符重名但两回事）+ keyof + 索引访问 Config[K] 这三件套，是读第三方类型定义和写工具类型的地基。

satisfies：校验，但不丢推断

type Routes = { [path: string]: { title: string; auth: boolean } };

const routes = {
  "/": { title: "首页", auth: false },
  "/new": { title: "写文章", auth: true },
} satisfies Routes;

用 : Routes 标注也能检查，但会把 routes 的类型拓宽成 Routes，之后 routes["/"] 就丢了具体信息；satisfies 是"按 Routes 检查，但保留字面量的精确类型"——配置表场景的神器。

类型谓词：自定义"守卫函数"

function isPostArray(data: unknown): data is Post[] {
  return Array.isArray(data) && data.every((d) => typeof d.id === "number");
}

const data: unknown = await res.json();
if (isPostArray(data)) {
  data[0].title;      // ✅ 在这个分支里，TS 确认 data 是 Post[]
}

参数 is 类型 这种返回值叫类型谓词——把 10.3 里 unknown 的手工检查封装成可复用的函数，是打通"运行时校验 → 静态类型"的桥梁（zod 的 .parse() 内部就是这套路子的工业级版本）。

映射类型：批量变换的工具类型是怎么造出来的

Partial、Readonly 这些内置工具类型的实现原理，就一层窗户纸——映射类型：

type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];      // 遍历 T 的每个键，原样取出类型加上 readonly
};
type MyPick<T, K extends keyof T> = {
  [K2 in K]: T[K2];                   // Pick 的实现
};

看懂这两个，官方手册的 Utility Types 页面对你就不再有神秘感。

DRF 骨架：

class PostViewSet(viewsets.ModelViewSet):
    serializer_class = PostSerializer
    permission_classes = [permissions.IsAuthenticatedOrReadOnly]

    def get_queryset(self):
        qs = Post.objects.all().select_related("author")
        if q := self.request.query_params.get("search"):
            qs = qs.filter(title__icontains=q)
        return qs

    def perform_create(self, serializer):
        serializer.save(author=self.request.user)
